[#purpose]
== Purpose

Souther is a JVM-targeted language for transcribing the *specification DSL* of Specification Model-Driven Development (SMDD) into an implementation model with minimal translation.

The spec DSL expresses business rules using only `+data+` (AND / OR / List / `+?+`) and `+behavior+` (`+->+` / `+>->+`). Constraints on the values themselves ("amount is non-negative", "the approver is the applicant's manager"), the confinement of construction paths, and dependency on the outside world are not written there. The spec DSL deliberately leaves these three in comments.

Souther's role is to make those three executable.

[cols="1,1",options="header"]
|===
| What the spec DSL leaves in comments | How Souther makes it executable

| Value constraints (`+// at least 0+`, `+// the approver is the applicant's manager+`) | `+invariant+`

| The invariant "this value has been validated" | Confinement of construction paths (`+decoder+` / `+constructs+`)

| `+// depends: productCatalogue+` / `+// side effect: sendingMail+` | A `+behavior+` with no `+let+` at a leaf; `+depends on+` (an injected Java implementation) at the call site

|===

The structure of the spec DSL (distinction, requiredness, multiplicity, state transition, totality) maps directly onto Souther's types. What the spec DSL cannot guard it divides up: structure by types, value constraints by tests, part of requiredness by the types an implementation is written against. Souther takes that remainder into the implementation model — a value constraint becomes an `+invariant+`, and an outside-world dependency an injected behavior.

[#mapping-principle]
=== Mapping principle

Each construct of the spec DSL maps to Souther as follows.

[cols="1,1",options="header"]
|===
| Spec DSL | Souther

| `+data Amount = Integer // at least 0+` | `+data Amount = Int invariant value >= 0+` (newtype; <<newtype>>)

| `+data X = A OR B+` (A, B are named data) | `+data X = A \| B+` (sum; cases are existing named data)

| `+data Reimbursement = Unit+` | `+data Reimbursement+` (data with no fields; a case named in a sum or a behavior output needs no declaration, <<unit-data>>)

| `+data X = A AND b+` (A is a record, b is an added item) | `+data X = { ...A, b: B }+` (field composition)

| `+List<T>+` / `+T?+` | `+List<T>+` / `+T?+`

| `+behavior f = In -> Out+` (Out has multiple success states) | `+behavior f : (...) -> Out1 \| Out2+` (bare sum)

| `+behavior f = In -> Out OR Failed+` | `+behavior f : (...) -> Out \| Rejected+` (a failure is just data; departure from the mainline is decided by composition)

| `+f >-> g+` | `+f >-> g+`

| `+// depends+` / `+// side effect+` | A `+behavior+` with no `+let+`

| `+// precondition+` | `+guard ... else+` (a business branch, not a contract; <<violation-destination>>)

|===

[#boundary]
=== The boundary with the outside world

Souther does not handle the outside world directly. The boundary is expressed with primitive values, collections, and Decoders / Encoders.

[,text]
----
outside world
  ↓
primitive values / collections
  ↓ Decoder
internal data
  ↓ behavior
internal data
  ↓ Encoder
primitive values / collections
  ↓
outside world
----

The JVM is used as the distribution platform that makes the generated types and behaviors available to Java programs.

[#design-principles]
== Design principles

[#closed-construction]
=== Construction paths of data are closed

A value of a given `+data T+` MAY be constructed only through one of the following.

* the Decoder of `+T+`
* the implementation of a behavior declaring `+constructs T+` (a Souther `+let+`, or an injected Java implementation)
* compiler-generated code

A behavior that merely writes `+T+` as its return type MUST NOT be able to construct `+T+`. The authority to construct belongs to the behavior, not to its implementation. Therefore `+constructs+` is written on the behavior (<<constructs>>); the `+let+` and the Java implementation receive the authority from the same declaration.

A helper `+let+` with no corresponding behavior (<<fn-declaration>>) MAY also construct data. In that case the constructed data MUST appear in the `+constructs+` of the behavior that calls that `+let+`.

The type need not be declared in the same module. A behavior constructs what its `+constructs+` names, and a type another module exposes is built through the same checked entry as any other, so its invariant runs either way. A type a module does not expose cannot be built elsewhere — there is no name for it, and no entry — which is also why arithmetic that would build one is a compile error (<<newtype-arithmetic>>).

[#invariant-on-construct]
=== Invariants are checked on every construction

Every invariant declared on a `+data+` MUST be checked on every construction path. A value that violates an invariant MUST NOT be returned.

The destination of a violation differs inside and outside the boundary: in a Decoder it becomes a failure of Raoh's `+Result+`; inside the domain it aborts (<<violation-destination>>).

[#separate-representation]
=== External representation and internal data are separated

A Decoder constructs internal data from an external representation; an Encoder converts internal data to an external representation. An external representation MUST NOT be cast directly to internal data.

[#behavior-composition-unit]
=== behavior is the unit of composition

Internal computation, outside-world dependency, validation, and conversion are all expressed as behaviors and composed sequentially with `+>->+`. A behavior is a top-level input/output relation with no owning class.

As a type, a behavior states *only the specification*. A simple behavior has no implementation; the implementation is written as a `+let+` (<<fn>>). If none is written, it is injected from Java (<<injected-behavior>>). The exception is `+>->+` composition, which is itself the implementation.

Only behaviors that appear in the spec DSL are behaviors; implementation helpers remain `+let+`. This keeps the list of behaviors aligned with the spec DSL.

[#no-impl-for-outside]
=== No implementation is written for outside-world dependencies

Outside-world dependencies — DB, HTTP, files, clock, ID generation — MUST NOT be implemented in the language. These correspond to the `+// depends:+` and `+// side effect:+` notes in the spec DSL. Only the type is declared in the language.

[,text]
----
behavior findMember : (id: MemberId) -> Member | NoSuchMember    // no let
----

The implementation is injected from Java. Writing no implementation (`+let+`) is what "provided from outside" means (<<injected-behavior>>). A caller writes that name in its `+depends on+` (<<depends-on>>). The distinction between dependency (only reads the outside) and side effect (changes the outside) is documentation of intent; it does not affect the rules of value composition.

[#unmarked-sum]
=== Business results are expressed as bare sums

Every business result is returned as a sum of domain data. A *business* "failure" is not a first-class concept in the language. A behavior's output is a bare sum. The case that a downstream stage does not consume in a `+>->+` composition is what departs from the mainline (<<composition>>). *Unexpected* failures such as out-of-memory or a network drop MUST NOT be listed in the type.

An invariant violation MUST NOT appear here. It is not a business result but a model bug, and its destination is an abort (<<algebraic-types>>).

Multiple independent validation errors are accumulated inside the Decoder (<<case-propagation>>).

[#asymmetric-interop]
=== Java interop is asymmetric

Java MAY use the generated artifacts. Souther MUST NOT call arbitrary Java APIs directly.

[,text]
----
Java   -> Souther artifacts     allowed
Souther -> arbitrary Java API    forbidden (touch the outside only via a behavior with no implementation)
----

[#out-of-scope]
== Out of scope

Souther does not have the following. These are design decisions, not features to be added later.

* arbitrary Java API calls
* mutable state
* exceptions (see below)
* null
* threads
* asynchronous processing in the language
* inheritance
* structural intersection types (`+A & B+`; see <<union-intersection>>)
* a function stored in a data field (it has no external representation, so it would break decoder / encoder derivation; <<decoder>>, <<encoder>>, <<blocks>>)
* reflection
* macros
* type classes
* higher kinds
* dependent types
* proof by SMT
* a termination prover a model writes measures for — recursion is proven total by size-change analysis, and what that cannot show is opted out with `+partial+` (<<fn-rules>>)
* a custom VM
* a package manager
* a REPL

Because the implementation of outside-world dependencies is delegated to Java, Souther itself has no DB, HTTP, or file APIs.

*On exceptions.* What is forbidden is *using exceptions to control business flow*. Business results are returned as cases of a sum (<<unmarked-sum>>); neither `+throw+` nor `+catch+` can be written.

The reporting path for model bugs, however, is not blocked. An invariant violation *aborts* (<<algebraic-types>>). An abort is not a Souther expression and has no catching syntax, so it cannot be used to control business flow.

A Java Binding at the boundary (the Java implementation of a behavior with no implementation; <<injected-behavior>>) is different. Against a *platform failure* (DB down, network drop, host not responding — anything that is not a domain outcome) it MAY throw an exception; Souther does not fold it into a case but passes it through to the boundary. The language (`+.sou+`) has no exceptions, but the Java side that touches the outside world may throw. The distinction is *domain outcome vs. platform failure*: a business-meaningful result such as "not found" or "insufficient stock" is a case; "infrastructure unavailable" or "not responding" is an exception (<<java-impl-rules>>).

[#modules]
== Source files and modules

The extension is `+.sou+`. Each file defines one module.

[,text]
----
module example.businesstrip
----

A single file compiled on its own MAY omit the `+module+` header and start directly with a `+data+`
/ `+behavior+` / `+let+`; the module is then named after the file (the file-name stem), or `+Main+`
when compiled from a source string with no file name. A module compiled together with others and reached by
`+import+` MUST write the header — an unnamed module cannot be the target of an `+import+`, so
omitting it there is a compile error.

Keywords and the standard library are in English, but user-defined identifiers (types, fields, behaviors) MAY use Unicode. Because the spec DSL is written in Japanese, business vocabulary can be used as identifiers directly. Identifiers SHALL be *NFC-normalized* before binding and comparison; in Japanese a precomposed character and a combining sequence can look identical, so without normalization names that look the same would diverge in binding. Source is UTF-8.

[,text]
----
data TravelRequest = Drafting | Submitted | AwaitingPreApproval | PreApproved
----

Public elements are listed with `+exposing+`.

[,text]
----
module example.businesstrip exposing (
    TravelRequest,
    submitTravelRequest,
    preApprove
)
----

`+exposing+` exposes at type granularity. A public data's `+decoder()+` / `+encoder()+` is always public API (<<jvm-codec>>), so member-level narrowing such as `+TravelRequest.decoder+` is not written — there is nothing to narrow.


When an exposed behavior is a `+>->+` composition, its output SHALL be written in `+exposing+` in the form `+name : cases+` (<<declared-composition-output>>). A composition's output is inferred from its stages (<<composition-with-requirements>>), but at the public boundary a signature is required rather than inference, so that the contract used by another module or by Java does not change silently when an upstream stage changes. Omitting it is a compile error (E1605).

[,text]
----
module example.order exposing (
    placeOrder : PlacedOrder | OutOfStock
)
----

`+exposing+` is the module's interface description: implementations are inferred, only the boundary is stated explicitly.

[#exposed-values]
==== A value and a helper are published

`+exposing+` MAY name a *value* — a `+let+` with no parameter list (<<fn-declaration>>) — and a *helper* — a `+let+` with them — alongside the module's data and behaviors. A limit a rule is written against, the representative record its examples are stated with, and the rule itself are part of what the module offers, and a reader names them instead of writing them out again.

[,text]
----
module example.pipeline exposing ( negotiatingDeal, taxIncluded, Deal, ... )

let negotiatingDeal = Negotiating { ... }
let taxIncluded (amount: Amount) = Amount(amount.value * 110 / 100)
----

An importer names the definition and nothing else: what it is built out of stays the declaring module's business, and does not join the reader's import list. What arrives is *closed* — the body with its own module's definitions already substituted into it — so a definition the importer happens to spell the same way is a different definition and changes nothing (<<qualified-reference>>).

A behavior's own `+let+` is not published, whatever its shape. What a reader of the module reaches is the behavior, which it calls; the `+let+` that satisfies it is an implementation, and the module publishes its specification.

A published definition MAY reach a *recursive* helper. Closing cannot remove one — it is lowered to a method rather than expanded (<<fn-rules>>) — so the helper travels with the body that calls it, under the name of the module that declares it, and so does every recursive helper it reaches in turn. The importing module emits them as its own methods, exactly as it does for a recursive standard-library helper it reaches. Which module declared a helper is its identity and not where its method goes: two modules may declare a recursive helper of one name, and one importer may end up emitting both.

A published value is substituted where it is named and a published helper expanded where it is called, exactly as one of the reader's own is (<<fn-value-semantics>>, <<fn-rules>>). What such a body builds is *not* the reader's to declare in `+constructs+`: publishing the definition is what states that origination, and the reader may have no name for the type. A type of some *third* module that the body happens to build is neither the reader's nor the publisher's to hand over, so that one stays the reader's to declare — which it can, since the module declaring it exposed it (<<closed-construction>>).

A published *value* rests on none of that. What a value builds belongs to its definition whatever module declares the type, so reading one across a boundary answers the same as reading one within a module (<<fn-value-semantics>>). Crossing the boundary is what the paragraph above is about, and a value never needed it.

A published body's source travels in the jar and is read back by the importing compiler (<<published-modules>>). What that source means is therefore part of what a compiled module promises, and is recorded under the same boundary version as the rest of it.

[#exposed-surface]
==== What reaches out may not rest on what is kept

What a module reaches out with SHALL NOT rest on a type it keeps to itself. An exposed data's field types, and an exposed behavior's input and output, are exposed by the module that declares them. A type carried inside a collection counts — `+List<UserId>+` names `+UserId+` as surely as a bare `+UserId+` does.

An exposed value SHALL NOT stand for a type the module keeps to itself, and an exposed helper SHALL NOT return one or take one — a reader would hold a value it has no name for, or be unable to write the argument it has to pass. What a definition stands for is its *type*, settled from its body (<<fn-rules>>), and not the constructions the body makes on the way: a definition may name a type it never builds (`+let published (n: Int) : List<Hidden> = []+`), and a type its body reached for on the way is its own workings — requiring those would put every inner type back in the reader's import list, which is what publishing the definition was for.

The same holds for an injected behavior — one with no `+let+` — whether or not it is in `+exposing+`, because the abstract base it generates is public regardless (<<java-base-class>>) and the implementation writes both types where it overrides `+apply+`.

Otherwise a reader is handed a value it has no name for, and the generated classes carry a public surface over classes it may not touch. It is reported where the module decides it, not at each reader that runs into it.

This does not reach the *cases* of a sum, or of an output written as more than one case. Those are generated as a union interface that is public regardless (<<jvm-anonymous-union>>), and a case reaches a reader through the decoder or through the `+protected+` factory rather than by being named — which is what E1305's unit-data allowance rests on. A module keeping a case to itself therefore stays a decision about the union, not about this rule.

[#imports]
Imports SHALL be listed explicitly. Wildcard imports are forbidden. A cyclic import is a compile error.

[,text]
----
import example.employee (
    Employee,
    EmployeeId
)
----

The standard library is imported in the same form: the qualifier — `+List+`, `+Map+`, `+Set+`, `+String+`, `+Bool+`, `+Int+`, `+Decimal+`, `+Date+`, `+DateTime+`, `+Option+` (<<reserved-namespace>>) — as the name, and the functions used listed. Once imported, they MAY be written unqualified (<<stdlib>>).

[,text]
----
import List ( map, filter, fold )
import String ( trim, split )
----

Qualified access (`+List.map+`) always works without importing, so `+import+` only elides the qualifier. Importing the same bare name from two modules is a compile error, reported at the second import line: writing both `+import String (length )+` and `+import List (length )+` says `+length+` is exposed from both. Import one and qualify the other call (`+String.length(...)+`). As with the wildcard prohibition, no name is delivered implicitly. A name the library does not have is a compile error at the import line, not at the first use.

An import says which names MAY be written without their qualifier. It does not say what one of them means where it is written: a binding in force means what it binds, and a name the module declares itself means that declaration. So `+import List ( map )+` and a parameter named `+map+` may sit in one module, and inside that parameter's scope `+map+` is the parameter. What a name means is settled once, wherever it is written — in a body, in an `+invariant+`, in an `+example+` row, in a `+fake+` — and an import is the last thing consulted.

[#published-modules]
=== Importing a module another project compiled

A module MAY be imported from the compiled output of another project, with no `+.sou+` of it in this
one. A compiled module carries what it declares — its `+data+` definitions, its behavior
signatures, its `+exposing+` line and the imports it was written under — on the classes it generated,
as the source that declared it. An `+import+` naming no module among the sources being compiled is
resolved against the compiled modules on the class path.

Nothing is declared beyond the dependency itself: under the annotation processor the class path is
the compile classpath, and the CLI takes `+-cp+` / `+--class-path+`.

[,text]
----
souther compile app/order.sou -d out-app -cp out-lib
----

What crosses that boundary is what crosses a boundary within one compilation: `+exposing+` is the
gate, and an imported type may not be a case of a sum declared here (<<e1606>>). An imported type in
a behavior's output union is unaffected — it joins through a bridge case this module emits
(<<bridge-case>>), so nothing of the imported module has to be regenerated for it. A module read this
way is not generated again — its classes and its examples belong to the build that produced them.

A compiled module records the version of what an importing module reaches. A module whose version is
not this compiler's is refused, naming the compiler that built it, rather than read and
misunderstood. A module compiled here SHALL NOT also be on the class path, and a module on the class
path that needs one absent from it is reported against the path.

A module on the class path needs another when what it declares names it — in a field's type, a
spread, an invariant, a helper an invariant calls, or an exposed composition's output. A `+let+` body
is not published, so an `+import+` only a `+let+` used is not one the importing project has to
satisfy: a dependency's implementation-only dependencies need not be on the class path.

[#qualified-reference]
=== Qualified reference

A type is also reachable through the module that declares it, written as the module name and the type name. Like the standard library's `+List.map+`, this needs no `+import+`: the `+import+` line only lets the name be written bare.

[,text]
----
data Line =
    { quantity: example.counting.Amount
    , price: example.pricing.Amount
    }
----

This is what a module does when two it depends on declare the same type name — `+Amount+` in each of two bounded contexts, which is normal and not the integrator's to rename. A qualified reference MAY be written wherever a type is named: a type position (a field, a behavior's input or output, a helper's parameter), a `+match+` arm's case name, a layer a constructor pattern opens (<<binding-patterns>>, <<match>>), and a `+constructs+` entry. A sum's case list is the exception: its cases are declared with it (<<sum-data>>), so there is no other module to name.

Which spelling names a type is not something a check has an opinion about. A bare `+Amount+` an `+import+` brings in and a qualified `+example.pricing.Amount+` are one type, so a clause and a body that spell it differently agree, and a pattern opens the type it names however the field that holds it was written.

`+import ... as+` names a module locally, and the alias may then carry the reference. The alias holds only in the module that writes it, and it MUST be a name nothing else answers to there — not another alias, not a module of this compilation, not a standard-library qualifier.

[,text]
----
import example.counting as Counting
import example.pricing as Pricing ( taxRate )

data Line =
    { quantity: Counting.Amount
    , price: Pricing.Amount
    }
----

Both parts of an `+import+` are optional: `+import example.pricing as Pricing+` only renames, and `+import example.pricing+` only writes the dependency down. What a qualified reference reaches is still what the declaring module exposes — qualifying a name that module keeps to itself is a compile error, as is qualifying with a name that is no module of this compilation.

A behavior of another module is named the same way, as a `+>->+` stage and as a `+depends on+`. What the qualifier says is which module the behavior comes from, which is what an `+import+` says, so a qualified stage or requirement needs no import line either.

[,text]
----
behavior ship = inventory.allocate >-> makeInvoice
behavior notify : (order: PlacedOrder) -> Notified constructs Notified
    depends on messaging.sendMail
----

Unlike a type, a behavior's name is also a member name in what is generated: an injected behavior is a field of the implementing class, and its name is that field's name (<<jvm-behavior>>). So one module cannot reach two behaviors of the same name, whether written bare or qualified — qualifying them does not separate the fields. Naming both is a compile error.

Two same-named types meet in one module because both values exist there; two same-named behaviors meet because the module chose to call both, which is the module not having named what it is doing. A module that genuinely depends on two of them — the same operation offered by two providers, say — declares two behaviors of its own, under names that tell them apart. Each is an injection target (<<injected-behavior>>), and which upstream behavior goes into each is the Java side's to decide.

[,text]
----
behavior allocateFromPrimary : (line: Line) -> Allocated | OutOfStock
behavior allocateFromSecondary : (line: Line) -> Allocated | OutOfStock
----

A dependency is a dependency however it is written, so a cycle closed by a qualified reference is the same compile error (<<e1501>>) as one closed by an `+import+`.

`+exposing+` lists what a module declares and does not re-export a name it imported. A module downstream of an integration module names an upstream type through the module that declares it, so the integration module translates a type it consumes rather than republishing it.

[#reserved-words]
== Reserved words

[,text]
----
module   import    exposing
data     invariant
behavior constructs depends on
match    with      as
let      if        then     else
guard
true     false
----

Operators and symbols: `+=+` `+|+` `+>->+` `+|>+` `+?+` `+->+` `+.+` `+...+` `+[+` `+]+`

Comparison, logic, arithmetic: `+==+` `+/=+` `+<+` `+<=+` `+>+` `+>=+` `+&&+` `+||+` `{plus}` `+-+` `+*+` `+/+` (`+/+` is division; `+/=+` is inequality; negation is not a prefix operator but `+not+` in `+souther.bool+`; <<stdlib-bool>>).

Lists: `+[+` `+]+` (literal and guard comprehension), `{plus}{plus}` (concatenation, of two lists or two strings; <<stdlib-list>>).

`+>->+` is associative (<<type-routing>>). `+|>+` is the value pipe, threading a value through functions — `+e |> f(a)+` is `+f(a, e)+` (<<pipe>>).

`+->+` is the arrow. It joins types — in a behavior declaration (<<behavior>>) and in a function type, wherever a type is written (<<delimiters>>) — and it introduces an anonymous body — in a `+match+` case (<<match>>) and a lambda (<<blocks>>). There is one kind of arrow. `+=+` binds a name to a right-hand side (whether the right-hand side is a type or a term is decided by the rules of <<behavior>>).

`+depends on+` is two words, and the `+on+` is not a reserved word. It is read as the second word of the keyword only where it follows `+depends+`, as the `+for+` of `+examples for+` is read after `+examples+` (<<example-placement>>), so a field, a parameter or a behavior MAY still be named `+on+`.

`+decoder+` / `+encoder+` / `+discriminate+` are not reserved words: the mapping to external representation is not syntax but is derived from a data's shape (<<decoder>>, <<encoder>>). `+error+` / `+success+` / `+failure+` are not reserved words either: a *business* failure is neither a special type nor syntax but ordinary domain data, and whether it departs from the mainline is decided by composition (<<unmarked-sum>>, <<behavior>>, <<composition>>).

There is no type name that carries an invariant violation. A violation inside the domain aborts, so no value needs to be carried (<<algebraic-types>>, <<violation-destination>>).

[#delimiters]
=== Delimiters and disambiguation

The full formal grammar (BNF) is deferred (<<future-work>>). The delimiters and precedence needed for reading and writing are fixed here.

* Both `+data+` declaration fields and record-literal `+TypeName { ... }+` fields are `+,+`-separated (<<product-data>>, <<record-literal>>). A declaration gives a type, so `+name: type+`; a literal binds a value, so `+name = value+` (`+:+` = has this type, `+=+` = is defined as this). A `+...+` spread is an element that composes types but appears in the same comma sequence as fields (<<field-spread>>). An `+invariant+` is a clause placed after the type body (`+{ ... }+` or `+= Y+`) and is not part of the field list (<<invariant>>). A clause's name follows the same rule as everything else named with `+=+` — it is defined as that rule, so `+invariant nonEmpty = List.length(value) >= 1+` (<<invariant-clause-name>>).
* Argument lists and the enumerations in `+constructs+` / `+depends on+` are `+,+`-separated (<<behavior-io>>, <<constructs>>, <<depends-on>>).
* Every `+,+`-separated list — declaration and record-literal fields, parameter and argument lists, tuple elements, list literals, and the `+constructs+` / `+depends on+` name lists — MAY carry a single trailing `+,+` before its closing delimiter. It is optional and has no meaning. The sample code in this spec keeps a leading-comma layout instead and writes no trailing comma.
* `+|+` is the case separator of a sum and binds more loosely than `+->+`. `+(x: T) -> A | B+` reads as `+(x: T) -> (A | B)+` (the whole output is a sum). An anonymous `+|+` MUST NOT be written on input (<<union-intersection>>).
* `+>->+` is the stage separator of a pipeline: not a binary operator but a flat n-ary sequence. It is associative (<<type-routing>>). Only a behavior name MAY appear in a stage position; parentheses such as `+(f >-> g)+` MUST NOT be written.
* `+|>+` is the value pipe, binding most loosely and left-associatively. `+a |> f |> g+` reads as `+g(f(a))+`. The left side enters the last argument of the right-hand call and is expanded to a call at parse time (<<pipe>>). This is distinct from the `+>->+` that composes behaviors; it threads the value of an expression.
* `+?+` is a type postfix (`+EmployeeId?+`) and desugars to `+Option<EmployeeId>+` (<<optional>>).
* `+.+` is field reference; `+...+` is spread (<<record-literal>>).
* The type position admits: a named type, a stdlib generic type (such as `+List<T>+`), an anonymous output sum (`+A | B+`), a postfix `+?+`, and a function type `+(A) -> B+`. A function type's parameters and result are themselves whole types, so `+->+` is right-associative — `+(A) -> (B) -> C+` returns a function and `+((A) -> B) -> C+` takes one — and `+(A) -> B | C+` still reads as `+(A) -> (B | C)+` by the `+|+` rule above. `+(A, B) -> C+` takes two parameters and `+((A, B)) -> C+` takes one tuple, as a lambda's parameter list does. A parenthesised single type is grouping.
* Writing a type in a position is not being admitted by it. What a position requires of a type is asked of the type: a data field, a newtype base and a behavior's input and output require an *external representation*, so none of them takes a type that carries a function at any depth (`+List<(Int) -> Bool>+` included); `+==+` / `+/=+`, a `+Set+`'s element and a `+Map+`'s key require *equality*; `+sort+` and a `+sortBy+` key require an *ordering* (<<equality>>).
* A newtype's base (`+data X = Y+`) is a type position narrowed to what `+X+` can take as its own external representation: no tuple, no function type, and no `+?+` (<<newtype>>). A sum's cases are names of declared data, so a case is never generic: `+data X = List<A> | B+` is not a sum (<<sum-data>>).

[#external-representation]
== External representation

The external representation handled by Decoders and Encoders is not Souther's own types but the neutral value model of the boundary library Raoh (a tree of scalar / List / Map). Souther owns the domain's types, invariants, and behaviors; the external representation and its parsing and generation are delegated to the peripheral library Raoh (<<separate-representation>>, <<decoder>>).

From a data's shape, Souther derives the decode side per input source (bare values / Map = raoh-core, JSON `+JsonNode+` = raoh-json, jOOQ `+Record+` = raoh-jooq) and the encode side to a neutral Map (raoh-core). The decode skeleton (fields, keys, discriminator) is common across sources; only the terminal field access varies per source. JSON output serializes the Map at the boundary (`+objectMapper.valueToTree+`, etc.; <<codec-generation>>).

An external representation may contain null, but internal data forbids null. null exists only at the boundary (Raoh's input) and MUST NOT pass through a Decoder into the domain.

[#builtin-types]
== Built-in types

[#primitives]
=== Primitive types

[,text]
----
Bool
Int          // signed 64-bit integer
Decimal      // java.math.BigDecimal
String
Date         // date. ISO 8601. java.time.LocalDate
DateTime     // date-time. ISO 8601. java.time.LocalDateTime
----

`+Date+` / `+DateTime+` correspond to the spec DSL's `+Date+` / `+DateTime+`. Value construction goes through a Decoder (from an ISO 8601 string). The current time is not obtained in the language; it is declared as a behavior with no implementation (<<injected-behavior>>).

==== Numeric literals

An integer literal is written as `+500+` and is `+Int+`. A `+Decimal+` literal takes an `+m+` suffix — `+500m+`, `+1.5m+`, `+0.5m+`. A fractional literal without `+m+`, such as `+1.5+`, is an error. Souther has no binary floating-point type and defaults fractions to `+Decimal+` (exact decimal), so `+Int+` and `+Decimal+` MUST be made explicit at the literal.

[#equality]
==== Equality

`+==+` and `+/=+` are *value equality*, not reference identity. Souther data are immutable values, so whether two are the same is decided by whether their fields are the same.

[,text]
----
guard approverId == request.applicant.managerId      // two EmployeeId built separately are equal if their values are equal
----

* primitives compare values
* data compare *fields recursively*, including fields taken in by a `+...+` spread
* sums are equal when they are the same case and their contents are equal
* `+List<T>+` compares elements in order; `+Map<String,T>+` compares keys and values
* `+T?+` is equal when both are `+None+`, or both are `+Some+` with equal contents
* a tuple compares its elements left to right (<<tuple>>)

Only *values of the same type* may be compared. Comparing different types is a compile error. A sum may also be compared with one of its *cases* (`+Rank == Staff+`): a case value is a value of its sum (case→sum is transparent, <<sum-data>>), so this is a sum-vs-sum comparison — true when the sum value is that case. Pure case membership is written this way for a case with no fields (a unit data, the usual state / role enum); a field-bearing case compared with `+==+` compares its fields too.

Ordering (`+<+` `+<=+` `+>+` `+>=+`) is defined for `+Int+` (numeric), `+String+` (lexicographic), `+Decimal+` (by value, ignoring scale), and `+Date+` / `+DateTime+` (chronological). A product data has no ordering, and neither does a sum with a field-bearing case. A single-value newtype (`+data X = Y+`; <<newtype>>) over one of the ordered types *is* ordered — by the value it wraps. So is an *enumeration* — a sum every one of whose cases is a unit data (<<sum-discrimination>>) — ordered by the order its cases are declared in, which is the order a state moves through (`+Prospecting < Won+`).

The order belongs to the sum, not to the case value: the same unit data may be a case of two sums, which place it differently. A case value therefore takes its order from the sum it is compared with or held in (`+stage < Won+`, a `+List<Stage>+`), and a bare case value that two enumerations both list has no order of its own.

[#newtype-comparison]
===== Comparing a newtype

A single-value newtype is compared by the value it wraps, for both equality and ordering, so `+.value+` is not written — `+value+` is the newtype's implicit inner name, not something a caller spells out. The nominal boundary is kept:

* Two of the *same* newtype compare their wrapped values: `+Amount <= Amount+`, `+Amount == Amount+`.
* A *bare literal* of the wrapped type takes that newtype from the other operand: `+Amount <= 100+`, `+Amount == 0+` (the `+100+` is an `+Amount+`). This mirrors how `+[]+` takes its element type from context (<<algebraic-types>>).
* Two *different* newtypes over the same base do not compare: `+Amount <= Quantity+` is a compile error, even though both wrap `+Int+`.
* A non-literal value of the wrapped type is not taken implicitly: `+Amount <= n+` (where `+n+` is an `+Int+`) is a compile error — write `+Amount <= Amount(n)+`.

The wrapped type must itself be ordered for `+<+` / `+<=+` / `+>+` / `+>=+`; equality works over any wrapped type. Arithmetic on a newtype is `+{plus}+` / `+-+` only (<<newtype-arithmetic>>).

`+Decimal+` ignores scale. `+1.0+` and `+1.00+` are equal.

[,text]
----
data Amount = Decimal
// read as 1.00 from a DB column, 1.0 from JSON. Treated as the same amount.
----

Scale is not lost from the value. An Encoder emits the scale it read, so a round trip (<<round-trip>>) is preserved. Scale is dropped *only from identity comparison*. If the number of rounding digits is a domain concern, write it as an invariant or a separate field, not as `+Decimal+` scale.

The `+hashCode+` of a data containing `+Decimal+` is computed after dropping scale (`+stripTrailingZeros+`). If equality ignores scale, the hash MUST ignore it too, or using the value as a `+Map+` key breaks. Java sees the same value equality: a generated data class implements `+equals+` / `+hashCode+` from all fields and can be used as a `+Map+` key directly (<<jvm-product>>). This is distinct from Java's `+==+` (reference) and `+BigDecimal.equals+` (scale-sensitive).

[#newtype-arithmetic]
===== Arithmetic on a newtype

A single-value newtype over `+Int+` or `+Decimal+` supports `+{plus}+` and `+-+`, and the result stays in the newtype: `+Money {plus} Money+` and `+Money - Money+` are `+Money+`. The operator opens each operand to its wrapped value, computes on the base, and re-wraps the result — so the result's invariant is re-checked at construction, exactly as any other construction is (<<invariant-mvp>>). A subtraction that leaves the invariant (a non-negative `+Money+` going below zero) *aborts* inside the domain (<<violation-destination>>). To make that a business result, guard it with `+guard ... else+` (<<guard>>); the compiler then confirms the guard discharges the construction (<<invariant-discharge>>).

Operand pairing is the same as comparison (<<newtype-comparison>>): the *same* newtype, or a newtype with a bare literal of its base (`+Money {plus} 100+`, the `+100+` taken as `+Money+`). Two *different* newtypes do not combine — `+Money - Quantity+` is a compile error even though both wrap `+Int+` — and a non-literal value of the wrapped type is not taken implicitly.

Arithmetic builds a value, so it is subject to <<closed-construction>>: a newtype of another module is built through the entry that module opens by exposing it, and a value of a type its module does *not* expose does not reach here at all: a module may not expose a data whose field would carry one out (<<exposed-surface>>). So the arithmetic and the entry it needs are always in the same place.

`+*+` and `+/+` *scale* a newtype by a plain number of its base and stay in the newtype (`+Money * 2+`, `+2 * Money+`, `+Money / 2+`) — the dimension is unchanged. The scalar is a bare `+Int+` / `+Decimal+` (literal or variable) of the newtype's base, not itself coerced to the newtype. A product or quotient of *two* newtypes *does* change dimension (`+UnitPrice * Quantity+` is a `+Money+`, not a `+UnitPrice+`), which the language does not model, so `+newtype * newtype+` (and `+Money * Money+`) is a compile error; compute those on `+.value+` and wrap the result explicitly. Only a newtype whose value is *directly* `+Int+` or `+Decimal+` has arithmetic — a newtype over another newtype does not.

Re-wrapping is a computation, not a fresh construction from raw data, so it needs no `+constructs+` (<<constructs>>) — as `+Int+` arithmetic does not "construct" an `+Int+`. A `+Money(...)+` literal construction (<<newtype>>) still does.

[#collections]
=== Collection types

[,text]
----
List<T>
Map<K, V>
Set<T>
----

Collections are immutable. A `+List+` is ordered and may repeat; a `+Set+` is unordered with no duplicate elements, compared by value equality (<<primitives>>); a `+Map+` is keyed by `+K+`, so a key carries its domain type (`+Map<ProductId, Stock>+`). Inside a behavior body `+K+` is any value type — `+List.groupBy+` keys by whatever the projection returns. A map that *crosses the boundary* — a data field, a behavior's input or output, at any depth — is a JSON object, whose keys are strings, so there `+K+` MUST be `+String+`, a String-backed newtype (`+data ProductId = String+`), `+Date+`, `+DateTime+`, or an enumeration — a sum every one of whose cases is a unit data (<<sum-discrimination>>). A newtype key is decoded into the key newtype (its invariant enforced, a bad key failing at that key's path) and encoded back bare; a temporal key is parsed from and written as its ISO 8601 form, the same representation a `+Date+` field has (`+{"2026-01-01": 300}+`); an enumeration key is the case's name, the same representation it has in a field (`+{"Won": 300}+`). A `+Set+`'s external representation is a JSON array, deduplicated on decode. An element may itself be a collection — `+Map<String, List<ProductId>>+` is what bucketing rows by a key produces (`+List.groupBy+`, <<stdlib-list>>) — and it crosses the boundary as the nested JSON its shape implies, decoded and encoded the same way at every depth.

A collection MAY be what a newtype wraps (`+data TagSet = Set<Tag>+`, <<newtype>>), which names the collection itself and gives an invariant something to hold about it — that its elements are unique, that it is not empty. The newtype crosses the boundary as the collection's own representation, a JSON array or object, not as `+{"value": [...]}+`.

Collections are *covariant* in their element. A case `+A+` may be used as its sum `+S+` (<<sum-data>>), so `+List<A>+` may be passed where `+List<S>+` is expected, `+Set<A>+` where `+Set<S>+` is expected, `+Map<String, A>+` where `+Map<String, S>+` is expected, and `+A?+` where `+S?+` is expected. This is sound because collections are immutable and there is no room to write a sibling case later. Covariance of mutable arrays (Java) is unsound because writes are a hole; that is the difference. Covariance applies only in the case→sum direction; sibling cases (`+A+` and `+B+`) are unrelated.

[#algebraic-types]
=== Built-in algebraic and auxiliary types

[,text]
----
Option<T>    = Some(T) | None
Never                      // a type with no value: an impossible case (empty sum)
Unit                       // a type with exactly one value
----

Souther has no `+Result+` / `+Either+` type. A behavior's output is a bare domain sum with no two-slot type separating success and failure (<<behavior>>, <<composition>>).

`+Never+` and `+Unit+` are not type names writable at the surface. `+Never+` denotes an impossible case: a single-case output (`+-> A+`) can be read as having an empty failure row, and it is the type of `+unreachable+` (<<unreachable>>) — the one expression that answers no value, and so fits every position. `+Unit+` is a reading aid only; it corresponds to the spec DSL's `+Unit+`, but it is never provided as a way to write a field, and is always expressed as a "data with no fields" (<<sum-data>>).

The only polymorphic types are the stdlib ones (`+Option+`, `+List+`, `+Map+`, `+Set+`). There are no user-defined generics. Neither `+data+` nor `+behavior+` takes a type parameter.

[#invariant-abort]
==== An invariant violation aborts

When the construction of a data with an invariant violates it inside the domain (<<invariant-mvp>>), the computation *aborts*. It returns no value and no case.

[,text]
----
behavior discount : (d: Quote) -> Discounted
    constructs Discounted
----

Writing a computation that breaks the invariant of `+Discounted+` does not change the output type; breaking it aborts. An abort is not a Souther expression and has no catching syntax, so it cannot control business flow (<<out-of-scope>>). At the boundary (<<java-example>>), Java catches it and maps it to 500, distinct from a business failure (400).

If the author wants to return the violation, that is a business judgment and MUST be written explicitly with `+guard ... else+` (<<guard>>). An invariant is a declaration that "a value passing here is always so", not a branch designed to be broken.

That judgment MAY be written by *attempting* the construction (<<attempted-construction>>), which states the rule once instead of restating it in the guard. What the attempt answers is a branch, not a value: no failure value reaches the domain, and the name a business failure gets is still the one the author writes in `+else+`.

A decode-side violation does not abort; Raoh's `+Result+` failure carries it (<<decoder-error>>). The same invariant is handled differently inside and outside the boundary.

==== How Option appears

`+Option<T>+` is the name of the type a `+?+` field has, and it MAY be written wherever a model *reads* an optional: a data field (where `+T?+` means the same thing), a behavior's input, a helper's parameter or declared return, a function type's result, and a local binding's annotation. A recursive helper and a function-typed parameter MUST declare their types (<<fn-declaration>>), so for those the name is the only way to say it at all.

The mark `+?+` outside a field is written only in the shipped core, as a type variable is (<<stdlib>>): `+?+` marks where an optional is *made*, and the name says what the type is.

An optional is *made* in one place: a `+?+` field being given its value (<<optional>>). Writing the type does not make one — `+let p: Option<Int> = None+` is <<e1303>> — and neither does declaring it as a helper's return: a helper answers the optional it read. Where a helper's absence is its own to name, that is a case of the model's own sum.

[,text]
----
partial let firstOver (n: Int, xs: List<Int>) : Option<Int> = {
    let head = List.get(0, xs)
    match head with
        | Some v -> if v > n then head else firstOver(n, List.drop(1, xs))
        | None -> head                  // the absence it read, passed on
}
----

It MUST NOT be written in a behavior's output, whichever way it is written. To state "might not be found" as a business result, that is a domain sum (<<unmarked-sum>>); an optional output is reported as itself rather than as a composition that does not fit (<<e1701>>).

[,text]
----
behavior findMember : (id: MemberId) -> Member | NoSuchMember     // write this
----

`+Some(T)+` is an exception to the rules of <<sum-data>> (a case is a reference to a named data and cannot carry a payload). Because `+Option+` is built in, users cannot imitate this form. Its contents are taken out with `+match+`; the `+v+` in `+| Some v+` is positionally bound to the wrapped value, not to `+Some+` (<<match>>).

[#optional]
=== Optional type

Optionality is expressed with `+?+`.

[,text]
----
data TravelCompleted =
    { preApprover: EmployeeId?
    }
----

This desugars to:

[,text]
----
preApprover: Option<EmployeeId>
----

To put a value in a `+?+` field, write an `+EmployeeId+` value directly and it is wrapped in `+Some+`; write `+None+` for empty. This is the only place `+None+` may be written as a value: what puts it there is the field, not the type of the position — a model may name `+Option<T>+` where it reads one (<<algebraic-types>>), and an annotation saying so does not license making one. Users never write `+Some(...)+` to construct a value (as in <<algebraic-types>>, this form is built-in only); `+Some(...)+` appears only as a destructuring pattern in `+match+` (<<match>>).

[,text]
----
TravelCompleted { preApprover = approverId }   // wrapped in Some(approverId)
TravelCompleted { preApprover = None }         // empty
----

Wrapping in `+Some+` and `+None+` are not data construction, so `+constructs+` is not required (<<constructs>>). Extraction is done with `+match+`'s `+| Some v+` / `+| None+` (<<match>>).

Outside a field, `+?+` is written only in the shipped core (<<algebraic-types>>); a user model marks nothing else with it, and names the type where it reads one.

The Decoder's external type is (Raoh's Decoder):

[,text]
----
Decoder<T> = external representation -> Result<T>    // failure carries Raoh's Issues
----

[#data]
== data

`+data+` defines typed data of the internal world. All fields are immutable.

A declaration takes the form `+data <Name> = <right-hand side>+`. If the right-hand side is `+{ ... }+` it is a product; `+A | B+` a sum; a single type name `+Y+` a newtype wrapping `+Y+` (<<newtype>>); if the right-hand side is omitted, a unit. This mirrors the spec DSL's `+data <Name> = ...+`.

[#product-data]
=== Product data (AND)

The spec DSL's `+AND+` maps to a product. A field name is the business role; the type may be specified separately.

[,text]
----
// spec DSL: data Employee = EmployeeId AND Rank AND ManagerId
data Employee =
    { id: EmployeeId
    , rank: Rank
    , managerId: EmployeeId // role name (managerId) differs from type (EmployeeId)
    }
----

Role and type may be written separately. In the spec DSL the same concept has a different name per layer: `+approverId+` (operation input) becomes `+preApproverId+` (stored state) becomes `+pre_approver_id+` (DB column). A field such as `+preApprover: EmployeeId+` writes the role in the field name and the concept in the type.

[#self-referential-data]
==== Self-referential data

Data MAY reference itself (directly or via another data). Structures such as an org chart or a category tree appear routinely in business.

[,text]
----
data OrgMember = { manager: OrgMember?, name: String }      // the manager is again an OrgMember (the chain ends at None)
data Department = { children: List<Department>, name: String }   // a tree (a leaf has an empty children list)
----

The derived codecs follow this self-reference. A nested `+{"name":"a","manager":{"name":"b"}}+` decodes to an `+OrgMember+` whose `+manager+` is again an `+OrgMember+`. Traversing a self-reference *by computation* (climbing the manager chain to the root, counting tree depth) is written with a recursive helper `+let+` (<<fn-declaration>>). `+fold+` folds only a fixed-structure `+List+`, so a self-reference of unbounded depth can be traversed only with helper recursion.

A self-reference requires a *base case*. A cycle that returns to itself through required fields only (not `+?+`, not `+List+`/`+Map+`) needs its own value to construct itself, which continues indefinitely — it is not constructible. Therefore *a required self-referential cycle with no base case is a compile error*.

* `+manager: OrgMember+` (no `+?+`) is a cycle with no base case. It is a compile error, not a runtime stack overflow.
* `+manager: OrgMember?+` (optional) and `+children: List<Department>+` (list) are base cases (the cycle is cut by `+None+` / the empty list), so they are allowed.
* A sum is an OR composition, so if a cycle passes through a sum it may bottom out in another case. The check stops at a sum and produces no false positive.

[#field-spread]
=== Field composition (spread)

In the spec DSL, a state sharing common items is written as `+data Submitted = TravelRequestCommon AND submittedAt+`, meaning "has all fields of `+TravelRequestCommon+`, plus `+submittedAt+`". Souther expresses this with the `+...+` spread.

[,text]
----
data TravelRequestCommon =
    { applicant: Employee
    , estimatedCost: Amount
    , destination: String
    , purpose: String
    , startsOn: Date
    , endsOn: Date
    }

// spec DSL: data Submitted = TravelRequestCommon AND SubmittedAt
data Submitted =
    { ...TravelRequestCommon // take in the common item's fields flatly
    , submittedAt: DateTime
    }
----

The `+...+` spread is defined as follows.

* The taken-in fields are laid out flatly. A `+Submitted+` value is referenced directly as `+x.applicant+` (not nested as `+x.common.applicant+`).
* The taken-in data's invariants are inherited too. The invariants of `+TravelRequestCommon+` are checked when `+Submitted+` is constructed. The spread carries not only fields but invariants.
* A field-name collision is a compile error.
* A spread is not inheritance. `+Submitted+` is not a subtype of `+TravelRequestCommon+`; the two are not assignment-compatible. They only share fields.
* A spread is an element of the same comma sequence as fields. It appears inside `+{+` separated by `+,+`, and multiple may be written. By convention it is placed first. It uses the same `+...+` as the value-level record-literal spread (<<record-literal>>).

To hold the common items as a single value rather than flattened, nest it as a normal field (`+common: TravelRequestCommon+`). The spec DSL's `+AND+` is a spread; explicit nesting is a normal field.

[#sum-data]
=== Sum data (OR)

The spec DSL's `+OR+` maps to a sum. *A case MAY reference an already-defined named data.* As in the business-trip model, where each state has its own fields, invariants, and transition behaviors and is bound together by `+OR+`, this structure is represented directly.

[,text]
----
// spec DSL: data TravelRequest = Drafting OR Submitted OR AwaitingPreApproval OR PreApproved
data TravelRequest =
    Drafting
  | Submitted
  | AwaitingPreApproval
  | PreApproved
----

Nested sums MAY be written directly.

[,text]
----
data CostBearer = OwnCost | ClientCost
data OwnCost = Reimbursement | Advance | CorporateCard
----

A case names a data; an inline record MUST NOT be written in a case position. A case that carries fields is declared separately, as the spec DSL declares it (for `+data Rank = Manager OR Staff+`, `+data Manager = { level: Level }+`). A case declared nowhere carries no fields, and the case list is its declaration (<<unit-data>>).

*A case value is a value of its sum.* As in functional languages, a value of a case type (e.g. `+Submitted+`) may be used transparently wherever its sum type (`+TravelRequest+`) is expected — field assignment, argument, or return value. Only the upward direction (case→sum) is allowed; the downward direction (sum→specific case) requires `+match+`. A nested sum (`+data OwnCost = Reimbursement | Advance+` being a case of `+CostBearer+`) is decided the same way, folding to the leaf case.

*What holds of every case is a property of the sum.* A sum has no fields of its own, so reading one is an error and the value must be opened with `+match+` — except for a field that *every* case spreads (<<field-spread>>): the sum exposes the fields of a data all of its cases include, and `+d.id+` reads it without opening the value. The same part is spread from the sum into a construction, so `+Filed { ...d, filedOn = on }+` writes at once what a `+match+` arm per case would write alike.

[,text]
----
data DocumentCommon = { id: String }
data Draft = { ...DocumentCommon }
data Sent  = { ...DocumentCommon, at: DateTime }
data Document = Draft | Sent
data Filed = { ...DocumentCommon, filedOn: Date }

let idOf (d: Document): String = d.id
let file (d: Document, on: Date): Filed = Filed { ...d, filedOn = on }
----

The shared part is what the author wrote: a spread is nominal (<<field-spread>>), so two cases that happen to declare a field of the same name have not shared it, and reading it stays an error. A spread reached through another spread counts, and a case that is itself a sum contributes its own leaves. When a case stops spreading the common data the field is no longer exposed, and the error appears at the read.

The read and the spread reach the same part and no more. What a single case carries of its own is not spread from the sum, so a construction wanting it is the missing-field error it would be from any other source (<<e1005>>), and a sum whose cases share no spread is not a spread source at all. A sum is still not assignment-compatible with the data its cases spread, and constructing one of its cases — deciding which case a value is — is still `+match+`.

[#unit-data]
=== Unit data

A data with no fields is declared with no body. It corresponds to the spec DSL's `+= Unit+`.

[,text]
----
// spec DSL: data Reimbursement = Unit
data Reimbursement
data Advance
data CorporateCard
data ClientCost
data Staff
----

Unit data appear frequently as sum cases (such as `+Staff+` in `+data Rank = Manager | Staff+`).

A unit written where a module *introduces* a type needs no declaration of its own: the name alone declares it. Three positions introduce a type — a sum's case list (<<sum-data>>), a behavior's output (<<behavior-io>>), and the output declared for a `+>->+` composition, written either on the composition or in `+exposing+` (<<declared-composition-output>>).

[,text]
----
data CostBearer = OwnCost | ClientCost
data OwnCost = Reimbursement | Advance | CorporateCard
// Reimbursement, Advance, CorporateCard and ClientCost are units; nothing else declares them

behavior quote : (c: Cart) -> PricedCart | EmptyCart     // EmptyCart is a unit
----

Everywhere else a type is *referred to*, and a name nothing declares is unknown there and reported: a parameter type, a field's type, `+constructs+`, `+depends on+`, a `+match+` arm, a codec variant, a `+let+`'s declared return type.

Whether a name is declared is answered within the module — its own declarations and the names its `+import+` lines list. A qualified name (`+inventory.InsufficientStock+`) names another module's declaration, so it is a reference wherever it is written. A sum's cases are declared with the sum, so they are module-local in any event (<<e1606>>).

The explicit declaration stays available, and is how a case that carries a comment of its own is written.

A unit data MUST NOT carry an `+invariant+`: it has no field for one to observe and no value it could reject (<<invariant-declaration>>). Writing one is a compile error rather than a clause with no effect.

A data body MUST NOT be empty: `+data T = { }+` names a type with one value, which is what a unit data is, so it is a second spelling of one. The two are not interchangeable where it counts — an empty product is built as `+T {}+` and a unit by its name alone — so the declaration form silently decides how the value is written. Writing it is a compile error naming the unit form. A body of spreads alone (`+data T = { ...CommonItems }+`) is not empty: what it includes gives it its fields (<<field-spread>>).

A unit data value is constructed by *writing the name directly* (as a zero-argument constructor becomes a value in functional languages). An empty record such as `+T {}+` is not used.

[,text]
----
// construct a unit in an implementation (let). Requires the behavior's constructs
[ClientBorne | bearer == ClientCost]     // ClientBorne is a unit, constructed by name alone
----

This is a guard comprehension (<<stdlib-list>>): it yields one `+ClientBorne+` if the condition holds, an empty list otherwise.

A bare identifier in an expression resolves as: a variable if a bound local exists; otherwise a built-in value (such as `+None+`; <<algebraic-types>>); otherwise the construction of a unit data of the same name; otherwise undefined. Souther does not distinguish identifiers syntactically by case (so that Japanese business vocabulary can be used as identifiers), so this resolution is done in the symbol table.

Because a local shadowing a built-in value is always an error, using a *built-in value name* (`+None+`; <<algebraic-types>>) as a binding name — `+let+`, a `+match+` binding, or a lambda argument — is a compile error. This prevents a shadowed built-in from silently becoming unreachable. A unit data name is domain vocabulary and may be used as a binding, in which case the local takes precedence and constructing a unit data of that name is not writable in the same scope. The rounding-mode cases (<<stdlib-decimal>>) are ordinary unit data and follow this rule; a shadowed case has no qualified escape syntax.

[#field-visibility]
=== Field visibility

A field is read as `+e.field+`, where `+e+` is a name, a call, or a construction, and `+.a.b+` chains from the left. So `+amountOf(i).value+` opens a newtype on the call that builds it, with no `+let+` written to hold the result. This never competes with the bare `+.field+` getter of <<blocks>>: a getter starts an expression, a read follows one.

*Reading* a field is possible wherever that data's type is visible. Within the same module, any data of that module may be read. A data of another module may have its fields read if it is exposed with `+exposing+` — being importable means it is exposed. An exposed data has all fields readable (there is no per-field exposure). A behavior may read the fields of its input data even when they come from another module.

A value of a type its module keeps to itself never arrives in another module, because the field that would have carried it there cannot exist: what a module reaches out with may not rest on what it keeps (<<exposed-surface>>). So "the data's type is visible" is the whole rule, and there is no second one about what a reader may do with a value it has no name for.

What is constrained is *not reading but construction*. Reading a field and constructing a new value of that data are separate authorities, so allowing cross-boundary reads leaves the guarantee that no unvalidated value can be built (<<asymmetric-interop>>) intact. There is no need to define a getter-only behavior just to pass a value out (<<behavior-composition-unit>>).

On the JVM, a public read accessor is generated for every field of a data, and a data is a record over its fields (<<jvm-product>>). Because module = package, the accessor is what reads across the boundary; on a data the module does not expose, the class is package-private, so the accessors are out of reach from outside all the same. Java can read an exposed one, but that is the same exposure as the encoder already emitting all fields as JSON; what is guarded is construction. The constructor stays non-public, and to build a value Java must go through the invariant-checking decoder (<<jvm-construction-privacy>>).

[#union-intersection]
=== Union types and intersection types

Souther has union types. They appear in three forms.

* named sum `+data X = A | B+` (sealed; subject to exhaustiveness checking)
* anonymous union in a behavior output `+-> Submitted | AwaitingPreApproval+` (<<unmarked-output>>)
* anonymous union with failure cases in a behavior output `+-> Out | E1 | E2+` (<<type-routing>>)

An anonymous union appears *only in a behavior's output*. An anonymous union MUST NOT be written in an input (parameter) type. To pass a sum, make a named data (<<unmarked-output>>); naming it makes it sealed, with exhaustiveness checking and a JVM type (<<jvm-sum>>). Where the spec DSL writes `+(A OR B)+` in an input, the sum is named as a `+data+` and then referenced. A JVM type is generated for an output anonymous union (<<jvm-anonymous-union>>).

[#union-member]
A member of an anonymous union MUST be nominal and MUST tell itself apart from the other members at run time, and it MUST have a form a `+match+` arm can write. The primitives (`+Int+` / `+Bool+` / `+Decimal+` / `+String+` / `+Date+` / `+DateTime+`) and named data types meet both, a data whether this module declares it or imports it. A collection meets neither: its type argument is erased, so `+List<Order>+` and `+List<Item>+` are one type at run time and no arm could choose between them, and no arm form names one. `+Option+` and a function type are outside for the same reason. What a member may be does not depend on where the union came from — a union written as a behavior's output and one a `+>->+` composition arrived at (<<type-routing>>) are the same union.

A named sum member contributes its cases and not itself, as it does in an external representation (<<sum-discrimination>>). The members a union is checked and generated from are therefore its *effective* members: every member written, with each named sum expanded to its leaves.

Each effective member goes by a name of its own. A `+match+` arm names a member by the name written for it, and so does the `+"type"+` discriminator (<<sum-discrimination>>), so one name cannot stand for two members. `+-> up.Yen | other.Yen+` is refused, and so is a `+Yen+` this module declares beside an imported one — including where one of them arrives as the leaf of a named sum member.

Structural intersection types (`+A & B+`, a type operator for "a value that is both A and B") are *not* provided. The spec DSL's `+AND+` means "has all of A's fields, plus more", not "is both A and B", and is fully expressed by the `+...+` spread of <<field-spread>> (take fields in flatly, inherit invariants, not a subtype).

[#newtype]
=== newtype (`+data X = Y+`)

When the right-hand side is a single type rather than a `+{ ... }+` product or a `+|+` sum, `+X+` is a newtype wrapping that type `+Y+`. `+Y+` is written the way a type is written anywhere else: a primitive (`+String+` / `+Int+` / `+Date+`, etc.), a named data, a sum, or a collection (`+List<T>+` / `+Set<T>+` / `+Map<K, V>+`, <<collections>>), including a collection of any of these. `+X+` is a distinct type from `+Y+` (nominally distinguished) with the same (bare) external representation as `+Y+`. The spec DSL's `+data X = Y+` (right-hand side a single name) is written directly.

[,text]
----
// spec DSL: data EmployeeId = String // not empty
data EmployeeId = String
    invariant String.length(value) > 0

// spec DSL: data InsufficientAuthority = Rank
data InsufficientAuthority = Rank

// spec DSL: data CostLine = CostType (CostType is a sum)
data CostLine = CostType

// a collection the domain has a name for, with an invariant on the collection itself
data TagSet = Set<Tag>
data Stock = Map<ProductId, Int>
----

`+Y+` MUST have an external representation, since `+X+` takes it as its own: a tuple (<<tuple>>) and a function type (<<fn>>) are refused as a newtype's base, where they are written. `+Y+` MUST NOT be optional — neither `+data X = Y?+` nor `+data X = Option<Y>+` — because whether a value is present is a property of the place it is used, written there as `+f: X?+`. A `+Map+` that a newtype wraps crosses the boundary as a JSON object, so its key follows the same rule a field's does (<<collections>>).

`+data X = Y+` is equivalent to having a single field `+value: Y+`. Construction applies the value to the type name, `+X(v)+` (`+Amount(500)+`, `+MemberId("m-01")+`), equal to `+X { value = v }+`. Reference is `+x.value+`; an invariant refers to the inside as `+value+`. The difference from `+data X = { value: Y }+` (with braces) is *the external representation only*: `+data X = Y+` reads and writes `+Y+`'s representation bare (`+EmployeeId+` is `+"e-01"+`), while `+data X = { value: Y }+` becomes an Object `+{"value": "e-01"}+`.

The constructor `+X(v)+` is written with parentheses like function application. Juxtaposition `+X v+` is not adopted, because Souther's application is uniformly `+f(x)+` and because, absent a capitalization rule on identifiers, `+Amount -5+` would be ambiguous between construction and subtraction. An invariant violation aborts like any other data construction (<<violation-destination>>). A construction whose argument is a compile-time constant statically verified to satisfy the invariant cannot abort, so it may appear anywhere in the type body; a construction where a constant breaks the invariant, such as `+Amount(-5)+`, is a compile error. A construction passing a runtime value may appear wherever an expression may — a behavior's result, a non-tail `+let+`, a `+match+` arm — and aborts on violation.

Whether it is a newtype is *decided by this syntax*, not inferred from the single-field shape. Adding a field to `+data Amount = { value: Int }+` does not silently change its representation (`+{...}+` is always an Object, even with a single field). For the bare representation, write `+data Amount = Int+`.

Because there is no `+|+`, there is no room to read `+data InsufficientAuthority = Rank+` as a one-case sum. A sum always has `+|+` (<<sum-data>>). When `+Y+` is a sum, `+X+`'s external representation is `+Y+`'s discriminated representation, and if it becomes a case of a nested sum it is folded to the leaf and dispatched (<<sum-discrimination>>).

[#invariant]
== invariant

[#invariant-declaration]
=== Declaration

A value constraint written as a comment in the spec DSL is made executable as an `+invariant+`.

[,text]
----
// spec DSL: data Amount = Integer // at least 0, in yen
data Amount = Int
    invariant value >= 0

data DateRange =
    { start: Date
    , end: Date
    }
    invariant start <= end
----

[#invariant-clause-name]
=== A clause MAY be named

A clause MAY be given a name, which is what tells it apart from the type's other clauses: `+invariant <name> = <expr>+`. An attempted construction departs by the named clause that did not hold (<<attempted-construction>>), and a decode failure reports the name (<<decoder-error>>).

[,text]
----
data QuoteLines = List<QuoteLine>
    invariant nonEmpty = List.length(value) >= 1
    invariant uniqueProducts = List.allUniqueBy(.product, value)
----

Two clauses that apply to one data MUST NOT share a name, a `+...+` spread's included clauses among them: a name that answered two rules would answer neither in particular. A clause MUST NOT be named `+_+`: that is what an attempt writes for the clauses carrying no name, so a clause named so could never be answered by name. A clause a spread takes in keeps the name its own declaration gave it.

A clause written without a name is enforced exactly as before one could be named: nothing tells it apart from the type's other unnamed clauses, so it aborts inside the domain and fails the decode outside it without saying which rule it was, and no arm can name it.

[#invariant-mvp]
=== Checking on construction

Invariants are checked at runtime. The compiler inserts an invariant check on every path that constructs a data. Invariants taken in by a `+...+` spread are checked on the same path.

The clauses are checked in the order they are declared — a `+...+` spread's first, then the declaration's own — and the first that does not hold is the one the failure names. Where several clauses fail, only the first is reported, so reordering the clauses of a published type changes what a caller is told and is a breaking change.

[#invariant-expressions]
=== Expressions allowed / forbidden in an invariant

Allowed: comparison, logical operations, arithmetic, field reference, built-in functions, blocks, and a `+let+` satisfying the three conditions below.

[,text]
----
let isNonNegative (v: Int) = v >= 0

data Amount = Int  invariant isNonNegative(value)
data Cart = { items: List<Line> } invariant List.all(x -> isNonNegative(x.quantity), items)
----

What may be called is a `+let+`, not a behavior (<<fn>>). An invariant is part of what a type is: it travels to an importing module as the source it was written as, together with the helper `+let+`s it names (<<published-modules>>). It names only what travels with it, so a behavior MUST NOT be called from an invariant whatever its requirement set — including one that depends on nothing and is callable from a `+let+` body (<<calling-a-behavior>>). To name a business rule, use a `+let+`.

A value or a helper another module publishes travels with it, so an invariant MAY name one, as a `+let+` body may (<<exposed-values>>). A limit or a format several modules' types are written against is therefore written once, in the module that owns it.

[,text]
----
module limits exposing ( maxLength )

let maxLength = 20
----

[,text]
----
module Member exposing ( MemberName )

import limits ( maxLength )

data MemberName = String
    invariant String.length(value) <= maxLength
----

The value is substituted and the helper expanded where they are named, closed by the module that declares them (<<exposed-values>>), so what the rule says does not change with where it is read. A project importing `+MemberName+` from a jar reads the invariant as it was written and resolves `+maxLength+` against `+limits+`, which is why that module is on its class path (<<published-modules>>).

A `+let+` may be called from an invariant when it satisfies all of the following, all statically decidable.

* the requirement set is empty (the corresponding behavior writes no `+depends on+`; <<depends-on>>)
* it constructs no data (the construction set of any helper `+let+` it calls is also empty; <<blocks>>)
* it is not `+partial+`

The first is decided by reading the declaration. `+let preApprove+` does not touch the outside world directly and so is pure in the sense of <<purity>>, but `+behavior preApprove+` writes `+depends on now+`, so its requirement set is non-empty and that `+let+` MUST NOT be called from an invariant.

A helper `+let+` always satisfies the first and second. To touch the outside world it can only receive a function as an argument (<<fn-declaration>>), and an invariant has no way to pass one. The third is about termination: an invariant is checked on every construction and must terminate. A `+partial+` helper disclaims totality and may loop, so it cannot appear in an invariant. A *total* helper is admissible even when it recurses — the compiler has proven it terminates (<<fn-declaration>>). This is what lets the list quantifiers `+List.all+` / `+List.any+` / `+List.member+` and the uniqueness checks `+List.distinct+` / `+List.allUniqueBy+` appear in an invariant: each derives from the total stdlib fold `+List.foldFrom+`, which is bounded by the finite list. Only a `+partial+` helper in an invariant is a compile error.

Forbidden: Decoder, Encoder, data construction, `+partial+` recursion, `+unreachable+` (<<unreachable>>), non-deterministic processing. Data construction is barred throughout the invariant expression, including inside a quantifier's closure — an invariant observes the value being built, it does not build another. `+unreachable+` is barred for the neighbouring reason: an invariant answers whether the value holds, and it answers on every path through itself, so a path that aborts instead decides a construction by a premise the clause never stated. A behavior call is barred by the rule above, whether written in the invariant or reached through a `+let+` it calls; and a `+let+` that goes through a behavior touching the outside world has that much of a requirement set and is rejected by condition 1 as well. Only pure (empty-requirement-set) computation enters an invariant.

[#violation-destination]
=== A violation's destination differs inside and outside the boundary

The same invariant is handled differently depending on where it breaks.

* *Decoder (boundary)*: the violation enters a failure (`+Issue+`) of Raoh's `+Result+` (<<decoder-error>>). A value that came from outside was invalid — an *expected result*. Which field broke it can be stated via `+path+` and `+code+`.
* *behavior (inside the domain)*: it *aborts* (<<algebraic-types>>). A computation among validated values broke a rule — a *model bug*.

[,text]
----
data Discounted = { amount: Int } invariant amount >= 0

behavior discount : (d: Quote) -> Discounted          // no violation case needed
    constructs Discounted
----

*A behavior's output needs no slot for the violation.* Constructing an invariant-bearing data does not change the output type.

If the business decides "return a different result when the amount is negative", that is not an invariant violation but a business judgment and MUST be written explicitly with `+guard ... else+` (<<guard>>). These are different: an invariant declares "a value passing here is always so", while `+guard+` is a business branch of "if not so, return this". The former breaking is a bug; the latter not holding is an expected result.

[#invariant-discharge]
=== Discharging an invariant at compile time

An invariant is checked at run time on every construction (<<invariant-mvp>>), and inside the domain a violation aborts (<<violation-destination>>). The compiler *also* checks, per behavior, whether each construction's invariant is *established* where the value is built — so a construction that must abort is caught at compile time, and one a guard makes safe is confirmed.

The check is intraprocedural. Within a behavior's `+let+` body it seeds what the input types guarantee — a newtype's own invariant, a product data's invariant over its fields — which is sound because an input of type `+T+` was built through `+T+`'s checked construction. It refines that along each `+guard+` / `+if+` guard (<<guard>>, <<if>>), and at every construction asks whether the guards prove its invariant.

* *Discharged* — the guards prove the invariant. No diagnostic; the construction cannot abort here (overflow aside).
* *Definitely violated* — the guards prove the invariant false on a reachable path. A compile error — the path-sensitive generalization of the constant check `+Money(-5)+` (<<newtype>>).
* *Possibly violated* — expressible but not proven. A warning: a possible abort. Guard it with `+guard+`, reify the relation into a type invariant (below), or attempt the construction (<<attempted-construction>>), which cannot abort.
* *Not expressible* — a clause outside the checked fragment. No diagnostic for it; the run-time check stands. The other clauses of the same invariant are answered on their own, so writing one the check cannot read beside one it can does not cost the second its report (<<invariant-discharge-capability>>).

Guards that cannot all hold describe a path the behavior does not take, and a construction standing on one is neither of the middle two: nothing is built there, so nothing is reported. That the guards contradict is itself derived over the same fragment — `+a <= b+` with `+b <= 0+` bounds `+a+` above without a word about `+a+` — so a path is dead whenever the relations say so, whatever order they were written in.

[,text]
----
data Money = Decimal invariant value >= 0m
data WithdrawRequest = { balance: Money, amount: Money }

behavior withdraw : (req: WithdrawRequest) -> Money | InsufficientBalance
let withdraw (req) = {
    guard req.amount <= req.balance
        else InsufficientBalance
    req.balance - req.amount          // discharged: the guard proves balance - amount >= 0
}
----

The checked fragment is bounded: the decision procedure derives over intervals and differences (`+value >= c+`, `+a <= b+`, and the like) with no external solver. A relation of neither shape — a sum of two lengths against a bound — is kept as it was written rather than derived from, so a guard *restating* an invariant discharges it even where the two together yield nothing. The set of *flagged* constructions is tied to that fragment, so every flagged construction has a guard the procedure can verify — an invariant it cannot express (a non-linear one, or one over a value it cannot name) is left to the run-time check rather than reported as a possible violation no guard could silence.

An *attempted* construction (<<attempted-construction>>) is never possibly violated: a failing invariant takes its `+else+` branch, so there is no abort to warn about. It is what silences the warning for an invariant outside the fragment, where no guard could. A violation the procedure *decides* is still an error there, because with the outcome settled at compile time there was no branch. In the success branch the built value seeds the check with its own invariant, as an input of that type does.

[#invariant-discharge-terms]
==== What the procedure can name

A term it compares is the numeric content of a location — a parameter, a field chain, a newtype's wrapped value — or the size of a container or a string: `+List.length+`, `+String.length+`, `+Set.size+`, `+Map.size+` applied to such a location. A size is named by the location it is taken of, so a guard and an invariant clause mean the same term exactly when they take the size of the same one. The size of a container is never negative, and the procedure knows that much without being told.

[,text]
----
data Lines = List<Line> invariant List.length(value) >= 1

behavior build : (rows: List<Line>) -> Lines | NoRows
let build (rows) = {
    guard List.length(rows) >= 1
        else NoRows
    Lines(rows)                       // discharged: the guard sizes the same list
}
----

A size taken of a container built by an operation is read through that operation, by the rules in <<invariant-discharge-preservation>>. A size taken of anything else — of what a `+let+` returned, of a string joined from parts — is not a term, and a clause needing it is left to the run-time check.

[#invariant-discharge-representation]
==== What the check reads

The check reads a behavior's body and the invariants around it at the level the rules above are written at: the standard library's operations are operations, and the `+let+`s a body or an invariant names are expanded into it (<<blocks>>). The two go together. The language defines what `+List.map+` does to a length, and every module has that definition, so a call to it says something on its own. A `+let+` carries no such definition, so what it says is its body — the one another module published as readily as the one written here.

An invariant that arrives from another module arrives expanded (<<published-modules>>), so a clause of an imported type is read as the computation it became rather than as the operations it was written as. Such a clause is outside the statically dischargeable fragment even where the same clause written here would be inside it. A clause written here is inside it whatever it names: an imported value or helper is substituted before the check reads the clause (<<invariant-expressions>>), so the rule the check reads is the rule the author wrote.

An operation the rules name is named as the call that survives to here, which is not every spelling an author can write: `+List.fold+` is the walk `+List.foldFrom+` from the head (<<stdlib-list>>) and is rewritten to it before any of this, so it is the second name the rules are written against. A rule under a name nothing here holds could not be reached, which is why the compiler's own tests hold each rule to a program that fires it.

[#invariant-discharge-preservation]
==== What an operation keeps of what it was built from

An invariant is stated of a value, and a value is often built from another by a standard-library operation. Whether the clause carries across that operation is a property of the operation, and is stated here rather than left to the checker: an author predicts which constructions are judged safe by reading this table.

Four shapes cover the operations.

[cols="1,3"]
|===
| shape | what the result is

| *permutes* | the same elements in another order — `+List.reverse+`, `+List.sort+`, `+List.sortBy+`
| *subset* | some of the same elements — `+List.filter+`, `+List.distinct+`, `+List.take+`, `+List.drop+`, `+Set.filter+`, `+Map.filter+`
| *maps* | one new element for each — `+List.map+`, `+List.indexedMap+`, `+Map.map+`
| *collapses* | at most one new element for each — `+List.filterMap+`, `+Set.map+`
|===

What each keeps:

[cols="1,1,1,1"]
|===
| shape | size | a property of every element | a particular element

| *permutes* | the same | kept | kept
| *subset* | no greater | kept | not kept
| *maps* | the same | not kept | not kept
| *collapses* | no greater | not kept | not kept
|===

So `+List.length(List.map(f, xs))+` *is* `+List.length(xs)+` — how the elements are made has no bearing on how many there are — and a guard on the length of `+xs+` discharges a construction from the mapped list. `+List.length(List.filter(p, xs))+` is its own term, no greater than `+List.length(xs)+`: an upper bound on the input bounds the result, and a lower bound on the input says nothing.

[,text]
----
data Lines = List<Line> invariant List.length(value) >= 1

behavior build : (rows: List<Row>) -> Lines | NoRows
let build (rows) = {
    guard List.length(rows) >= 1
        else NoRows
    Lines(List.map(toLine, rows))     // discharged: a mapping keeps the length
}
----

"A property of every element" is a clause like `+List.all(p, value)+` or `+List.allUniqueBy(f, value)+`: nothing new is in a sublist, so what held of every element still holds. "A particular element" is `+List.member(x, value)+` or `+Set.contains(x, value)+`, which a selection may drop.

An operation not in the table keeps nothing that can be relied on, and a clause over what it built is left to the run-time check.

[#invariant-discharge-projection]
===== A projection the closure copied

A mapping keeps no property of its elements in general, but a clause stated over a *projection* is a clause about one field, and a closure that copies that field across keeps it. Two mapped elements differ at a copied field exactly when the two they came from did, so uniqueness by that field carries.

[,text]
----
data QuoteLines = List<QuoteLine> invariant List.allUniqueBy(.product, value)

let toLine (r: LineRequest): QuoteLine =
    QuoteLine { product = r.product, quantity = Quantity(r.quantity), ... }

behavior buildQuote : (lines: List<LineRequest>, ...) -> Quote | DuplicateProduct | NoLines
let buildQuote (lines, ...) = {
    guard List.length(lines) >= 1
        else NoLines
    guard List.allUniqueBy(.product, lines)
        else DuplicateProduct
    Quote { lines = QuoteLines(List.map(toLine, lines)), ... }   // both clauses discharged
}
----

The field the closure copied need not be the one the clause names: when the closure writes `+code = r.sku+`, uniqueness of the result by `+.code+` is uniqueness of the input by `+.sku+`, and that is the guard to write.

This is bounded to a field *copied*. A field the closure computes from others — `+code = String.concat([r.sku, r.name])+` — is not this: two rows that differ can land on one value, and nothing about the result follows.

[#invariant-discharge-facts]
==== A clause that states no relation is settled, not derived

Not every invariant is a comparison. `+List.allUniqueBy(.product, value)+`, `+List.member(value, codes)+` and `+String.matches("[A-Z]{2}-[0-9]{4}", value)+` state something about a value that no arithmetic relates to anything else. Such a clause is *settled* by a guard rather than derived: a `+guard+` states its condition where it does not depart and denies it where it does, and a construction under a guard stating the clause is discharged, one under a guard denying it a violation.

[,text]
----
data Lines = List<Line> invariant List.allUniqueBy(.product, value)

behavior build : (rows: List<Line>) -> Lines | DuplicateProduct
let build (rows) = {
    guard List.allUniqueBy(.product, rows)
        else DuplicateProduct
    Lines(rows)                       // discharged: the guard states the clause
}
----

Two clauses are one thing exactly when they are the same expression over the same terms. Nothing relates two different ones — uniqueness by `+.product+` says nothing about uniqueness by `+.sku+`, and one pattern says nothing about another. What a binding is *called* is not part of the expression, so `+r -> r.product+`, `+row -> row.product+` and `+.product+` state one thing; a name the closure reads from outside it is part of the expression, so bounding by one field is not bounding by another. Which of the six comparisons an author reached for is not part of it either: `+a /= b+` is `+a == b+` denied, `+a >= b+` is `+a < b+` denied, and which side of an equality a term is written on says nothing — so a `+guard+` on `+a == b+` discharges a clause reading `+b /= a+` where it departs.

This is what a clause outside the derived fragment falls back to, whatever its shape. A comparison over a value the procedure cannot name is settled the same way, which is why `+guard+`-ing it verbatim discharges the construction.

[#invariant-discharge-capability]
==== A clause says how it can be discharged

Some clauses are statically dischargeable and others are not, and the same `+invariant+` keyword is written for both. Left implicit, an author believes there is a static guarantee where there is none. So the compiler answers, per clause, how that clause can be discharged. It is a query rather than a diagnostic — a correct program would carry one on every declaration, which is noise — and the LSP surfaces it on the clause.

[cols="1,3"]
|===
| | what discharges it

| *derivable* | a relation the procedure reasons over. Any guard that *implies* it discharges the construction: `+guard amount >= 10+` discharges `+invariant value >= 0+`.
| *exact match* | a term the procedure can name but not reason about. Only a guard establishing *the same* property discharges it, and nothing weaker: `+invariant List.allUniqueBy(.product, value)+` takes `+guard List.allUniqueBy(.product, lines)+`.
| *runtime only* | not representable as a static obligation. No guard discharges it, and the run-time check on construction is the whole of its enforcement.
|===

The first two are the *statically dischargeable* ones, and they are separate because they admit different guards — which is what an author needs to know before writing one. The third carries a reason, because there is more than one way to be outside the fragment and which one it is decides what can be done about it.

The classification is the clause's own, read with the construction assumed to name what it is given. A construction that names nothing the procedure can name discharges nothing whatever its clauses say (<<invariant-discharge-terms>>); that is a fact about the construction and not about the clause.

The answer carries the clause's name where it has one (<<invariant-clause-name>>), so what the LSP shows on a clause says both how it can be discharged and what an attempt departs by. The unit is the conjunct, as it is for the rest of the check, so a named clause written as `+a && b+` is classified twice under that one name — what discharges each half is what an author acts on, and the name is what a caller reads.

[#invariant-reify]
==== Reifying a cross-behavior relation

The check does not cross behaviors: a relation established in one behavior is not assumed in another (<<sequential-composition>>). Inferring such a precondition would be an implicit cross-unit contract, which the language declines — `+depends on+` and an exposed composition's output are always declared, not inferred (<<depends-on>>). The consistent way to carry a relation is to *reify it as a type invariant*, which the seeding then assumes downstream for free.

[,text]
----
data WithdrawRequest = { balance: Money, amount: Money }
    invariant amount <= balance                 // the relation lives in the type

behavior withdraw : (req: WithdrawRequest) -> Money
let withdraw (req) = req.balance - req.amount   // discharged with no guard here
----

So a possible-violation warning over the fields of one input data is a prompt to declare their relation as that data's invariant. When a value's validity is guaranteed *outside* the language — a Java-side or injected contract stronger than any type — there is no type to reify onto, and that construction keeps its run-time check.

[#decoder]
== Decoder

[#decoder-role]
=== Role

A Decoder is the boundary that constructs internal data from external input. It implements the spec DSL's parse-don't-validate (validate raw data at the boundary and construct a domain type only on success). Souther derives a Raoh Decoder from a data's shape. The derived Decoder reads an external representation (<<external-representation>>) and, on success, constructs T; failure is represented by Raoh's `+Result+` (the failure side carrying `+Issues+`).

[,text]
----
MemberId.decoder() : Decoder<MemberId>     // external representation -> Result<MemberId> (failure = Raoh Issues)
----

A decode failure is not a Souther domain type. Malformed input is not a business result but a boundary concern (<<unmarked-sum>>), so it is not listed among domain sum cases but placed on the failure side of Raoh's `+Result+`. Decode is not a behavior but the edge of the boundary and is not a `+>->+` stage (<<sequential-composition>>). Composition in the domain world is done only with behaviors and `+>->+`.

A Decoder does not appear in Souther's syntax. A default Decoder is derived from a data's field names and types. A data definition writes only `+data+` / `+invariant+` / `+behavior+`. This keeps the mapping to external representation (key names, normalization, discriminators) out of domain definitions. When the default derivation is insufficient, a custom Decoder is written on the boundary side (Java / Raoh) (<<custom-codec>>).

[#decoder-derivation]
=== Derivation rules

The default Decoder is derived from a data's shape by the following conventions.

* A JSON key matches the field name. Each field of an Object is read from the key of the same name.
* A newtype (`+data X = Y+`; <<newtype>>) is read directly from `+Y+`'s representation, not an Object (a bare scalar if `+Y+` is primitive, the derived Decoder of `+Y+` if a named data or sum). `+{ ... }+` is read as an Object even with a single field.
* A nested named data is read recursively with that data's derived Decoder.
* `+List<T>+` is read element by element with `+T+`'s derived Decoder.
* `+T?+` (Option; <<optional>>) is `+None+` if the key is absent or the value is `+null+`, and `+Some+`-wrapped after reading `+T+` if a value is present.
* Invariants are checked on construction; a violation becomes a failure (`+Issue+`) of Raoh's `+Result+`. Because decode always succeeds or fails, the destination of a violation always exists (<<violation-destination>>).
* Errors of independent fields are accumulated (Applicative; <<case-propagation>>). Accumulation is handled by Raoh combinators.

[,text]
----
// a newtype reads from a bare integer (the data X = Y form)
data Amount = Int
    invariant value >= 0
// derived Decoder: Int(n) -> Amount { value: n } (with invariant check)

// a multi-field data reads from an Object, field name = key
data Employee =
    { id: EmployeeId
    , rank: Rank
    , managerId: EmployeeId
    }
// derived Decoder: reads { "id": ..., "rank": ..., "managerId": ... } with each field's derived Decoder
----

The invariant check on construction and spread (`+...+`) follow the same semantics as a record literal (<<field-spread>>, <<record-literal>>).

[#sum-discrimination]
=== Discrimination of sum data

The derived Decoder of a sum data reads the discriminator field `+"type"+` and dispatches to the case's derived Decoder. The tag is the case name.

[,text]
----
data TravelRequest =
    Drafting | Submitted | AwaitingPreApproval | PreApproved
// derived Decoder: reads "type" and dispatches "Drafting" -> Drafting, "Submitted" -> Submitted, ...
----

A sum every one of whose cases is a unit data (folded to the leaves) is an *enumeration*: it carries nothing but which case it is, so it travels as that case's name — a bare string — and not as an object holding a discriminator alone. This is the form a fieldless enumeration has everywhere else, and it is what lets such a sum key a `+Map+` at the boundary (<<collections>>): a JSON object's key cannot be an object. A name no case answers to fails the decode at that value's path. One field-bearing case is enough to make the sum an object with `+"type"+` again.

[,text]
----
data Stage = Prospecting | Won | Lost
// derived Decoder: reads "Prospecting" / "Won" / "Lost"
// derived Encoder: Won -> "Won", so a field is { "stage": "Won" } and a key is { "Won": 300 }
----

A nested sum is folded to the leaf case and dispatched.

[,text]
----
data OwnCost     = Reimbursement | Advance | CorporateCard
data CostBearer = OwnCost | ClientCost
// derived Decoder: the name is one of "Reimbursement" / "Advance" / "CorporateCard" / "ClientCost"
// (every case is a unit data, so this one is an enumeration).
// The tag "OwnCost" does not appear in the external representation.
----

Folding is done because only the leaf identifies the value. Tagging a direct case would break the round trip (<<round-trip>>). Once `+CostBearer+`'s encode writes `+"OwnCost"+`, which leaf it was is lost, and the subsequent decode of `+OwnCost+` would reject that name as not one of its own. Folding at the leaf lets the same external representation be read by any layer's decoder. This is the same as case→sum assignment folding to the leaf (<<sum-data>>). Exhaustiveness in `+match+` is checked per layer (<<match>>), which is a separate matter from external representation.

A case's contents are decided by the case's shape. A product case lays fields flatly in the same Object as `+"type"+` (`+{"type":"Submitted", "applicant":…, …}+`). A unit case writes only `+"type"+` (`+{"type":"Staff"}+`). A newtype case (`+data X = Y+`; <<newtype>>) cannot place `+"type"+` on a bare scalar, so it puts the contents under the `+"value"+` key.

[#discriminator-field]
Because a product case lays its fields there, a case MUST NOT declare a field named `+"type"+` — the field and the tag would want one key, and whichever was written second would be all that was left. This is a compile error where the case is declared, not a value quietly written over where it is encoded. It holds of a member of a behavior's output union for the same reason (<<union-encoder>>), and of a field a case takes in by spread as much as one it writes. A data that is neither a case nor a union member may have the field: nothing writes a discriminator beside it.

[,text]
----
data Rank = Manager | Staff
data Manager = Level   // newtype
data Staff             // unit
// derived: Manager -> {"type":"Manager","value":3}, Staff -> {"type":"Staff"}
----

This maps directly onto Raoh's `+discriminate("type", …)+`. The discriminator selects `+"Manager"+` and passes the same Map to the case's decoder, which reads `+"value"+` and assembles `+Manager+`. This is the same framework as a product case reading fields flatly, only the read location becomes `+"value"+`. A standalone newtype (not a sum case) stays bare (`+3+`); the `+"value"+` wrapping appears only inside a sum.

Folding to the leaf concerns nested *sums*; a newtype case stops there. A newtype is not a sum, so making `+data InsufficientAuthority = Rank+` (Rank is a sum) a case of `+PreApprovalReason+` yields `+{"type":"InsufficientAuthority","value":{"type":"Manager","value":3}}+`, where the inner Rank is discriminated independently under `+"value"+`.

When the discriminator key or tag is business-specific (reading `+"status"+` and dispatching to `+"draft"+` / `+"submitted"+`, or reading a persistence `+representation_version+` for versioning), that is a matter of the external representation and cannot be derived from a data's shape. It is done with a custom Decoder on the boundary side (<<custom-codec>>).

[#custom-codec]
=== Custom boundary codec

When the default derivation is insufficient (a different key name, normalization, default filling, a business-specific discriminator, persistence version branching), write a Decoder on the Java side that assembles the external representation and calls the data's (invariant-checking) construction. The `+JdbcFindMember+` calling `+Member.decoder()+` in <<java-example>> is this form. External-representation conversion stays confined to the boundary and is not brought into domain definitions.

A business-specific sum tag does not mean rebuilding the case decoders. Souther generates a public per-case decoder (`+Submitted.decoder()+`) and a sum decoder that is only a `+discriminate("type", …)+` over them (<<sum-discrimination>>). The boundary keeps the per-case decoders and rewrites just that one layer with its own key and tags — reading `+"status"+` and dispatching `+"draft"+` / `+"submitted"+` is `+discriminate("status", variant("draft", Drafting.decoder()), variant("submitted", Submitted.decoder()))+`. Field assembly and invariant checks are reused; only the tag table is written. The encoder side is less symmetric: the derived sum encoder bundles the tag with each case's encoding, so a custom sum encoder re-tags each case's Map itself.

[#decoder-error]
=== Decoder errors

A decode failure is carried by the failure side of Raoh's `+Result+`. An error is a Raoh `+Issue+` (with `+path+` / `+code+` / `+message+`), and failures of independent fields are accumulated (<<case-propagation>>). Souther does not own the *boundary's* failure vocabulary. No domain type such as `+DecodeFailed+` or `+DecodeError+` is introduced; the representation of boundary failure is delegated to the peripheral library Raoh.

This differs from a violation inside the domain (<<algebraic-types>>). A break at the boundary means a value from outside was invalid — an expected result, and which field broke it should be statable (`+path+` and `+code+`), which Raoh holds. A break inside the domain means a computation among validated values broke a rule — a model bug — so it aborts (<<violation-destination>>). The boundary's vocabulary is not brought into the domain, and the domain's vocabulary is not taken out to the boundary.

At the boundary (HTTP, etc.), the `+Result+` failure is received and mapped to an appropriate response (e.g. 400). The `+MemberController+` branching on the decode `+Result+` in <<java-example>> is this form.

==== Codes an invariant produces

A newtype's invariant reaches the boundary as the Raoh constraint that states the same rule, so the failure carries that constraint's `+code+` and metadata: `+String.length(value) >= 1+` fails as `+too_short+` with `+min+`, `+String.matches(p, value)+` as `+invalid_format+`, a numeric bound as `+out_of_range+` with `+min+` / `+max+`, `+List.length(value) >= 1+` as `+too_small+` with `+min+` / `+actual+`, and `+List.allUniqueBy(x -> x, value)+` as `+duplicate_element+` with the duplicates it found. The vocabulary is Raoh's, so a `+MessageResolver+` keyed on the standard codes resolves and localises these without Souther supplying message text. Which type rejected the value is told by `+path+`, as for any other decode failure.

Only a rule with an exact Raoh equivalent is mapped this way. Anything else — a quantifier over a list, a uniqueness under a projection, a check across two fields, an object's invariant — runs as the rule it is and fails with the code `+invariant_violation+`, carrying the rejecting type in the metadata — its declaring module as `+module+` and its name as `+type+` — and, where the clause was named (<<invariant-clause-name>>), that name as `+clause+`. The module is its own entry because a type is its module and its name (<<modules>>): two modules may each declare an `+Id+`, and a resolver keyed on the name alone would answer for either. So a boundary failure says which rule was broken and not only that the value was rejected. A clause's name never becomes the `+code+`: the code stays the shared one, so a resolver keyed on Raoh's vocabulary keeps working and the metadata is what it switches on.

The clauses are checked in the order they are declared, which is the order construction decides in (<<invariant-mvp>>) — so the boundary and an attempted construction name the same clause for the same value. A mapped clause declared after an unmapped one gives up its Raoh code to keep that order: Raoh answers a plain `+Decoder+` once a rule of its own has been chained on, and a typed constraint cannot follow. Construction re-checks every clause regardless (<<violation-destination>>): the constraints are how a failure is *reported*, not what makes a value valid.

[#codec-generation]
=== Generation method and Raoh

The derived Decoder, without going through an independent Decoder IR, is generated *directly as bytecode* by the ClassFile backend as a Raoh Decoder (`+net.unit8.raoh.decode.Decoder+` and combinators). The generated decoder reads from the neutral tree of the external representation (<<external-representation>>; Raoh's `+Object+` / `+Map+` input) and returns `+Result<T>+`.

[,text]
----
Source -> AST -> (fill decoder/encoder into the AST by derivation) -> type check -> ClassFile backend -> .class (emits Raoh Decoders)
----

Souther's runtime (souther-runtime) does not depend on Raoh. Only the generated bytecode and the apps using it depend on Raoh. Primitive parsing, error accumulation (Applicative), and discriminator dispatch (<<sum-discrimination>>) are handled by Raoh combinators; Souther only maps a data's shape (keys, types, discriminator, case tags) onto Raoh decoder construction.

Decoders are generated per input source. Bare values / Map use raoh-core combinators, JSON `+JsonNode+` uses raoh-json, and jOOQ `+Record+` uses raoh-jooq. The skeleton (keys, types, discriminator, case tags) is common across sources; only terminal field access is swapped per source. For each exposed data, decoders are generated for the sources its shape supports. Bare values / Map and JSON are always generated. JSON temporal fields (`+Date+` / `+DateTime+`) are read as ISO 8601 strings (`+string().date()+` / `+string().dateTime()+`). jOOQ `+Record+` decoders are generated only for a flat shape with no nesting, List, or Map (scalar and newtype columns only) — a row is flat, so a nested object does not fit in one column. Unit data ignore input, so they support all sources.

[#encoder]
== Encoder

[#encoder-role]
=== Role

An Encoder is a total function converting internal data to an external representation (<<external-representation>>). Souther derives a Raoh Encoder from a data's shape.

[,text]
----
TravelRequest.encoder() : Encoder<TravelRequest>     // TravelRequest -> external representation (Raoh's neutral tree)
----

Like a Decoder, an Encoder does not appear in Souther's syntax. A default Encoder is derived from a data's field names and types (<<decoder-role>>). Encode is also an edge of the boundary and is not a `+>->+` stage.

[#encoder-derivation]
=== Derivation rules

The default Encoder is derived by rules symmetric to the Decoder.

* A newtype (`+data X = Y+`; <<newtype>>) writes directly to `+Y+`'s representation (a bare scalar if `+Y+` is primitive). `+{ ... }+` writes to an Object even with a single field.
* A multi-field data writes to an Object. The key is the field name; the value is converted by each field's derived Encoder. Fields taken in by a `+...+` spread are laid flatly too.
* A nested named data is converted by that data's derived Encoder.
* `+List<T>+` is converted element by element with `+T+`'s derived Encoder.
* `+T?+` (Option; <<optional>>): if `+Some(v)+`, write `+v+` at the key; if `+None+`, omit the key. `+None+` is not written and is read back as `+missing key → None+`, so the round-trip law (<<round-trip>>) holds.
* A sum data tags the discriminator field `+"type"+` with the case name and converts with the case's derived Encoder. A product case lays fields flatly, a unit case writes only the tag, a newtype case puts contents in `+"value"+` (<<sum-discrimination>>). A nested sum writes the leaf case's tag.

[,text]
----
data Amount = Int  invariant value >= 0
// derived Encoder: Amount -> Int(self.value) (bare integer)

data Submitted =
    { ...TravelRequestCommon
    , submittedAt: DateTime
    }
// derived Encoder: Submitted -> { "applicant": ..., "estimatedCost": ..., ..., "submittedAt": ... }
----

To match key names or representation to an external spec, write a custom Encoder on the boundary side (<<custom-codec>>).

[#round-trip]
=== Round-trip law

The following is recommended (not required).

[,text]
----
decode(encode(value)) == value
----

`+encode(decode(raw)) == raw+` is not required, because a Decoder may normalize, fill defaults, or drop surplus items.

[#behavior]
== behavior

A behavior defines the *specification* of a behavior over internal data. It is a top-level input/output relation with no owner.

A declaration takes the form `+behavior name = right-hand side+`. There are two right-hand sides, and what is written and what is left undetermined are inverted between them.

If *an argument list and output* (<<behavior-io>>) are written, what is written is the type. The implementation is undetermined: writing a `+let+` makes it the implementation (<<fn>>); writing none injects it from Java (<<injected-behavior>>). A behavior of this form has no body. What the spec DSL notes as `+// depends:+` comes here.

If a `+>->+` composition (<<composition>>) is written, what is written is the assembly step of chaining stages in this order, and that is itself the implementation. So no `+let+` is needed and no injection occurs. The type is undetermined and computed by the rules of <<type-routing>>.

Both are the same form as the spec DSL's `+behavior+`. The DSL writes both with `+=+`.

[,text]
----
// spec DSL
behavior preApprove = AwaitingPreApproval AND ApproverId -> PreApproved OR NotAuthorized   // right side is a type
behavior placeOrder = validateOrder >-> priceOrder >-> allocateStock                      // right side is a composition
----

That a type or a term may come to the right of `+=+` is because the DSL writes it that way; it is not a distinction Souther introduced. The same two lines map to Souther as:

[,text]
----
behavior preApprove : (request: AwaitingPreApproval, approverId: EmployeeId) -> PreApproved | NotAuthorized
    constructs PreApproved, NotAuthorized          // a type. Implementation is a let or Java injection

behavior placeOrder = validateOrder >-> priceOrder >-> allocateStock
                                                 // a composition. It is itself the implementation

// spec DSL: // depends: clock
behavior now : () -> DateTime                // write the type, no let → injected from Java
----

Specification and implementation are separated not because `+data+` already does so, but *so that one line of the spec DSL remains as is* (<<non-functional>>). Just as `+invariant+` rides on `+data+`, `+constructs+` rides on `+behavior+`. Both are the part Souther makes executable of what the spec DSL left in comments (<<mapping-principle>>).

[#behavior-io]
=== Input and output

The spec DSL's input `+AND+` maps to an argument list. A parameter is always written `+name: type+`.

[,text]
----
// spec DSL: behavior decidePreApproval = EstimatedCost AND Applicant AND CostBearer -> PreApprovalReasons
behavior decidePreApproval : (
    estimatedCost: Amount,
    applicant:     Employee,
    costBearer:    CostBearer
) -> List<PreApprovalReason>
----

A parameter name is for the reader and does not affect type identity. The implementation (`+let+`) gives its own names and corresponds by position. A type MUST NOT be written without a name: if `+(String)+` were writable, whether it meant "the type String" or "the name String" would be unreadable.

Zero arguments is written `+()+` (as in `+now+`). "No argument" and "takes one `+Unit+`" are different; `+Unit+` is not exposed at the surface (<<algebraic-types>>).

[#unmarked-output]
=== Output is a bare sum

The spec DSL's output `+OR+` maps directly to a bare sum. No success/failure distinction and no marker such as `+error+` is attached. A behavior is a function from input to one of the possible business results.

[,text]
----
// spec DSL: behavior submitTravelRequest = Drafting -> Submitted OR AwaitingPreApproval
behavior submitTravelRequest : (request: Drafting) -> Submitted | AwaitingPreApproval
    constructs Submitted, AwaitingPreApproval

// spec DSL: behavior preApprove = AwaitingPreApproval AND ApproverId -> PreApproved OR NotAuthorized
// NotAuthorized is just data. Not an error, not a Result.
behavior preApprove : (
    request:    AwaitingPreApproval,
    approverId: EmployeeId
) -> PreApproved | NotAuthorized
    constructs PreApproved, NotAuthorized
----

The commonest shape a model asks for is "the amount, or the reason there is none", and the value it answers with is usually a primitive or a type another module owns. Both are members (<<union-member>>), so the behavior answers with the value itself and no type is declared to hold it.

[,text]
----
// spec DSL: behavior computeTaxableAmount = Remuneration AND UpliftPay AND SocialInsurance -> Yen OR DeductionsExceedGross
behavior computeTaxableAmount : (
    remuneration:    Remuneration,
    upliftPay:       Yen,
    socialInsurance: Yen
) -> Yen | DeductionsExceedGross          // Yen is imported; it is the answer, not a wrapper around it
    constructs Yen, DeductionsExceedGross

behavior half : (n: Int) -> Int | NoAnswer   // a primitive is a member the same way
    constructs NoAnswer
----

The value is read back with the arm that names it — `+| Yen as y+`, `+| Int as n+` (<<primitive-arm>>) — and binds bare.

Which case "departs as a failure" is not decided by this behavior alone. When composed with `+>->+`, the case the immediately following stage does not consume departs the mainline (<<composition>>). If a downstream stage takes `+NotAuthorized+` as input, that case is processed; if not, it departs and is carried to the output. The same value departs in one composition and stays on the mainline in another.

An input may be a sum (spec DSL `+(Submitted OR PreApproved) AND ...+`). Here *an anonymous sum MUST NOT be written directly in a parameter type*. First declare the sum as a named data and write that name in the parameter. The implementation opens the cases with `+match+`.

[,text]
----
// name (Submitted OR PreApproved)
data CompletableRequest = Submitted | PreApproved

// spec DSL: behavior completeTravel : (Submitted OR PreApproved) AND ActualCost AND TravelReport -> TravelCompleted OR InvalidActualCost OR NoTravelReport
behavior completeTravel : (
    request:      CompletableRequest,
    actualCost:   Amount,
    travelReport: String
) -> TravelCompleted | InvalidActualCost | NoTravelReport
    constructs TravelCompleted, InvalidActualCost, NoTravelReport
----

An anonymous union appears only in a behavior's *output* (<<union-intersection>>). An input type is always a single named type (including a named sum). Naming it lets the reader fix the input candidates by looking once at `+data CompletableRequest = Submitted | PreApproved+`, and on the JVM the input has a name so a Java implementation receives it as a single type (an anonymous union has no common supertype; <<asymmetric-interop>>, <<jvm-anonymous-union>>).

[#constructs]
=== Data construction authority (constructs)

A behavior that constructs data MAY write the constructed type in `+constructs+`. This is an internal construction authority; unlike a dependency (`+depends on+`), it is invisible to callers. So for a behavior with a `+let+` implementation it is *optional* — omit it and it is inferred from the body. If written, it MUST *exactly match* the body (too few = E1002, too many = E1006). An injected behavior has no body, and its declaration is the input to factory generation, so it MUST always write it (<<java-base-class>>).

[,text]
----
behavior applyChange : (input: ChangeEmailRequest) -> Member
    constructs Member
----

To construct multiple data, list them: `+constructs Member, AuditRecord+`.

An entry names a type the way a type is named anywhere else, so a type another module declares may be written through it (`+constructs up.Amount+`) as well as under the name an `+import+` brings in. Which spelling the clause uses and which the body uses are independent — both name one type, and that is what E1002 and E1006 compare. Naming one type twice, however spelled, is a duplicate entry.

The following count as data construction: a record literal (`+TypeName { ... }+`), a sum data constructor, a unit data construction, and constructing a collection containing new data as elements. Returning an existing value unchanged does not count as construction.

The built-in `+Some+` / `+None+` (<<algebraic-types>>) do not count as data construction. Option is not domain data but an auxiliary type and has no invariant, so <<invariant-on-construct>> has nothing to guard. So `+constructs+` is not required to put a value in a `+?+` field (<<optional>>) — and since Option cannot be written as a type, there is no way to declare `+constructs Some+` anyway (<<algebraic-types>>).

*If you write `+constructs+`, you may not omit anything the implementation constructs.* The departure value of `+guard ... else+` (<<guard>>) is the same: `+else NotAuthorized+` constructs one unit data, so if declaring, include it in `+constructs NotAuthorized+` (omitting it is E1002). Being a failure case is no exception — what <<closed-construction>> closes is construction, regardless of success or failure.

==== What constructs is for

`+constructs+` is not for guarding invariants — that is handled by `+__construct+` and the Decoder, both of which always check on construction (<<invariant-mvp>>). What `+constructs+` handles is *reading the model*: from the declaration, whether a behavior *creates* a new value or merely *passes through* an existing one. This is not visible from the output type.

[,text]
----
behavior preApprove : (request: AwaitingPreApproval, approverId: EmployeeId) -> PreApproved | NotAuthorized
    constructs PreApproved, NotAuthorized   // creates new states

behavior checkCeiling : (a: Amount) -> Amount | OverCeiling
    constructs OverCeiling                  // Amount returns the input as is; not created
----

Both have `+Amount+` / `+PreApproved+` in the output, but one creates and the other passes through. This distinction does not appear in the output type. Writing it leaves it in the declaration and makes a check against reading and mis-taking. Omit it and it is inferred — write it (opt-in) if you want the reading and the check.

Creating a type that does not appear in the output also shows here. The `+constructs HighValueTravel, InsufficientAuthority, ClientCost+` of `+decidePreApproval = (...) -> List<PreApprovalReason>+` is information nowhere in the output type.

A helper `+let+` (with no corresponding behavior) may also construct data, but a helper `+let+` is not a specification statement and does not declare its own `+constructs+`. Its *construction set is inferred transitively* (folding in any helper `+let+` it calls). If the calling behavior writes `+constructs+`, it MUST include that set (E1002 if it does not); if omitted, that set is folded into the inference. A block is the same, constructing under the enclosing behavior's authority (<<blocks>>).

A *value* is the other case. It too is substituted where it is named (<<fn-value-semantics>>), but what it builds is built by its definition: a behavior stating a rule against a named limit originates none of it, and the limit does not belong in that behavior's `+constructs+`. This is what lets a threshold be named at all — the figure gets one place to live and one comment saying where it comes from, and the rules reading it go on saying what they do. Writing the entry anyway is accepted, the same answer a construction another module's published body carried in gets (<<exposed-values>>).

A dependency (`+depends on+`) is different and MUST *always* be written (<<depends-on>>). `+depends on+` is an outward contract to the caller and injector; leaving it to inference would let the contract change silently. `+constructs+` is an internal authority invisible to callers, so they diverge here. Thus `+depends on+` is a declaration and `+constructs+` (for a behavior with a `+let+` implementation) is optional. A `+>->+` composition infers both output and requirements (<<composition-with-requirements>>).

[#record-literal]
=== Record literals and spread

Construction is done with a record literal that writes the constructed type name.

[,text]
----
PreApproved {
    applicant     = request.applicant,
    estimatedCost = request.estimatedCost,
    submittedAt   = request.submittedAt,
    preApprovedAt = now(),
    preApprover   = approverId
    // ... list the rest of the common items too
}
----

To fill same-named fields together, use a spread `+...src+`. It copies `+src+`'s same-named fields and states the rest explicitly. Surplus fields of `+src+` are ignored; a field missing from `+TypeName+` is a compile error.

[,text]
----
// copy the common items and submittedAt of request (AwaitingPreApproval), and add two
PreApproved { ...request, preApprovedAt = now(), preApprover = approverId }
----

To replace only some fields while keeping the same type, also write the type name and use a spread. If `+x+` has type `+Member+`, write `+Member { ...x, address = newAddress }+`. No dedicated update syntax is provided.

When a field value is a binding of the same name as the field, the value may be omitted. `+Member { address }+` is shorthand for `+Member { address = address }+`, filling from the same-named binding in scope.

A record literal and a spread both require construction authority (`+constructs+`). Because the type name appears at the construction point, the authority check and field check are done on the spot.

[#blocks]
=== Blocks

To apply processing to each element of a list, pass a block as an argument. A block is written `+<args> -> <expr>+`.

[,text]
----
// spec DSL: data UnvalidatedOrder  = ... AND List<UnvalidatedOrderLine>
//           data ValidatedOrder = ... AND List<ValidatedOrderLine>
// validate and repack each detail. A block is needed here.
behavior validateLines : (xs: List<UnvalidatedOrderLine>) -> List<ValidatedOrderLine>

let validateLines (xs) = List.map(x -> validateLine(x), xs)
----

A block is an anonymous `+let+`. It is the same as a `+let+` (<<fn>>), only unnamed. A named one may be passed by name.

[,text]
----
let isValid (r: PreApprovalReason) = ...

List.all(reasons, r -> isValid(r))   // wrap in an anonymous block
List.all(reasons, isValid)           // pass by name directly. Same thing
----

A name that names a function *is* that function where a value goes, whoever declared it: a `+let+` of this module, a `+let+` another module published, and a standard-library function alike. `+String.trim+` written where a value goes is a `+(String) -> String+`, and `+String.trim(s)+` is that function applied to `+s+`. So the two lines above are one rule rather than two, and a function reaches every position a block reaches — an argument, a binding, a branch of an `+if+`, an element of a list a `+fold+` walks.

[,text]
----
let step: (String) -> String = if flag then String.trim else String.uppercase
let steps: List<(String) -> String> = [String.trim, String.uppercase]
----

Application is written after what is applied, and what is applied is any expression: a name (`+f(x)+`), a parenthesised expression (`+(if flag then String.trim else String.uppercase)(s)+`), or the result of an application (`+adder(1)(x)+`). What is applied is evaluated once, and before the arguments. An argument list MUST begin on the line its callee ends on — a `+(+` that opens a line is a parenthesised expression, so a block whose result is a tuple written under a call reads as that block's result and not as an application of the line above.

A behavior's name handed over is the *behavior*, not the `+let+` that implements it: a Java implementation replaces the behavior, so passing one to `+List.map+` and calling it by name reach the same place (<<calling-a-behavior>>). A behavior with a requirement arrives bound through `+depends on+` and is a binding by the time it can be named, so nothing carries a requirement past that statement.

A block and a `+let+` may be passed as arguments, and a `+let+` may take one as an argument (<<requirement-propagation>>). *What is not allowed is a boundary that requires an external representation*: a data field, a newtype's base, and a behavior's input and output (<<fn-rules>>). A function has none, so placing one would create an exception to decoder / encoder derivation (<<decoder>>, <<encoder>>), and it is refused wherever it sits — directly, or inside a `+List+` or a `+Map+` written there. This is a representation constraint unrelated to side effects. The spec DSL itself holds a rule it wants to swap not as a function but as data (`+data fieldDefinition = ... AND validationRule?+`).

A block may also be bound to a name by a block's `+let+` and applied (`+let f = (x) -> ...+`, then `+f(a)+`); written at the top level the same line is a definition, and its parameters move to the left of `+=+` (<<fn-declaration>>). Like a named `+let+` (<<fn-declaration>>), as long as it does not escape — applied only, never leaving as a value — a block is expanded into its call/apply site and forms no closure. When it escapes — *returning* a function, or choosing at runtime (`+let f = if ... then (x) -> ... else ...+`) — a closure capturing free variables is generated. It is a synthesized class implementing the runtime `+Fn+`, holding the captured variables in fields. Where expandable it is expanded; only where necessary is it a closure. The *cannot place in a data field* constraint above is unchanged by closures: it is a representation constraint, separate from whether a closure exists.

A bare field access `+.field+` is a getter block: it desugars to `+(x) -> x.field+`, so a field is projected point-free — `+List.map(.value, xs)+` instead of `+List.map(x -> x.value, xs)+`, and with the pipe `+xs |> List.map(.value)+`. It is single-layer (`+.value+`, not `+.a.b+`; reach through a newtype over a newtype with the constructor pattern of <<binding-patterns>> or <<match>>) and works for any field, so a newtype's `+.value+` and a record's `+.a+` read the same way. It is a block like any other: it may sit in an argument, be bound with `+let+`, and — since it names its own parameter's type nowhere — be given one by the binding it is written on (`+let g: (Item) -> Int = .n+`). It is a lambda shorthand, not a first-class value, and never collides with the in-scope `+value+` an invariant refers to (<<invariant>>), which is a field name, not a getter.

A block and a helper `+let+` are the same in constructing data. A block constructs under the enclosing behavior's `+constructs+`, and a hoisted helper `+let+` constructs under the `+constructs+` of the behavior that calls it (the construction set is inferred transitively and reconciled; <<constructs>>). Either way the construction authority is on the behavior and does not disappear with naming. So hoisting a constructing `+[HighValueTravel { threshold = threshold } | …]+` (<<stdlib-list>>) into `+let makeHighValueTravel (threshold) = HighValueTravel { threshold = threshold }+` passes if the calling behavior declares `+constructs HighValueTravel+`.

[#binding-patterns]
=== Binding patterns

Where a name is bound — a block's `+let+`, a behavior implementation's parameter, a helper's parameter, a lambda's parameter — a *pattern* may be written instead, opening the value where it is named. The patterns admitted here are the ones every value of the type satisfies: a name, a tuple, a newtype opened by its constructor, a record's fields.

[,text]
----
let TagSet(ts) = set                    // open a newtype
let { name, quantity } = line           // read fields under their own names
let { quantity = n } = line             // ... or under another
let (k, v) = pair                       // open a tuple (<<tuple>>)

let count (TagSet(ts)) = Set.size(ts)   // a helper's parameter

behavior size : (set: TagSet) -> Int
let size (TagSet(ts)) = Set.size(ts)    // a behavior implementation's parameter

List.map((TagSet(ts)) -> Set.size(ts), sets)   // a lambda's parameter
----

A pattern that some values of the type do not satisfy — a sum's case, `+Some+` — MUST NOT be written here; it belongs to `+match+` (<<match>>), which has the arm that catches what fails. A binding has one arm and nothing to fall to. Whether a name is refutable is decided by what it declares, so `+let X(v) = e+` is refused when `+X+` is not a newtype, and the report names `+match+`.

Outside `+match+` the name a constructor pattern writes is also checked against the value's own type: `+let TagSet(ts) = LabelSet+` is refused. In a `+match+` the arm's name is one of the scrutinee's cases and exhaustiveness has already settled it; a binding names a type on its own authority.

A helper's parameter written as a constructor pattern needs no type beside it — `+let count (TagSet(ts))+` already says the parameter is a `+TagSet+`. A tuple or record pattern names no type, so a helper whose parameter type its body does not determine still annotates it (`+let twice ({ quantity }: Line)+`).

On a behavior's implementation the pattern is not a type either way: the parameter types come from the behavior (<<fn-declaration>>), and a pattern only opens the input the behavior has already typed. The name the pattern writes is checked against that input, so `+behavior size : (set: TagSet) -> Int+` implemented as `+let size (LabelSet(ts))+` is refused. A `+depends on+` parameter names an injected behavior, so it takes a name, not a pattern.

A lambda's `+(a, b) -> ...+` is its parameter list, not a tuple pattern; a single tuple parameter is `+((a, b)) -> ...+`.

[#depends-on]
=== Dependencies (depends on)

A behavior that touches the outside world writes what it depends on in `+depends on+`.

[,text]
----
behavior preApprove : (request: AwaitingPreApproval, approverId: EmployeeId) -> PreApproved | NotAuthorized
    depends on now
    constructs PreApproved, NotAuthorized
----

What is written is the name of a behavior whose *requirement set is not empty* (<<requirement-propagation>>) — one with no implementation (<<injected-behavior>>), or one whose own `+let+` declares `+depends on+` — declared in this module or imported from another (<<modules>>). Write it if the `+let+` uses that name. Even when used indirectly by passing it to a helper `+let+`, the one passing is you, so you write it.

A behavior with an empty requirement set is not written here. It depends on nothing, so there is nothing to inject, and it is called directly (<<calling-a-behavior>>). Writing one in `+depends on+` is rejected where the clause is written (<<e1607>>), as is a `+>->+` composition — whose requirements are inferred from its stages and are not written, so requiring one would make a caller declare a set that changes when an upstream stage changes — and as is a name that is no behavior in scope.

Only a simple behavior with a `+let+` may have `+depends on+`. A behavior with no implementation does not write it: it is the leaf of the dependency, and its name being listed is itself the statement of dependency. A `+>->+` composition does not write it either: it is decided by the union over stages, readable from the stages (<<composition-with-requirements>>).

==== Correspondence to the spec DSL

The DSL attaches `+// depends:+` / `+// side effect:+` to a *leaf*.

[,text]
----
// responsibility 2: save the business-trip application to the database
// depends: travelRequestDatabase
// side effect: save to the database
behavior saveTravelRequest = UnvalidatedTravelRequest AND PreApprovalNeeded -> SavedTravelRequest
----

In Souther this becomes a behavior with no implementation, so no `+depends on+` is needed. The same as the DSL attaching no note to a composition: it is readable from the stages.

The DSL holds only these two because it places side effects at the ends of a workflow. The form "use the outside world once in the middle of a pure computation" does not appear in a specification model. Souther allows it, so a position with no source in the DSL — a behavior with a `+let+` — arises. `+depends on+` lets the DSL's note be written on a non-leaf behavior too. The positions increase, but the content is the same "what it depends on" as the DSL; no lines are added.

==== depends on becomes a let argument

What is written in `+depends on+` appears as a `+let+` argument, after the business inputs, in declaration order.

[,text]
----
let preApprove (request, approverId, now) = {
    guard approverId == request.applicant.managerId
        else NotAuthorized

    PreApproved { ...request, preApprovedAt = now(), preApprover = approverId }
}
----

The behavior has 2 arguments and the `+let+` has 3 because *the behavior's type is the type after partial application*.

[,text]
----
let:      (request, approverId, now) -> PreApproved | NotAuthorized
bind:     fix now                             f_a(x) = f(x, a)
behavior: (request, approverId)      -> PreApproved | NotAuthorized
----

`+PreApprove.bind(new JdbcClock())+` (<<jvm-behavior>>) is this partial application. What remains after binding is the behavior's declared type, and Java calls `+apply(request, approverId)+` with 2 arguments. `+depends on+` does not appear in the caller's arguments.

This merely surfaces the "requirements are constructor arguments" of the end of <<blocks>>. In the `+let+`, `+now+` is just an argument, not an effect or a special type. So the `+let+` side needs no place to write `+depends on+`.

A helper `+let+` (with no corresponding behavior) fits the same form. To touch the outside world, it receives a function as an argument — a helper writes its own type (<<fn-declaration>>), so it writes it there.

[,text]
----
let record (x: Int, now: () -> DateTime) = ...       // helper. Receives it as an argument
----

The `+now+` appearing inside a `+let+` is an argument in either case. There is no path to call a behavior with no implementation directly as a top-level name. So a helper `+let+` having no place to write `+depends on+` is not a restriction. The passer writes it in its own `+depends on+` and passes it as an argument.

==== Checking

The set of behaviors with a non-empty requirement set that a `+let+` uses and the set written in `+depends on+` MUST match. Too few is E1602, too many is E1603 (<<e1602>>, <<e1603>>). An over-declaration erring on the safe side is not admitted either.

[#calling-a-behavior]
=== Calling a behavior

A behavior's `+let+` may call a behavior. Which ones it may call is decided by one question — the requirement set — and the answer does not depend on where the behavior was declared. A behavior this module declares and one it imported are called the same way.

A helper `+let+` may not. A helper is expanded into what calls it, and an invariant that names one carries it to an importing module as source (<<published-modules>>); it names only what travels with it, which is what keeps an invariant's rule a single question about the requirement set rather than a second one about where a name came from. A behavior a helper wanted is called from the behavior's own `+let+` and its result passed in.

* An *empty* requirement set: call it by name. Nothing is injected and nothing is written in `+depends on+`.
* A *non-empty* requirement set: write it in `+depends on+` and call it through that name (<<depends-on>>). It arrives already bound, as any requirement does.

[,text]
----
behavior preApprove : (request: AwaitingPreApproval) -> PreApproved | NotAuthorized
    depends on now

behavior rejectAndNotify : (request: AwaitingPreApproval) -> Notified | NotAuthorized
    depends on preApprove
let rejectAndNotify (request, preApprove) = match preApprove(request) with
    | PreApproved as p -> Notified { to = p.applicant }
    | NotAuthorized as r -> r
----

A call yields the behavior's declared output. Where that output is a sum, the caller opens it with `+match+`, and a case it does not handle is its own to declare in its output. Nothing departs on its own: departure is what `+>->+` does (<<type-routing>>), and a call is not a stage.

A behavior's `+constructs+` is its own and adds nothing to its caller's. A helper `+let+` is different — it is not a specification statement and declares no authority, so its construction set folds into the behavior that calls it (<<constructs>>).

Behaviors do not recurse. A behavior MUST NOT reach itself, through calls, through `+depends on+`, or through a mixture of the two (<<e1608>>). Recursion is a property of a named module helper (<<fn-rules>>).

[#tuple]
== Tuples

`+(a, b, ...)+` is a tuple bundling two or more values into one. It is an expression-level value, used only in the middle of a computation — a helper `+let+` returning multiple values and destructuring them — and MUST NOT be written in a data field or a behavior input/output. Like a function (<<blocks>>), it does not cross the boundary, so no codec is derived. Domain vocabulary stays as named data.

A tuple *type* `+(A, B, ...)+` may be written in a helper or standard-library signature — a parameter, a return type, or a type argument such as `+List<(String, 'a)>+` — since a signature is not a codec boundary. It is still rejected in the two boundary positions above: a data field and a behavior's input/output, where a codec would have to be derived. A one-element `+(T)+` is not a tuple type.

A tuple is compared by its elements (<<equality>>), so two built separately from the same values are one value. It is therefore a `+Set+`'s element and a `+Map+`'s key like any other, which is how a rule over a composite key is written: `+allUniqueBy(t -> (t.from, t.event), transitions)+` says one row per `+(from, event)+`. A tuple has no *ordering*, so it is not a `+sort+`'s element or a `+sortBy+`'s key (<<stdlib-list>>) — order by one key and then the other instead.

[,text]
----
let stats (xs: List<Int>) = (List.sum(xs), List.length(xs))   // return multiple values

let average (xs) = {
    let (total, count) = stats(xs)      // positional destructuring bind
    ...
}
----

`+let (x, y) = t+` destructures a tuple positionally and binds. Names correspond to elements left to right. A one-element `+(e)+` is just a parenthesized expression and is not a tuple. A tuple may be held as is in a `+let+`, passed to a helper, or be an element of `+List<(a, b)>+` (a first-class value). Extraction is by destructuring only; there are no index functions such as `+fst+` / `+snd+`.

A lambda argument `+(a, b) -> ...+` is multiple arguments (<<blocks>>), distinct from a tuple. A single tuple argument is written with its own parentheses, `+((a, b)) -> ...+` (<<binding-patterns>>).

[#fn]
== let — implementation

A `+let+` is the implementation of a behavior. A behavior is the specification (<<behavior>>), and a `+let+` is what satisfies it.

[#fn-declaration]
=== Declaration and binding

A `+let+` is written `+let <name> (<args>) = <body>+`. If a behavior of the same name exists, it implements it.

Parameters go on the left of `+=+`, and a `+let+` written without them defines a *value*. The parameter list, not the shape of the body, is what tells a function from a value. An empty `+()+` is refused, since it would be a second spelling of the value form.

[,text]
----
let ceiling = Amount(100000)                    // a value
let isOver (amount: Amount) = amount > ceiling  // a function
----

A value is named where the value it stands for would be written, and it may be spread (`+Drafting { ...standardRequest, estimatedCost = Amount(50000) }+`). A behavior taking nothing is implemented by a value, since the parameter counts agree.

[,text]
----
behavior preApprove : (request: AwaitingPreApproval, approverId: EmployeeId) -> PreApproved | NotAuthorized
    depends on now
    constructs PreApproved, NotAuthorized

let preApprove (request, approverId, now) = {
    guard approverId == request.applicant.managerId
        else NotAuthorized

    PreApproved { ...request, preApprovedAt = now(), preApprover = approverId }
}
----

The type comes from the behavior. The `+let+` side only names its arguments, corresponding by position. The behavior-side names are for the reader; what binds is the `+let+`-side names. `+constructs+` is on the behavior, so it is not written on the `+let+` (<<constructs>>).

Arguments are the behavior's argument list followed by `+depends on+` in declaration order. A `+let+` is the pre-injection function and a behavior's type is the post-injection type, so a `+let+` has as many more arguments as there are `+depends on+` (<<depends-on>>). If `+depends on+` is empty, both have the same arguments.

A `+let+` with no corresponding behavior is a *helper*. Not being a domain behavior, it does not pollute the behavior list, cannot be placed in a `+>->+` stage, and does not appear in `+exposing+`. It states its own type, though a parameter whose type its body determines may leave it unwritten (below).

[,text]
----
let isNonNegative (v: Int) = v >= 0
let applyAll (xs: List<Int>, p: (Int) -> Bool) = List.all(p, xs)
----

The return type is inferred. However, a *recursive helper* MUST declare its return type — `+let depth (s: OrgMember): Int = ...+` — because the result type cannot be inferred through the cycle, and only with a declaration can a self-call be type-checked. The declaration is required only for a recursive helper. A non-recursive helper is inferred as before, and a `+let+` with a same-named behavior cannot write a return type (the type comes from the behavior).

A written return type is a declaration into the body, and it stays one where the helper is expanded: it is pushed into the body at each call site, so a value only its context can type — an empty `+[]+` / `+Map.empty+` / `+Set.empty+`, or a `+fold+` over one — takes the declared element type even where the call site itself expects nothing concrete (a generic parameter such as `+Map.toList+`'s). This is the same direction a binding's `+let x: T = v+` has (<<block-expression>>).

The body is an expression. `+{ ... }+` is a block expression (<<block-expression>>), written to place a `+let+` or `+guard+`.

`+=+` introduces a named definition. The bodies of an anonymous block (<<blocks>>) and a `+match+` case are introduced by `+->+` — the same symbol as the type arrow. A lambda written on the right of `+=+` is the parameter-list form: `+let f = (x) -> e+` and `+let f (x) = e+` define one thing, and the parameter-list form is what the formatter writes back. Only a lambda the source wrote moves. A `+.field+` getter is a block too (<<blocks>>), but its parameter is synthesized, so it stays a block — and a block is not a value, which is what a definition writing no parameters would need it to be.

[#fn-value-semantics]
=== A value is substituted where it is named

A value is not module state. Its expression is elaborated in the module that declares it and substituted at each reference, so nothing is held between references and the module's values come into being in no order.

* Its names are resolved once, where it is written (<<qualified-reference>>). What is substituted is the resolved definition, not text to be read again at the reference.
* It is evaluated at each reference. A value's body obeys a helper's rules — it cannot call an injected behavior (<<depends-on>>) — so it is pure and total, and re-evaluation is not observable.
* Two references may yield distinct values. Nothing observes that: there is no reference identity in the language, and comparison is structural (<<newtype-comparison>>).
* An invariant a value breaks is reported at the value, whether or not anything names it.
* What a value constructs is the value's own. A behavior that names one reads something already made, so the construction stays with the definition and is not required in that behavior's `+constructs+` (<<constructs>>). A spread of a value reads one the same way. This is where a value parts from a helper, whose construction set does fold into its caller.
* A spread names a value like any other position: `+Drafting { ...standardRequest, estimatedCost = Amount(50000) }+` reads the same in a behavior's body and in an `+example+` row. A binding in force wins there too, so a parameter or a `+let+` sharing a value's name is what the spread copies.
* A value MUST NOT reach itself, through naming another value, spreading one, or calling a helper that does. A helper on a call cycle is lowered to a method and recurses (<<fn-rules>>); a value has no such form, so a cycle through one is a compile error naming the path it goes round. This is reported apart from the recursion check, which would ask for a return type the author never wrote.

[#fn-rules]
==== Rules

* A `+let+` with a same-named behavior does not write argument types; the type comes from the behavior. A count mismatch is a compile error. A behavior whose type takes nothing (`+() -> T+`) is implemented by a value, which writes no parameter list.
* A `+let+` written with a parameter list defines a function; one written without defines a value. An empty `+()+` is a compile error — a definition taking nothing is the value form. A helper therefore has at least one parameter.
* A module's `+let+` MUST NOT be named like a data the module declares. A data is written where a value goes — a unit data is one, a newtype is applied to what it wraps, a record is constructed by its name — so the two would be one spelling with two answers. An identifier may be written in any script and case carries no meaning (<<unit-data>>), so the collision is refused where it is declared. A behavior and a same-named `+let+` are not a collision: they are one thing's declaration and implementation.
* The same holds for a name that reaches the value namespace by *import*: `+import lib ( Amount )+` in a module that declares `+data Amount+` is refused at the import line. Where a name comes from does not change how many answers one spelling may have. A binding is not a collision — it is in force over a region and everything outside it is unaffected (<<blocks>>) — and neither is an import a module's own `+let+` of that name shadows, which is that `+let+`.
* A helper (a `+let+` with no same-named behavior) states its own argument types, except where its *body* determines them. A parameter takes the type of the first position the body puts it in that names one: an operand of an operator against a value of known type (`+let twice (n) = n * 2+`), an argument of a call whose parameter type is declared and concrete (a signature with a type variable names no type, so a standard-library combinator's `+List<'a>+` determines nothing), the value of a field in a construction, an `+if+` condition, the value of a binding — its written type where it has one, and otherwise whatever the binding's own body determines, so `+let y = x in y * 2+` types `+x+` through `+y+`. The whole body is read, so a position further down it — or a helper declared further down the file — determines the parameter just as well; written order decides only which of several determining positions wins. Call sites are not read — what a helper means is settled by reading the helper, not by reading its callers. A parameter the body leaves open MUST be annotated: Souther has no user generics, so there is nothing to generalise an open parameter into. A *function-typed* parameter MUST be written: neither applying it nor handing it to a combinator that applies it determines its type. A *recursive* helper is lowered to a method rather than inlined (below) and is typed on its declaration, so it writes all of its argument types.
* A helper *may recurse* (self- and mutual recursion). A non-recursive helper is inline-expanded at its call site; a recursive helper is not inlined but lowered to a method — self- and mutual calls become plain method calls. Traversal of self-referential data that `+fold+` cannot write (climbing the manager chain to the root, counting tree depth) is written this way.
* A recursive helper MUST *declare its return type* (above). Without a declaration it is a compile error.
* A recursive helper MUST be *pure*: its own body MUST NOT call an injected behavior (`+depends on+`). It MAY apply a function argument that does — the effect is then the caller's, declared in the caller's `+depends on+` and carried in by the closure (<<blocks>>). An effect touching the outside world is placed on the behavior that calls the helper, or on the function it is handed.
* Recursion is *total by default*. A recursive helper — or a group of mutually-recursive helpers — MUST terminate, proven by *size-change termination*: each recursive call relates caller parameters to callee arguments, an argument that is a strictly smaller part of a parameter is a strict decrease and one passed through unchanged is non-increasing, and every recursive cycle MUST strictly decrease some parameter. A strictly smaller part comes from a `+match+` on a field or a case (`+match s.manager with | Some b -> depth(b)+` passes the unwrapped `+OrgMember+` — an org chart, or a two-`+Option+`-field binary tree), or from a value handed to a standard-library container combinator's closure over a container that is part of a parameter — a list element (`+List.fold((acc, c) -> acc + depth(c), 0, t.children)+` — an element of `+t.children+` is smaller than `+t+`, so an n-ary `+List<T>+`-children tree is total), or an `+Option+`'s unwrapped `+Some+` payload (`+s.manager |> Option.map(b -> depth(b) + 1)+` — the payload of `+s.manager+` is a smaller `+OrgMember+` than `+s+`, so `+Option.map+` recursion over a manager chain is total, exactly as the equivalent `+match+` is). Either way it bottoms out on the finite self-referential data. This one check covers self-recursion, mutual recursion, and structural lexicographic recursion (different calls decreasing different positions). A helper or group that cannot be shown to terminate is a compile error (E2001). Write `+partial let f ...+` to opt out: a `+partial+` helper is not checked and may not terminate, and a `+partial+` member opts its whole mutually-recursive group out. Numeric (`+n - 1+`) and index (`+List.get(i, xs)+` with `+i + 1+`) recursion is not structural — Souther has no inductive `+Nat+` — so it MUST be `+partial+`; counting is otherwise written with `+fold+`. There is no way to *claim* totality on non-structural recursion; `+partial+` only disclaims it. The standard library's `+List.foldFrom+` is trusted total. An `+example+` is evaluated within a time budget, so a `+partial+` recursion that does not terminate is reported rather than hanging the compiler.
* A local lambda (`+let f = (x) -> ...+`) cannot recurse. Recursion is a property of a named module helper.
* Two `+let+`s MUST NOT be written for one behavior.
* A `+let+` may implement a behavior only when both are in the *same module*. A behavior of another module may be imported and called, but its implementation MUST NOT be given by a `+let+` in another module. This is the line that keeps the name-binding rule from conflicting with separate compilation.
* A helper `+let+` may construct data, but its construction set is inferred transitively and MUST be included in the calling behavior's `+constructs+` (<<constructs>>, <<blocks>>) — except for what another module's published body carried in, which that module already stated (<<exposed-values>>). A helper cannot be placed in a `+>->+` stage, because it does not appear in the spec DSL. It may be written in `+exposing+`: what a module offers is not only its list of behaviors.
* A function type (`+(A) -> B+`) is an ordinary type and may be written wherever a type is (<<delimiters>>). What refuses one is the position's requirement, not the grammar: a data field and a behavior's input and output require an external representation, and a function has none — including a function carried inside a `+List+` or a `+Map+` there. A behavior output is a sum of business results, and a function is not a business result.
* A `+let+` may return a function (`+let adder (n: Int) = (x) -> x + n+`). An escaping function — a return value or a runtime choice — becomes a closure capturing free variables (<<blocks>>). If only passed or applied on the spot, it is expandable and no closure is needed. A helper's name written where a value goes is the function it names. A binding MAY state its type (`+let p: (Int) -> Bool = ...+`), and that is what settles the parameters of the lambda it binds. Where no type is written they are inferred from how it is applied (a local rule, distinct from global type inference, which the declarative design does not do — a behavior takes its type from the specification and a helper states its own, <<fn-declaration>>).

[#injected-behavior]
=== A behavior with no implementation — outside-world dependency

*If a behavior with only a type has no implementation*, its implementation is injected from Java. It corresponds to the spec DSL's `+// depends:+` and `+// side effect:+`.

An implementation is either a same-named `+let+` (<<fn-declaration>>) or a right-hand `+>->+` composition (<<composition>>). A `+>->+` composition behavior has no `+let+` but does have an implementation, so it is not subject to injection. What is injected is only one that wrote a type and no `+let+`.

[,text]
----
// spec DSL: // depends: clock
behavior now : () -> DateTime

// spec DSL: // depends: memberRepository
behavior findMember : (id: MemberId) -> Member | NoSuchMember | CorruptStoredData
    constructs NoSuchMember, CorruptStoredData
----

Output cases are domain outcomes only. `+NoSuchMember+` (not found) and `+CorruptStoredData+` (a stored value breaks a domain invariant) are business-meaningful results, so they are cases. A *platform failure* such as DB down is not placed here — the Java Binding throws an exception and Souther passes it through (<<java-impl-rules>>).

No keyword is needed. Having no implementation is what "provided from outside" means. The spec DSL also has no word for `+required+`; whether something is a dependency is only noted in a comment. This form keeps the DSL line as is.

`+constructs+` is required on a behavior with no implementation too (<<constructs>>). The declaration reads the same as when implemented in Souther. `+findMember+` creates two failures and does not create `+Member+`; `+Member+` is obtained by passing a value read from outside through the decoder. The factory of <<java-base-class>> distributes from here.

Typical uses: DB query, HTTP call, file I/O, clock, ID generation, message sending. The concrete APIs are not brought into the language core. The distinction between dependency (only reads) and side effect (changes) is documentation of intent and does not affect value composition.

Forgetting to write an implementation is not an error; that behavior simply becomes subject to injection. But a caller MUST write that name in `+depends on+` (<<depends-on>>), and doing so surfaces it in a `+bind+` argument (<<jvm-behavior>>). If there is no caller, it is not caught within the `+.sou+`.

Which behaviors get a `+let+` and which are injected is not decided mechanically from the DSL. The spec DSL's `+// depends:+` is a note, not an obligation, so its absence does not mean an internal implementation. The 1:1 of <<non-functional>> is a declaration correspondence: one DSL behavior line maps to one Souther behavior declaration. It does not decide the implementation form (`+let+` / injection / `+>->+` composition). The model author chooses the form using the DSL's `+// depends:+` and `+// side effect:+` as cues: a note suggests injection, an internal computation a `+let+`, a chain of state transitions a `+>->+`.

[#java-base-class]
=== Java base-class generation

A behavior subject to injection (wrote a type, no `+let+`; <<injected-behavior>>) is generated as an *abstract base class*, and for each unit data listed in `+constructs+` has a `+protected+` factory that constructs it. Whether it takes one input or several is orthogonal to injection, exactly as for a `+let+`-implemented behavior (<<jvm-behavior>>): a *single* input extends the unary `+Behavior<In, Out>+` (so it still composes with `+>->+`) and inherits its `+apply+`; *any other count* makes it a standalone abstract class with a typed `+apply(A, B, …)+` and no `+Behavior+` supertype. Two or more inputs are more than `+>->+` passes along, and a behavior taking none has nothing to receive, so neither can follow an arrow; both can still be a pipeline's first stage, which receives the pipeline's own arguments (<<sequential-composition>>). A zero-input behavior therefore declares `+apply()+` and is handed nothing — it produces rather than transforms. A Java implementation overrides that typed `+apply+` directly, so several inputs are passed as arguments rather than bundled into a record. A collection parameter keeps its `+java.util.List+` / `+Map+` / `+Set+` (or the runtime `+Option+`) type with its element type, not `+Object+`.

[,text]
----
behavior findMember : (id: MemberId) -> Member | NoSuchMember | CorruptStoredData
    constructs NoSuchMember, CorruptStoredData
----

generates, conceptually:

[,java]
----
public abstract class FindMember implements Behavior<MemberId, FindMemberResult> {
    protected FindMember() {}
    protected final NoSuchMember      NoSuchMember()      { ... }   // only declared unit cases
    protected final CorruptStoredData CorruptStoredData() { ... }
    // apply(input) is inherited from Behavior (unimplemented). An implementation overrides it.
    // A platform failure such as DB down is not a case but an exception. The implementation throws; Souther passes it through.
}
----

Java `+extends+` this and implements `+apply+` (<<java-example>>). Success values (such as `+Member+`) are assembled by the decoder; failure cases are created by the inherited `+protected+` factory. Because a data's constructor is non-public, the implementation may be placed outside the generated package (in any package). An output case that is not a unit or that carries an invariant gets no factory and is obtained via the decoder.

This abstract base class is *always public*, regardless of whether it is in `+exposing+`, so that a Java implementation can `+extends+` it from any module; a behavior subject to injection is by definition implemented outside the module. `+exposing+` controls the exposure of domain types, but the injection base class is scaffolding for implementation and is exposed independently. Without it the injection example of <<example>> would not hold.

Because the base is public and the implementation overrides `+apply+` from outside the module, the implementation *writes* the behavior's input type and its output type. A type the module keeps to itself cannot be written there, and no raw-typed override stands in for it — the erased signature clashes with the one being overridden. So an injected behavior's input and output MUST be exposed by the module that declares them, whether or not the behavior itself is in `+exposing+` (<<exposed-surface>>).

When a *non-unit* data is listed in `+constructs+` and that data is not exposed with `+exposing+`, it is a compile error (E1305). A factory is generated only for a unit data, and a non-exposed data has no decoder either, so a Java implementation would have no way to create that value. If exposed, it can be created via the decoder (<<jvm-codec>>). The requirement is that it be either a unit data or an exposed data.

What is confined is <<invariant-on-construct>>. An invariant-bearing data is always checked whether it goes through `+__construct+` or the decoder. So even if it can be created from outside, *no unvalidated value can be created*. A unit data has nothing to validate, so nothing is lost by allowing it to be created from outside.

The base is an ordinary JVM abstract class, so any JVM language implements it. Kotlin and Scala `+extends+`/`+:+` it and override `+apply+` as Java does; a collection parameter arrives as `+java.util.List+`/`+Map+`/`+Set+`, which a Kotlin or Scala collection or a Clojure persistent collection satisfies directly. Clojure extends the abstract base with `+proxy+` or `+gen-class+` (not `+reify+`, which is interface-only) and dispatches `+apply+` by arity; because the `+constructs+` factories are `+protected+`, a Clojure implementation reaches them through `+gen-class+`'s `+:exposes-methods+` (a `+proxy+` sees only public methods). The factories stay `+protected+` — that is the construction confinement, not an interop choice.

[#java-impl-rules]
=== Rules for Java implementations

A Java implementation returns a *domain outcome* — a success value (such as `+Member+`) and a declared failure case (such as `+NoSuchMember+` / `+CorruptStoredData+`).

A *platform failure* (DB down, network drop, HTTP failure — anything that is not a domain outcome) is not folded into a case but *MAY be thrown as an exception*. Souther does not make the exception a case but passes it through to the boundary (a generated `+>->+` pipeline or `+apply+` does not swallow the exception). The language (`+.sou+`) has no exceptions (<<out-of-scope>>), but a Java Binding that touches the outside world may throw. The boundary (the Java / framework side) receives and handles the exception — HTTP 503, a retry, a transaction rollback. A VM failure or an implementation bug also escapes as an exception (out of scope for guarantees).

Guidance for the distinction. A *domain outcome* (not found, insufficient stock, a stored value breaks a domain invariant — a business-meaningful result) is a case, appears in a domain type, and is subject to exhaustiveness checking. A *platform failure* (infrastructure unavailable or not responding) is an exception, does not pollute domain types, and is handled at the boundary as a cross-cutting concern. Folding DB-down into a case would make every DB-touching behavior's domain type carry an infrastructure case, and when the DB actually goes down there is no honest case value to return (one would have to fake "insufficient stock" or fabricate an infrastructure case). So the former is a case, the latter an exception.

The exception *type* is agreed between the boundary and the implementation. With jOOQ + Spring, the boundary catches `+org.springframework.dao.DataAccessException+` and maps it to 503. jOOQ's own `+org.jooq.exception.DataAccessException+` is not a subclass of Spring's type, so this assumes Spring's exception translation for jOOQ is in effect (Spring Boot's jOOQ auto-config adds it by default). An implementation that throws a checked exception (such as raw JDBC's `+SQLException+`) wraps it in a non-checked exception of the same `+DataAccessException+` family (e.g. `+DataAccessResourceFailureException+`) — not `+IllegalStateException+` or a bare `+RuntimeException+` (which would pass through a `+DataAccessException+`-typed handler and make an infrastructure failure look like a program bug). The handler catches this failure type narrowly, and an implementation bug (an exception) falls through to a general 500.

`+CorruptStoredData+` (a stored value breaks a domain invariant on decode) stays a domain case. Infrastructure worked and returned data, and that data breaking a domain rule is a statement about the *domain*. Whether it deserves a name is the model author's judgment; this rule forces neither.

[#set-invariant]
=== Set invariants are passed as input data

An invariant that a single object cannot decide (schedule overlap, uniqueness) MUST be stated by passing the set needed for the decision as input data, not as a hidden dependency. The side effect of reading existing applications is placed at the workflow boundary (a behavior with no implementation).

[,text]
----
// spec DSL: behavior checkScheduleOverlap = SameApplicantRequests AND Drafting -> Drafting OR ScheduleOverlap
data ScheduleOverlap

behavior checkScheduleOverlap : (
    sameApplicantRequests: List<TravelRequest>,
    request:               Drafting
) -> Drafting | ScheduleOverlap
    constructs ScheduleOverlap        // Drafting returns the input as is; not created

// a behavior with no implementation (reads the outside)
behavior readRequestsOfApplicant : (applicant: EmployeeId) -> List<TravelRequest>
----

`+checkScheduleOverlap+` stays a pure judgment; the side effect is on the outer behavior with no implementation. This corresponds to the conclusion of SMDD's DDD trilemma (purity is not layer separation but making explicit which functions have side effects).

[#requirement-propagation]
=== Requirement propagation

Anything referencing a behavior with no implementation inherits its requirement. Requirements accumulate outward, toward the side that wrote the name. If a `+let+` calls a behavior with no implementation, it becomes the requirement of the behavior holding that `+let+`. It accumulates further onto a composition placing that behavior in a stage.

At the destination, whether to write or infer diverges (<<depends-on>>).

* a simple behavior with a `+let+`: *write* in `+depends on+`; receive it as a `+let+` argument
* a `+>->+` composition: *infer*; decided by the union of the stages' requirement sets

[,text]
----
behavior loadAndConvert = findMember >-> toView      // depends on not written
----

This requires the implementation of `+findMember+`. Composing several gives a union. A composition is not made to write it, because it is readable from the stage declarations; the spec DSL also attaches no `+// depends:+` to a composition.

A stage and a call differ in who owns the behavior. A `+>->+` composition *builds* its stages, so a stage's requirements become the composition's and accumulate outward. A `+let+` that calls a behavior *receives* it, so the behavior itself is the caller's requirement and its own requirements stay with it (<<calling-a-behavior>>). One behavior may be reached both ways; which a module writes says which relationship it means.

The call graph is static at every stage, so the requirement set is decided as a concrete set. That no variable enters is what makes this design hold: inference and declaration can be reconciled, and the composition union can be computed, because the set is concrete (<<core-semantics>>). A behavior reaching itself would leave nothing to build first, so it is a compile error (<<e1608>>).

This is unchanged by making a `+let+` higher-order.

[,text]
----
let applyAll (xs: List<MemberId>, p: (MemberId) -> MemberLabel) = List.map(p, xs)
----

The requirement set of `+applyAll+` is empty. Whatever `+p+` requires is irrelevant, because `+p+` arrives already closed. Requirements are injected as constructor arguments (<<jvm-behavior>>) and enter at the moment `+PreApprove.bind(now)+` builds the implementation. The receiver need not know what it required. `+bind+` is the operation that partially applies that argument.

[#composition]
== behavior composition

[#sequential-composition]
=== Sequential composition `+>->+`

`+>->+` connects behaviors. Of the previous stage's output cases, those the next stage's input type can receive flow to the next stage; the cases it does not receive are carried to the output (departing the mainline).

[,text]
----
behavior handle = findMember >-> toResponse
----

The stage following `+>->+` is single-input (a 1-argument behavior). `+>->+` passes one value to the next stage, so the receiver cannot take two or more. To place a multi-argument behavior downstream, call it inline in the implementation or receive it with `+match+` instead of making it a stage.

*The first stage is not restricted.* The first receives the pipeline's own arguments, so any number is fine; the pipeline receives them as is. A behavior subject to injection is a first stage on the same terms as an implemented one (<<java-base-class>>): the pipeline inherits it as a requirement and calls it with those arguments.

[,text]
----
// spec DSL: behavior reject = AwaitingPreApproval AND RejecterId -> PreApprovalRejected OR NotAuthorized
//           behavior returnToDraft = PreApprovalRejected -> Drafting
//           behavior rejectAndReturn = reject >-> returnToDraft
behavior rejectAndReturn = reject >-> returnToDraft
// rejectAndReturn : (AwaitingPreApproval, EmployeeId) -> Drafting | NotAuthorized
----

The rule of <<type-routing>> requires single input only for the right side; however many the left side takes is irrelevant to routing.

A multi-input pipeline is itself a multi-input behavior, so it cannot be placed downstream of another pipeline. It can be the first stage.

A stage is a behavior, not a `+let+`. `+>->+` is composition on the specification side, and the spec DSL writes it so. A helper `+let+` does not appear in the spec DSL and cannot be a stage.

Decode / encode are not behaviors but edges of the boundary and are not `+>->+` stages. At the boundary, decode first, pass only the successful domain value to the behavior pipeline, and emit the output with encode (<<decoder>>, <<encoder>>). `+>->+` composes only the domain world (behaviors and their sum outputs).

[#type-routing]
=== Type-routing composition rule

A pipeline carries the *mainline*. Only the mainline is passed to a stage; a case a stage did not receive departs the mainline and is *never passed to the remaining stages* of that pipeline. A departed case is piled onto the output.

Let the previous stage's output sum be `+O_f+` and the next stage's input type `+I_g+`. Of `+O_f+`, cases `+I_g+` can receive flow to the next stage; the remaining cases `+R+` depart the mainline.

[,text]
----
f : A -> B | R           g : B -> C           f >-> g : A -> C | R
f : A -> B | R           g : B -> C | S       f >-> g : A -> C | S | R
f : A -> B1 | B2         g : B1 | B2 -> C     f >-> g : A -> C
----

The same holds for three or more stages: *only the mainline passes to the next stage*.

[,text]
----
f : A -> B | C     g : B -> D     h : C | D -> E
f >-> g >-> h : A -> E | C
----

`+h+` can receive `+C+`, but `+C+` already departed the mainline at `+g+`, so it does not reach `+h+`. What reaches `+h+` is only the `+D+` that `+g+` produced. This is the Railway. "Failure" is not special-cased; an unconsumed case simply departs the mainline, and which case departs is decided by the composition partner (<<unmarked-sum>>).

The output sum is treated as an open error row: `+(C | R) | S+` is flattened and same-named cases folded. If no case of `+O_f+` matches `+I_g+`, composition is impossible (<<e1701>>).

That a case departed the mainline is remembered by the composition, and not forgotten by naming a midpoint.

[,text]
----
behavior fg = f >-> g          // mainline D, departed C
behavior x  = fg >-> h         // only mainline D passes to h; C stays departed. x : A -> E | C
----

`+fg+` remembers mainline `+D+` and departed `+C+`. In `+fg >-> h+`, only mainline `+D+` passes to `+h+`, and `+C+` stays departed and is carried to the output. So a named-midpoint `+fg >-> h+` is the same `+A -> E | C+` as the one-line `+f >-> g >-> h+`.

`+>->+` is associative. Hoisting a sub-pipeline by name or regrouping does not change the result.

The mainline/departed split is composition plumbing, not a marker on values (<<unmarked-sum>>). The plumbing unwinds at both ends of the pipeline. Viewing `+fg+` alone, its output is the folded sum `+D | C+`, and the external representation is as before. Even if the same type of case appears in both mainline and departed, the plumbing remembers which rail, so they are not mistaken.

When a downstream stage receives only some cases, or you want to branch per case, open branches with `+match+` instead of `+>->+`.

[,text]
----
match submitTravelRequest(request) with
    | Submitted as s   -> ...
    | AwaitingPreApproval as p -> ...
----

[#composition-with-requirements]
=== Composition with outside-world dependencies

A behavior's internal representation is:

[,text]
----
Behavior<Requirements, Input, Output>
----

`+Output+` is the sum of possible business results, with no fourth slot separating failure. Composition rule:

[,text]
----
f : Behavior<R1, A, O_f>
g : Behavior<R2, B, O_g>        // I_g = B receives cases of O_f
f >-> g : Behavior<R1 ∪ R2, A, (O_g) | (sum of O_f minus the consumed part)>
----

`+R1+` and `+R2+` are what the stages declared (<<depends-on>>). The composition's `+R1 ∪ R2+` is inferred by the composition; a composition does not write `+depends on+`. Whether an implementation is internal or Java-side does not affect value composition. `+Requirements+` (dependencies needed) and `+Output+` (the sum of results produced) are composed independently: the former by set union, the latter by consumption / propagation.

`+Output+` consumption / propagation splits into the *mainline* passing downstream and the cases that departed unconsumed. The composition carries this split, so, like the `+R1 ∪ R2+` set union, `+>->+` is associative (<<type-routing>>). The mainline / departed split stays in the composition plumbing and folds back into a sum when it exits as `+Output+`. The internal representation needs no fourth slot for failure.

[#single-case-composition]
=== Composition of single-case output

A behavior with a single-case output (`+-> A+`) can be seen as having no passed-through case (an empty failure row, `+Never+`). If a downstream stage receives `+A+`, it flows through. The user need not wrap it in anything. If `+guard ... else+` returned another case early, that case propagates as `+R+` of <<type-routing>>.

[#declared-composition-output]
=== Declaring and reconciling a composition's output

A `+>->+` composition's output is inferred from its stages (<<composition-with-requirements>>). A spec DSL composition line writes no output (`+behavior placeOrder = validateOrder >-> ...+`), so the default is this inference.

An inferred output *changes silently on a distant change* when a stage is a behavior of another module. If an upstream stage adds a case, the composition output grows silently; if a downstream stage narrows its input, a previously processed case moves to departed (<<type-routing>>) and likewise increases the output. The composition's definition site has nothing to signal this.

So a composition *MAY optionally declare its output*. If written, it MUST *exactly match* the inferred output or it is a compile error (E1604). Neither too few (a case appears that is not declared) nor too many (a declared case does not appear) is admitted.

[,text]
----
behavior placeOrder = validateOrder >-> priceOrder >-> allocateStock
    -> PlacedOrder | OutOfStock
----

`+-> PlacedOrder | OutOfStock+` is the composition's declaration, not the output of the last stage `+allocateStock+`. Because a stage is a behavior reference (name only), the trailing `+->+` reads unambiguously as the composition's. Writing this line makes an error appear here when an upstream stage adds a case, so it does not grow silently downstream.

Input is not declared. A pipeline is point-free, and the input is decided by the first stage (<<sequential-composition>>). Only the output may be declared. A dependency (`+depends on+`) has the same distant-change risk, but a composition leaves it inferred (<<depends-on>>).

For an internal composition this declaration is optional. But for a composition exposed with `+exposing+` it is *required*, written not on the definition line but in the exposing list as `+name : cases+` (<<modules>>). Leaving a public boundary to inference means that when an upstream stage adds a case, it reaches another compilation unit (another module, or a non-exhaustive Java switch or JSON serialization) silently, and the definition site has nothing to signal it. Placing a signature in `+exposing+` makes the composition's definition error (E1604) the moment a case is added, and the author chooses to handle the case or update the signature. If no signature exists, it is E1605. A non-composition behavior writes its type at the definition, so it MUST NOT write a signature in `+exposing+` (doing so is E1605). This division corresponds to.

[#case-propagation]
== behavior case propagation and Decoder error accumulation

A behavior's output sum is treated as an open error row; a case the downstream does not consume in a `+>->+` propagates through to the tail (<<type-routing>>). This is the composition style of the domain world.

Decode-side error accumulation is handled by the peripheral library Raoh. A derived Object Decoder reads each field from the key of the same name and collects all failures of independent fields (Applicative).

[,text]
----
{ "name": ..., "email": ..., "age": ... }
// read name / email / age with each field's derived Decoder and accumulate all independent failures (Raoh)
----

A derived Decoder's field accesses are mutually independent and collect all failures. Accumulated failures aggregate into Raoh's `+Result+` failure (`+Issues+`). In a custom boundary codec (<<custom-codec>>), one access may depend on a preceding result; from that point it becomes sequential (monadic), and a subsequent access is not run if the preceding one fails.

Accumulation (applicative) is inside the decode boundary; case propagation is behavior composition. They belong to different layers. Because decode is not a `+>->+` stage, the two never mix on the same sum (<<sequential-composition>>). Accumulation holds because a Decoder's field accesses are mutually independent (do not depend on a prior value).

[#examples]
== Examples

An `+example+` attaches compile-time-checked test rows to a behavior. It is evaluated as part of compilation: a row that does not hold is a compile error (<<e1905>>), so a stale example cannot survive a build. An `+example+` is not exposed and produces no run-time class.

[,text]
----
example submitTravelRequest
    | "within the ceiling it submits" :
        (Drafting { applicant = EmployeeId("e-001"), estimatedCost = Amount(50000) })
            -> Submitted
    | "over the ceiling waits for pre-approval" :
        (Drafting { applicant = EmployeeId("e-001"), estimatedCost = Amount(100001) })
            -> AwaitingPreApproval
----

An `+example+` names a target behavior, then lists one or more `+|+`-led rows. A row is an optional description string (a business-case name, followed by `+:+`), an input argument tuple, `+->+`, and an expected result. `+example+`, `+examples+`, and `+for+` are contextual keywords, not reserved words, so they do not collide with an identifier or the `+example.*+` namespace.

[#example-expected]
=== The expected result

The expected side asserts at one of two granularities.

* A bare type name (`+-> Submitted+`) asserts only the *arm* — which case of the output sum the result is — and ignores its fields.
* A construction (`+-> Rejected { reason = "high_cost" }+`), a newtype application (`+-> Amount(0)+`), or a literal asserts the *whole value* by structural equality.

The cases a row may name are the output's cases whether the output is written as a case list (`+-> Submitted | Rejected+`) or under the sum's own name (`+-> Verdict+`, <<sum-data>>) — a case stands where a value of its sum is expected here as everywhere else. A sum among those cases contributes its own cases, so a row names a leaf. The sum's name is not itself an expected arm: it says which cases are possible, not which one this input yields (<<e1904>>).

Types make totality and the case set exhaustive (<<match>>, <<unmarked-sum>>); an `+example+` fixes the value rule for a representative input — which arm, or which value, a given input yields.

[#example-evaluable]
=== What can carry an example

A behavior with a `+let+` implementation is evaluated (<<fn>>), and so is a `+>->+` composition (<<composition>>). An injected behavior (no `+let+`, <<injected-behavior>>) cannot be — you fake one, you do not example it (<<e1902>>). A behavior's `+depends on+` dependencies are supplied by fakes at the example (<<example-fakes>>).

A composition's row is written like any other. Its arguments are the first stage's (<<sequential-composition>>), and its expected result is any case of the composition's output — including one that departed the main line at an earlier stage (<<type-routing>>), which is the part no stage's own example can state, because the routing is not any stage's rule.

[,text]
----
behavior winOrder = settleQuote >-> makeOrder
    -> Order | BelowFloor

example winOrder
    | "meeting the floor wins the order" : (Negotiating { floor = Amount(100) }, Amount(200)) -> Order
    | "below the floor it stops here"    : (Negotiating { floor = Amount(100) }, Amount(50))
        -> BelowFloor { floor = Amount(100), offered = Amount(50) }
----

An input and an expected value are fixtures: literals, newtype applications, record constructions, and helpers applied to those. A `+?+` field takes a value directly (wrapped in `+Some+`) or `+None+` for empty, the same way a `+let+` body writes an optional (<<optional>>); omitting the field reads as `+None+` too. A row's argument is decoded into the behavior's parameter type through that type's derived Decoder (<<decoder>>), so a fixture that breaks an invariant is rejected (<<e1903>>).

A row may also *name a value* (<<fn-declaration>>) rather than write the whole input again, and may spread one to vary a field. A spread copies the fields of the value it names — one another module published as readily as one of this module's own, since a published value crosses closed — and the case is the one the construction writing it names; a name on its own stands for the case the value it denotes constructs. So a fixture in a position typed by a sum says which case it is however it is written.

[,text]
----
let acmeLead = QualifiedLead { companyName = CompanyName("Acme"), budgetFixed = true, ... }

example convert
    | "a fixed budget converts" : (acmeLead) -> Converted
    | "an unfixed budget does not convert" : (QualifiedLead { ...acmeLead, budgetFixed = false }) -> NotConverted
----

What a row may name is a property of the value graph, not of one definition's text: a value is *fixture-evaluable* when its body is a literal, a construction, a spread, `+Set.fromList+` / `+Map.fromList+` over one, a helper applied to those, or a reference to another fixture-evaluable value. So a chain of values holds even though each link names the next. A value that reaches itself has no fixture to be, and is reported as the cycle it is.

A row may also *apply a helper* — the rule the row is about — wherever a fixture value is written: an input, an expected result, a `+with+` value, a `+fake+` table's inputs and outputs, a record field, a list element, a map key or value, and an argument of another helper application. The helper is *run*, as the module that compiled it runs it, and the value it returns is read back into the form a fixture is written in, so what encloses the application is built the one way. Where nothing encloses it — the application is the whole of an expected result, or the whole of a value the row names — the row asserts the value the helper answered with, and which case that is comes from the value rather than from the text. Its arguments are fixtures like any others, so a fixture that breaks the argument type's invariant is <<e1903>>.

[,text]
----
let taxIncluded (amount: Amount) = Amount(amount.value * 110 / 100)

example bill
    | "billAtTaxInclusivePrice" : (taxIncluded(Amount(100))) -> Bill { total = Amount(110) }
----

Without this a row restates what the rule computes — `+Amount(110)+` where it means "the taxed price of 100" — and a change to the rule leaves a row that is wrong and still passes.

Two functions cannot be applied in a fixture, because there is no method to run: a standard-library intrinsic implemented in Java, and a helper whose body produces a function. Both are <<e1903>>, saying that.

Building the fixtures, running the helpers they apply, applying the behavior and comparing the result are one evaluation under one time budget, so a row cannot buy more time by applying more helpers.

`+Set.fromList+` and `+Map.fromList+` are admitted because a value is ordinary code, where a list literal is a `+List+` whatever the position declares, while a row writes a set as its elements and a map as its entry pairs. They are the forms that notation stands for, so one record serves as both a value and a row.

A collection is written as a list, and its declared type says what the list means: a `+List+` keeps its order and repeats, a `+Set+` drops duplicates on decode (`+labels = [ Label("bug"), Label("bug") ]+` is one label), and a `+Map+` takes its entries as `+(key, value)+` pairs — `+counts = [ ("bug", 2), ("ui", 1) ]+` — the form `+Map.fromList+` takes (<<stdlib-map>>). A `+Date+` / `+DateTime+` takes a written temporal (`+Date("2026-07-25")+`, <<temporal-literal>>). This is what lets a rule over dates, sets, or maps be fixed by its examples rather than only by a hand-written test at the boundary.

This holds wherever a value is written, not only inside a record: a behavior taking `+(lines: List<Line>)+` is exampled with `+([ Line { quantity = 1 } ])+`, one returning a `+Map+` is expected as its pairs, and a fake's value is written the same way. A collection does not need a data wrapped around it to reach an example. A map keyed by a newtype (<<collections>>) writes its keys as they are constructed (`+[ (ProductId("A-1"), 3) ]+`), and each key goes through that type's invariant like any other fixture.

When a row does not hold, the diagnostic (<<e1905>>) shows what the behavior produced against what the row expects, both encoded through the data's derived Encoder (<<encoder>>) so the two read against each other.

[#example-fakes]
=== Faking a dependency

To evaluate a behavior that `+depends on+` an injected dependency (<<depends-on>>), the example supplies a fake for it. Best is to need none: an outside-world value written as an *input* rather than an injected behavior keeps the behavior example-able with no fake (<<purity>>). When a dependency stays injected, a fake stands in, scoped to the example and never shipped (no run-time class is produced).

A *value dependency* — one whose faked result is a constant — is given on the row with `+with+`:

[,text]
----
example preApprove
    | (AwaitingPreApproval { ... }, EmployeeId("boss-1")) with now = "2026-07-20T09:00" -> PreApproved
----

A *function dependency* — one whose result varies with its input — is given by a `+fake+` declaration: an input→output table matched by value equality, defaulting to a `+_+` row or, absent one, a miss error (<<e1909>>). A multi-input injected dependency (<<java-base-class>>) is faked the same way, with the row's inputs matched as a tuple.

[,text]
----
fake findManager
    | (EmployeeId("e-1")) -> EmployeeId("boss-1")
    | _               -> EmployeeId("unknown")
----

Each dependency of the target must have a fake — a `+with+` on the row or a `+fake+` table — or it is a compile error (<<e1908>>). A fake, like an example, is written inline or in an attached `+examples for+` file, and is local to its module. `+fake+` is a contextual keyword.

A composition's dependencies are its stages' (<<composition-with-requirements>>), so a row exampling one supplies a fake for each of those. That holds whichever path the row takes: an input that departs the main line at the first stage never reaches the second, and the second stage's dependency is faked all the same. What a row has to supply is a property of the composition, not of the input this row happens to use. One dependency two stages share is one fake — the composition holds one of it (<<composition-with-requirements>>) — and the diagnostic names the stage that wants it (<<e1908>>).

[#example-placement]
=== Inline or an attached file

The base form is written inline, in the same source as the behavior. To keep fixtures out of the model source, examples may instead be written in an attached file that begins with `+examples for <module>+`. It holds the rows, the `+fake+` tables they run against, and the values they name; a data, a behavior, an `+import+` and a `+let+` with parameters belong in the module itself, and writing one there is <<e1906>>. The compiler merges an attached file into its target module; it is not a module of its own and needs no `+import+` (it sees the target module's names directly). Its values join the module the rows join, so a name the module already declares is <<e1906>> too — the rows would read that declaration and the one written here would say nothing. An attached file that names a module not being compiled is <<e1907>>.

[#control-flow]
== Control structures

[#let]
=== let

[,text]
----
let normalized = String.trim(input)
let counted: Map<String, Int> = List.fold((acc, k) -> Map.upsert(k, 1, n -> n + 1, acc), Map.empty, keys)
----

Reassignment is forbidden. A `+let+` is placed inside a block expression (<<block-expression>>). What follows `+let x = v+` is the scope of that binding, nested at desugaring time.

A `+let+` at the top level is a definition (<<fn-declaration>>); a `+let+` inside a block is a binding. Which one a `+let+` is follows from where it is written, not from how it is spelled, and the two are typed from different places. A definition takes its parameter types from its own body and its call sites are not read (<<fn-rules>>). A binding has no declaration to read, so a lambda bound here takes its parameter types from the applications in the body that binds it. A block holds no parameter list — `+let f (x) = …+` is written at the top level — so the two forms never meet in one place.

A binding may carry its type, `+let x: T = v+`. The type is optional — a binding otherwise takes the type of its value — and writing it does two things: the declared type is pushed into the value, so a value only its context can type (an empty `+[]+`, `+Map.empty+`, `+Set.empty+`, including one produced by a `+fold+` over such a seed) takes the declared element type instead of staying undetermined (<<algebraic-types>>); and the value is checked against it, so a declared type the value does not have is a compile error rather than an ignored comment. This is the same declaration-into-body direction a helper's declared return type has (<<fn-declaration>>) — it is a declaration, not an extension of inference. As with a helper's return, `+T+` is an ordinary type, a function type included: `+let p: (Int) -> Bool = (x) -> ...+` settles the parameters of the lambda it binds, and is how a lambda whose body names no type for them is given one (<<fn-rules>>). A tuple destructure (`+let (a, b) = t+`) takes no annotation.

[#if]
=== if

[,text]
----
if condition then expression1 else expression2
----

`+if+` is an expression. If both branch types agree, its type is that type; if they are different data, it is a sum of both (`+if c then Submitted{...} else AwaitingPreApproval{...}+` is `+Submitted | AwaitingPreApproval+`). A mismatch between primitives is a compile error.

The condition is a `+Bool+`, with one exception: a construction followed by `+as <name>+`, whose invariant decides the branch and whose value the name carries into the success branch (<<attempted-construction>>).

The widening reaches inside a collection as well, since a collection is element-covariant (<<collections>>): branches giving lists of different cases give a list of both, the same direction `{plus}{plus}` takes on its elements (<<stdlib-list>>). It descends `+List+`, `+Set+`, `+Map+`, `+Option+` and tuples, so an empty collection whose element type nothing has fixed yet takes it from the other branch at any depth, not only at the top. Where the context did fix it — a declared return or field type reaches both branches (<<collections>>) — the two branches merge by the widening like any other pair. `+match+` arms merge by this rule too.

[,text]
----
if total >= 100000 then [HighValueTravel { threshold = threshold }] else [ClientCost]   // List<HighValueTravel | ClientCost>
----

[#match]
=== match

[,text]
----
match request with
    | Drafting as d             -> ...
    | Submitted as s            -> ...
    | AwaitingPreApproval as p  -> ...
    | PreApproved as a          -> ...
----

Place `+with+` after the scrutinee and list cases one per `+|+`. The leading `+|+` of the first case is optional. Braces are not used. Souther is layout-independent, so only `+|+`-separated cases hold without layout.

The one place layout decides anything is which match an arm belongs to. A `+match+` written in an arm's body is ended by a `+|+` that reaches back to the enclosing match's arm column; a `+|+` indented past it is the inner match's own arm.

[,text]
----
match settlement with
    | FixedSettlement { budgetRange } ->
        match budgetRange with
            | RangeBudget { ceiling } -> ...      // an arm of the inner match
            | UndecidedBudget          -> ...
    | HourlySettlement { unitPrice } -> ...              // back to the outer match
----

Nothing else reads indentation, and a misplaced arm cannot silently change meaning: a case is a named data (<<sum-data>>), and a name belongs to one data, so an arm that lands on the wrong match is a compile error naming the case and the sum. Where the two matches are on one line, the columns cannot separate them — write the inner one in a block (`+-> { match … }+`), which ends it explicitly.

A case value is bound with `+as+` (the `+s+` in `+| Submitted as s+` is Submitted, read as `+s.submittedAt+`). `+as+` binds the whole matched value. A bare identifier beside the case name is not a second spelling of it: `+| Submitted s+` is a compile error naming the `+as+` form to write instead. A case is a reference to a named data (<<sum-data>>), so it carries no payload to bind positionally; the one case that does is Option's `+Some+`, and the positional form is written only there (below).

Fields may be bound directly with a destructuring pattern, the inverse of construction. It uses the same `+{ }+`, `+,+`, `+=+` as construction `+Member { id = x }+`, and `+{ id }+` is shorthand for binding to a same-named variable (paired with <<record-literal>>). Write only the fields used. Destructuring is possible only for a single named case; an or-pattern (below) binds to a sum type and has no fields. It may be combined with `+as+`: `+| Member { id } as whole+` binds both fields and the whole.

[,text]
----
match c with
    | EmailContact { email = e } -> ...   // e is the email field
    | Member { id, mail }        -> ...   // { f } binds f to a same-named variable
----

A newtype case is opened with the constructor form `+X(v)+`, the inverse of construction `+X(v)+` (<<newtype>>). `+v+` binds the wrapped value. Nesting it reaches through a newtype over a newtype in one pattern — `+| Activated(EmailAddress(s)) -> s+` binds `+s+` to the base `+String+`, so `+.value.value+` is not written; the shorter `+| Activated(a) -> ...+` binds `+a+` to the one wrapped layer (`+EmailAddress+`). Each written name MUST be the newtype opened at its layer: `+Activated(Source(s))+` is a compile error when `+Activated+` wraps `+EmailAddress+`, not `+Source+`. The single-layer accessor `+.value+` (<<newtype>>) stays for reading one layer inline; the pattern is for reaching through several. The same form opens a newtype where a name is bound (<<binding-patterns>>); what `+match+` adds is the arm for a value that may be one of several cases.

[,text]
----
match m with
    | Activated(EmailAddress(s)) -> s          // s is the base String, two layers opened
    | Unactivated(a)             -> a.value    // a is EmailAddress, one layer opened
----

[#primitive-arm]
An arm may name a primitive type. A behavior or a standard-library function that answers a value or a reason there is none returns a union with a primitive as a member (<<union-member>>) — a model's own `+-> Int | NoAnswer+`, and the core's `+Int.divide+` / `+Int.remainder+` returning `+Int | DivisionByZero+` (<<stdlib-int>>), `+Decimal.divide+` returning `+Decimal | DivisionByZero+` (<<stdlib-decimal>>), `+String.toInt+` / `+String.toDecimal+` returning `+Int | NotANumber+` / `+Decimal | NotANumber+` (<<stdlib-string>>) — and the arm that takes the value names that primitive. Nothing wraps it: the matched value is the number itself, so `+as+` binds it as it binds any other case.

[,text]
----
match Int.divide(i.numerator, i.denominator) with
    | DivisionByZero -> 0
    | Int as n       -> n
----

`+| Int(n)+` is rejected: the parens open a newtype (above) and a primitive is not one, so the message names the `+as+` form instead. `+| n -> n+` is not a fallthrough either — Souther has no `+_+` wildcard, every arm names a case, and `+n+` is looked up as a type name and not found.

Where the model has already ruled the failure out — a `+require+` (<<attempted-construction>>) or the divisor type's own invariant keeps the divisor away from zero — the union need not arise: the operator `+/+` divides, and its abort on zero (<<stdlib-int>>) cannot be reached. The arm is for the divisor the model admits as an input.

To route multiple cases to the same processing, list `+|+` within a case, `+| A | B -> ...+` (an or-pattern). It writes "these states are treated the same" for a state-machine sum in one line. The case-separator `+|+` and the or-pattern `+|+` are the same symbol, but `+->+` ends a case's pattern part, so they do not conflict.

[,text]
----
match request with
    | Submitted | AwaitingPreApproval as x -> ...   // x is TravelRequest (the sum type)
    | Drafting as d    -> ...
    | PreApproved as a -> ...
----

An or-pattern's binding differs from a single case. A single case's `+as+` binds to that case's type (the `+s+` in `+| Submitted as s+` is `+Submitted+`), but an or-pattern's `+as+` binds to *the scrutinee's sum type*, because no single case type fits all alternatives. So an or-pattern binding cannot read case-specific fields; carry it as the sum or open it again with match. Exhaustiveness counts cases one by one; a case received by two cases is a duplicate error.

The `+Some+` of `+Option+` (<<algebraic-types>>) extracts the wrapped value by *positional binding*. The `+v+` in `+| Some v+` is bound to the contents, not to `+Some+`. `+Some+` is the only built-in case with a payload, so it reaches the contents by positional binding rather than `+as+` (which binds the whole value elsewhere). `+| Some as v+` cannot be written. A `+?+` field and the return of `+List.get+` / `+Map.get+` are extracted this way.

When the contents are a newtype, the constructor-destructuring form nests inside the positional binding: `+| Some(EmployeeId(v)) -> v+` opens the wrapped `+EmployeeId+` and binds `+v+` to its base value, so the `+.value+` on the positional binding is not written. The first written name MUST be the element type — `+Some+` wraps `+EmployeeId+`, so `+Some(EmailAddress(v))+` is a compile error — and each further name opens one more layer, the same rule as `+X(Y(s))+` on a user case. This nesting is allowed only in a pattern; `+Some(...)+` is still not a construction form (<<algebraic-types>>). The short `+| Some v+` (bind the whole contents) stays.

[,text]
----
data TravelCompleted = { preApprover: EmployeeId? }

let approverLabel (c: TravelCompleted) =
    match c.preApprover with
        | Some(EmployeeId(v)) -> v         // v is the base value, no .value
        | None              -> "None"
----

A match on sum data MUST be exhaustive. Exhaustiveness is decided over the direct cases the sum declared. A nested sum (`+OwnCost+` of `+data CostBearer = OwnCost | ClientCost+` being further `+Reimbursement | Advance | CorporateCard+`) does not flatten leaf cases; receive `+OwnCost+` and split with a nested `+match+`. Exhaustiveness is checked independently per layer, so cases never overlap. Case→sum assignment (<<sum-data>>) folds to the leaf; match is the reverse, descending the layers.

[#unreachable]
==== An arm may say its combination cannot arise

A table indexed by two sums has a cell for every pair, and some of those pairs the model does not admit. `+unreachable "reason"+` is what such an arm answers: it produces no value, and reaching it aborts.

[,text]
----
match age with
    | UnderThirty ->
        match period with
            | UnderOneYear      -> BenefitDays(90)
            | TenToTwentyYears  -> BenefitDays(180)
            | TwentyYearsOrMore ->
                unreachable "twenty insured years cannot precede the age of thirty"
    ...
----

This is not a proof. The compiler does not decide that the point cannot be reached — it could not, since what rules the pair out is a fact about the world or a check some caller already made, and neither is written in the types this rule sees. What the form does is state that premise where it is relied on, and make its failure an abort rather than a number a report goes on to print.

The rules it obeys:

* The reason is a string literal and MUST be written. It is read without running the model — by a reader, by the diagnostic an `+example+` gets (<<e1911>>), and by the abort's message — so it is not an expression that builds one.
* Its type is `+Never+` (<<algebraic-types>>), which fits whatever the position expects. An arm answering it contributes no case to what the `+match+` answers: the type is the one the other arms agree on.
* The position it stands in MUST state what it holds, or a branch beside it MUST — a field, a declared return, an annotated binding, an arm beside one that answers a value. Written where nothing does (`+let n = unreachable "..."+`, `+1 + unreachable "..."+`), it is <<e1307>>: the value it stands for is never made, but the code around it is still compiled, and nothing there says what shape that code reads.
* Exhaustiveness counts the arm like any other. Nothing here relaxes <<e1201>>, and there is still no `+_+`.
* Reaching it *aborts*, as an invariant violation does (<<invariant-abort>>) and for the same reason: what failed is the model, not the business. It is not catchable, and a boundary maps it to a 500, apart from a business failure's 400.
* It is not written in an `+invariant+` (<<invariant-expressions>>): an invariant answers whether the value being built holds, on every path through it.

What it is not for is a case the model can produce. `+| InsufficientFunds -> unreachable "the caller checked the balance"+` states an assumption no type carries, and if the caller ever does not check, the rule aborts where it should have answered. Where the combination is one the model admits as input, the arm answers a value or the input types change; `+unreachable+` is for what the model rules out.

[#guard]
=== guard

[,text]
----
guard amount <= balance
    else InsufficientBalance
----

`+guard+` is used inside the implementation (`+let+`) of a behavior whose output has a departure case. If the condition is false, it returns the `+else+` value and ends on the spot. The `+else+` value is one of the output sum's cases (just data). The implementation only places the value of the case it wants to return as the last expression. No special wrapping.

`+guard+` is sugar for `+if+`. The following two mean the same.

[,text]
----
guard <condition> else <value>
<rest of the body>
----

[,text]
----
if <condition> then <rest of the body> else <value>
----

Desugaring is done at parse time; later stages (type check, construction-authority check, backend) see only `+if+` or the attempted form below. That both branches may have different types (<<if>>) is what makes this desugaring hold.

[#attempted-construction]
=== An attempted construction

[,text]
----
guard DomainName(d) as name else BadDomain
if DomainName(d) as name then [ name ] else []
----

Where the condition is a construction followed by `+as <name>+`, that construction's invariant decides
the branch. The invariant is run — the type's own and every invariant a `+...+` spread brought in
(<<invariant-mvp>>, <<field-spread>>). Holding, the value is built and `+<name>+` names it in the
success branch; failing, the `+else+` value is taken and no value is built. The invariant runs once.

A construction is either spelling — a newtype's `+T(v)+` or a record literal `+T { ... }+`
(<<record-literal>>). A behavior that reports every business failure rather than the first one it meets
builds the reasons as a list and attempts the case that carries them, so "at least one reason" is that
case's own invariant rather than a guard written beside it.

[,text]
----
data NotConverted = { reason: List<BlockedReason> }
    invariant List.length(reason) >= 1

if NotConverted { reason = blockers(lead, enquiry) } as blocked
    then blocked
    else Converted { ... }
----

The name is in scope in the success branch only. *Nothing carries the failure.* There is no value for
it — no `+Option+`, no `+Result+`, no reason — and the name a business failure gets is the one written
in `+else+`, which MAY be a value naming nothing (`+else []+`).

`+guard+` here is the same sugar for `+if+` (<<guard>>), so the `+if+` form is the base one and a
helper `+let+`, which has no departure case to name, reaches it too.

[#attempt-departures]
==== Departing per clause

The `+else+` MAY instead answer each invariant clause the type names (<<invariant-clause-name>>), so a
behavior that departs differently per rule states the rules once rather than restating them as guards.

[,text]
----
guard QuoteLines(List.map(r -> toLine(r), lines)) as ls else
    | nonEmpty       -> NoLines
    | uniqueProducts -> DuplicateProduct
----

What an arm answers is which rule failed. The name a business failure gets is still the one the arm
writes, and no value crosses from the failure into the arm.

Which arm is taken is decided by the clause that failed, so the order the arms are written in has no
effect; which clause failed is decided by the order the clauses are declared in (<<invariant-mvp>>).

The arms MUST cover what can fail, so that no failure reaches a branch that is not there:

* every named clause of the type MUST have an arm, and an arm MUST name a clause the type has;
* `+| _ -> …+` MUST be written when the type has a clause carrying no name, and MUST NOT be written when
  it has none — it answers the clauses that cannot be named, and there being none to answer is worth
  saying.

Adding an unnamed clause to a type whose clauses are all named is therefore a compile error at every
mapping site, which is what adding a rule to a published type should be: today it shows up only as more
aborts and more decode failures.

The `+else <value>+` form keeps its meaning — one value for any failure — so naming a clause does not
disturb a site that does not care which rule broke.

A construction inside an argument is an ordinary construction and aborts on violation
(<<violation-destination>>); what is attempted is the outer construction alone.

An attempt builds a value on its success branch, so the enclosing behavior's `+constructs+` MUST name
the type (<<constructs>>). The type MUST carry an invariant, its own or one a spread brought in:
without one the `+else+` value could never be reached, so writing it is a compile error rather than a
branch that is not one.

Writing `+T(v)+` on its own still aborts (<<violation-destination>>). This is the form a writer
chooses at the site, and it is what lets a rule be stated once — the rule lives in the type's
`+invariant+`, and a guard restating it can drift from it. Across a module boundary the restatement
cannot be written at all: a helper `+let+` an invariant names is not exposed (<<exposed-surface>>), and a
behavior cannot be called from an invariant (<<invariant-expressions>>). The attempt names the type,
which the declaring module does expose.

Newtype arithmetic (<<newtype-arithmetic>>) re-wraps rather than constructs, so it is not what `+as+`
takes; write the construction out (`+T(a.value - b.value)+`).

[#block-expression]
=== Block expressions

`+{ ... }+` is an expression. Place `+let+`s and `+guard+`s, then put the result expression last.

[,text]
----
let preApprove (request, approverId) = {
    guard approverId == request.applicant.managerId
        else NotAuthorized

    PreApproved { ...request, preApprovedAt = now(), preApprover = approverId }
}
----

If only the result expression is placed, no block is needed. `+let isNonNegative (v: Int) = v >= 0+` and `+let isNonNegative (v: Int) = { v >= 0 }+` are the same.

A block is an expression, so it may be written anywhere an expression may (`+if c then { let x = f(a) g(x) } else h+`). Its contents desugar per the rules of <<let>> and <<guard>> and appear in the AST as bindings and `+if+`. A bare `+{+` resolves to a block expression; a record literal is preceded by a type name (<<record-literal>>), so there is no confusion.

[#purity]
== Purity

Souther code *does not touch the outside world directly*. The following are forbidden.

Mutable variables, field assignment, static mutable fields, random, current time, environment variables, files, network, threads, exceptions, reflection.

An outside-world dependency is declared as a behavior with no implementation, and its implementation is injected from the Java side (<<injected-behavior>>). A `+let+` may receive one as an argument and call it, so a `+let+`'s result may depend on the outside world. But the way it touches must go through a call to the injected thing, and that fact is written in `+depends on+` (<<depends-on>>). This corresponds to the conclusion of SMDD's DDD trilemma — purity is not layer separation but making explicit which functions have side effects (<<set-invariant>>). *Souther made this "explicit" literal.* Left to inference, which functions have side effects cannot be read from the declarations.

*"The requirement set is empty" is stronger than this sense of purity.* This chapter's sense is "does not touch directly", which every `+let+` satisfies. An empty requirement set means receiving nothing injected, which only some `+let+`s satisfy. What may be called from an invariant is the latter (<<invariant-expressions>>). To avoid conflating the two, the latter is henceforth called "empty requirement set" and not "pure".

[#stdlib]
== Standard library

[#reserved-namespace]
=== Reserved namespace

The standard library is bundled with the compiler and referenced by short qualifiers — `+List+` (list), `+Map+` (map), `+Set+` (set), `+String+` (string), `+Bool+` (boolean), `+Int+` / `+Decimal+` (numbers), `+Date+` / `+DateTime+` (temporal), `+Option+` (optional). Every function is called through this qualifier: `+List.map(f, xs)+`, `+String.trim(s)+`, `+List.length(xs)+`. There is no automatic import — names are not delivered implicitly. What may be written bare is operators (`+==+` `+<+` `+{plus}{plus}+`, etc.), `+if+` / `+match+`, literals, and the current module's helpers. Argument order follows the convention of <<pipe>> (primary subject last).

A standard-library function is therefore never a bare name and never crosses what a module writes bare. What a module writes bare in a value position is one of: a binding in force, one of its own `+let+`s, a data of its own written as a value, a behavior it can reach, a name an import let it write without its qualifier, a name the language gives (`+None+`), or a case of a data core declares (`+HALF_UP+`; <<stdlib-decimal>>). One spelling means one of these — a `+let+` may not be named like a data (<<fn-rules>>), a name the language gives may not be taken, and a binding in force wins over a declaration.

A qualifier is the only spelling that reaches its library, so a *type* MUST NOT be named like one: `+data List = String+` is a compile error, as `+module souther.foo+` is. In expression position the qualifier still yields to a binding — a parameter or a `+let+` named `+Map+` makes `+Map.empty+` that binding's `+empty+` field — because a binding in force wins over everything.

To call a library name bare, import it explicitly: writing `+import List (map, filter )+` lets you write `+map(f, xs)+` unqualified thereafter. Qualified access always works, and `+import+` is only sugar to elide the qualifier. Importing the same bare name from two modules is a compile error, so qualify one of them (e.g. `+String.length+` and `+List.length+` used together in one module; <<imports>>).

Qualifiers such as `+List+` denote a module only in expression position, distinct from the type-position `+List<T>+` (angle brackets), which does not conflict. `+length+` / `+get+` span `+String+` and `+List+`, and `+List+` and `+Map+`, but they become distinct names `+String.length+` / `+List.length+`, `+List.get+` / `+Map.get+`, so they are not overloads but each module's own function.

The entity the short qualifier denotes is placed in the reserved namespaces `+souther.string+` / `+souther.list+` / `+souther.map+` / `+souther.set+` / `+souther.bool+` / `+souther.int+` / `+souther.decimal+` / `+souther.date+` / `+souther.datetime+` / `+souther.option+`. The `+souther+` namespace is reserved, and a user module MUST NOT name itself under it — `+module souther.foo+` is a compile error. Only the reserved namespace holds core's privileges (generics, recursion, intrinsics), and this is the line preventing a user from granting them to itself (the boundedness of <<algebraic-types>>). A name that merely starts with the string `+souther+`, such as `+southernmost+`, is an ordinary user name, not under this namespace.

[#type-variables]
==== Type variables

A core function may write a type variable `+'a+` in a type position — a parameter, a return value, `+List<'a>+`, `+Map<String, 'a>+`, or a function type `+('a) -> 'b+`. No declaration list (`+<A>+`) is written; a `+'a+` appearing in a signature is implicitly universally quantified. Because identifiers do not distinguish case (<<unit-data>>), a type variable is marked by a leading apostrophe rather than by a lowercase name.

Only core in the reserved namespace may write a type variable; a user module writing `+'a+` is a compile error. The user model stays bounded (<<algebraic-types>>). When a non-recursive core helper has `+'a+`, it is monomorphized by inline expansion at the call site — `+'a+` is resolved to each call's concrete type, and no polymorphic method is generated.

[#intrinsics]
==== intrinsics

A primitive is declared as a core function with a body of `+= intrinsic "key"+`. `+key+` names the JVM operation the backend emits and is *prefixed per type* to make it unique (`+"string.trim"+`, separating `+list.length+` and `+string.length+`).

[,text]
----
let trim (s: String) : String = intrinsic "string.trim"
----

An intrinsic MUST declare its return type (it cannot be inferred from `+intrinsic+`). A call is type-checked against the declared signature — that is, `+trim+` is "a built-in function whose signature is placed in core", and this declaration, not a hardcoded compiler table, decides its arguments and return value — and the backend emits the bytecode for `+key+`. It is neither inlined nor lowered. Only the reserved namespace may write it. A user cannot call the JVM directly and only calls blessed functions (<<asymmetric-interop>>).

*Every* standard-library function is declared in a core module this way, whether its body is Souther (self-hosted, like `+List.map+` over `+foldFrom+`) or `+intrinsic "key"+` (a JVM kernel). The declaration is the single source of truth for the signature — there is no compiler table of signatures, and a function the compiler can call but a declaration does not describe does not exist. What stays in the compiler is what the *type language cannot say*, as a side condition on a declared signature rather than in place of one:

* the operators (`{plus}` `+-+` `+*+` `+/+` `+==+` `+<+` `+<=+` `+>+` `+>=+`) are syntax, and the arithmetic ones carry the closed-newtype rules (<<newtype>>) a plain function does not;
* "the element is an ordered value" — Souther has no `+comparable+` type class, so `+List.sort+` / `+max+` / `+min+` / `+sortBy+` declare `+List<'a>+` and the constraint on `+'a+` is checked in the compiler.

Because a signature is a declaration and nothing else, a standard-library function is a function value like any other: `+List.map(String.trim, xs)+` and `+let f = String.length+` are ordinary (<<blocks>>). A value the library offers is declared the same way, with no parameter list — `+let empty : Map<'k, 'a> = intrinsic "map.empty"+` — and is written `+Map.empty+`.

[#pipe]
=== The value pipe and argument order

To thread a value through functions, write `+|>+` left to right. `+e |> f(a)+` is `+f(a, e)+` — the left side enters the *last argument* of the right-hand call. A parenthesis-less function name `+e |> f+` is `+f(e)+`. `+|>+` binds most loosely and left-associatively, so `+a |> f |> g+` reads as `+g(f(a))+`.

[,text]
----
input.raw
    |> split(",")                          // split(",", input.raw)
    |> map(piece -> piece |> trim |> lowercase)
    |> filter(piece -> String.length(piece) >= 1)
    |> sort                                // sort(...)
----

Standard library arguments put *the primary subject (collection, string, Map) last, functions, separators, and keys first*: `+List.map(f, xs)+`, `+List.filter(p, xs)+`, `+List.fold(step, seed, xs)+`, `+String.split(sep, s)+`, `+Map.get(key, m)+`. So the left value drops into the last argument and the pipe flows top to bottom. A `+fold+`'s folding block stays in `+(acc, x)+` order.

The right side admits only a function call or a function name; `+e |> 3+` is a compile error. A bare field getter is not a pipe target either — write `+e.field+` for a single value, or use the getter inside a call (`+xs |> List.map(.field)+`), not `+e |> .field+` (<<blocks>>). `+|>+` is expanded to a call at parse time, so no later stage sees `+|>+` — the same pure syntactic sugar as `+guard+` expanding to `+if+`. It is distinct from the `+>->+` that composes behavior stages (<<composition>>); that connects behaviors, this threads expression values.

[#stdlib-string]
=== String

[,text]
----
length   isEmpty  trim     lowercase  uppercase  contains  startsWith  endsWith
substring  append  reverse  repeat     padLeft    padRight  lines
split    join  replace    words      fromInt   concat       matches
toChars  toCode  toInt  fromDecimal  toDecimal
----

`+append(a, b)+` joins two strings in their written order; the `{plus}{plus}` operator is the common form, `+append(a, b)+` equals `+a {plus}{plus} b+` (<<stdlib-list>>).

`+matches(pattern, s)+` is a whole-string regular-expression match (Java `+Pattern+` flavour, anchored: the *entire* string must match), returning a plain `+Bool+`. It is what states a format-constrained value as an invariant — `+data PostalCode = String invariant String.matches("[0-9]{3}-[0-9]{4}", value)+`. The `+pattern+` MUST evaluate to a string at compile time: it is validated there (compiled once to confirm it is well-formed), so a malformed regex is a compile error rather than a runtime exception. A string literal evaluates to one, and so does a `{plus}{plus}` of literals and of values — a `+let+` with no parameter list (<<fn-declaration>>) — which is how types whose formats share a part hold that part once instead of spelling it out in each of them:

[,text]
----
let sitePrefix = "001"

data SiteId = String
    invariant String.matches(sitePrefix ++ "[0-9A-Za-z]{12}", value)
----

What is validated is the string the whole expression evaluates to, not the pieces it is written in. At run time the pattern is compiled on first use and cached, not recompiled on each call. A regex backslash class is written with a doubled backslash (`+"\\d{3}"+`), since a string literal drops the backslash of an unknown escape (<<primitives>>). A pattern a run-time value takes part in is therefore not accepted (a future `+Regex+`/`+fromString+` would carry that, returning a case for an invalid pattern); a pattern the compiler can read is what the invariant needs. Regex lives in core rather than a package, since Souther has no package layer. A pathological pattern can backtrack; keep invariant patterns simple.

The middle row is the rest of what Souther's types allow, which have no `+Char+`, `+Maybe+` or `+Float+`. `+split(sep, s)+` splits by a separator into `+List<String>+`, keeping empty pieces (`+split(",", "a,,b")+` is `+["a", "", "b"]+`). `+words(s)+` splits by runs of whitespace, dropping empty pieces. `+join(sep, xs)+` joins with a separator. `+replace(target, replacement, s)+` replaces every occurrence of `+target+`. `+fromInt(n)+` makes an `+Int+` a decimal string. `+concat(xs)+` joins a `+List<String>+` with no separator (equal to `+join("", xs)+`). The primary subject string is last (<<pipe>>). There is no `+Char+` type and no character-mapping operation.

`+isEmpty(s)+` is `+length(s) == 0+`, the sibling of `+List.isEmpty+` / `+Map.isEmpty+` / `+Set.isEmpty+`. It belongs in a predicate — `+filter(piece -> not(String.isEmpty(piece)))+` — rather than in a newtype invariant: a derived decoder recognises `+String.length(value) >= 1+` and reports a violation as `+too_short+` with its bound, while the helper's inlined form leaves it the generic `+invariant_violation+` (<<decoder-error>>).

`+reverse+` / `+repeat+` / `+lines+` / `+padLeft+` / `+padRight+` are the rest of what Souther's types allow. `+reverse+` walks code points, so a character outside the basic plane survives it. `+repeat(n, s)+` joins `+n+` copies (nothing for `+n+` of 0 or less; a count no string could hold *aborts* rather than quietly giving fewer copies than asked for, as an `+Int+` overflow does — <<stdlib-int>>). `+lines(s)+` breaks on newlines, accepting both `+\n+` and `+\r\n+`, and keeps empty pieces — a trailing newline leaves an empty last line. `+padLeft(n, pad, s)+` / `+padRight+` widen `+s+` to `+n+` characters with copies of `+pad+` and leave a string already that long alone; `+pad+` is a length-1 string, so a longer one can overshoot the width. Padding is what *builds* a fixed-width identifier — a bay number becomes `+"03"+` with `+padLeft(2, "0", fromInt(bay))+` — so a code whose shape a newtype invariant states can be produced in the domain and not only checked there.

`+fromDecimal(d)+` renders a `+Decimal+` in plain notation, never in exponent form, keeping the scale the value carries: `+1000.00m+` is `+"1000.00"+`. Scale is incidental to the number (<<primitives>>) but not to how it is written, so a caller wanting a fixed number of places sets it first with `+Decimal.round(d, scale, mode)+` and names the rounding there. Grouping separators and a currency symbol are presentation and stay outside the domain. `+toDecimal(s)+` parses back, returning `+Decimal | NotANumber+` — the sibling of `+toInt+`, and a compiler built-in for the same reason.

The bottom row gives character access without a `+Char+` type — a character is a length-1 `+String+`. `+toChars(s)+` gives the characters of `+s+`, one per Unicode code point, as single-character strings (`+toChars("a12")+` is `+["a", "1", "2"]+`), so `+List.fold+` can walk them. `+toCode(ch)+` is such a character's first code point, `+-1+` for the empty string. `+toInt(s)+` returns `+Int | NotANumber+`: a named case, since `+Maybe+` has no surface form — the same case-return the `+/+` operator and `+Int.divide+` draw between abort and case. `+toInt("007")+` is `+7+` (leading zeros kept, unlike a numeric parse-and-reformat); `+toInt("12x")+` is `+NotANumber+`, and the parsed value is taken out with `+| Int as n+` (<<primitive-arm>>). `+toInt+` is a compiler built-in rather than a core declaration (<<intrinsics>>); `+toChars+` / `+toCode+` are ordinary intrinsics.

Together these make a checksum (Luhn, EAN, a mod-10 check digit) a plain `+let+` over `+List.fold+` in a behavior: validate the digits with `+matches("[0-9]+", value)+` in the type's invariant, read each digit as `+toCode(ch) - toCode("0")+` (total, because the invariant proved every character is a digit), and take the remainder with `+Int.modBy+`. A checksum is *not* an invariant — it folds, and an invariant may not recurse (<<invariant-expressions>>) — so it lives in a behavior, but a short one.

[#stdlib-int]
=== Int

[,text]
----
add  subtract  multiply  divide  remainder  compare  modBy
abs  min  max  clamp
----

`+Int+` is signed 64-bit (<<primitives>>). If an operation exceeds that range it *aborts* — it does not wrap. Overflow is a model bug, not a business result, so like an invariant violation it throws `+ConstraintViolation+` (<<algebraic-types>>, <<violation-destination>>, <<jvm-abort>>).

Division by zero returns `+Int | DivisionByZero+`. This is a possible input on the business flow (a divisor of 0), so it is returned as a case rather than aborting. The arm that takes the quotient names the primitive and binds it with `+as+` — `+| Int as n+` (<<primitive-arm>>).

The four operations may also be written with the operators `{plus}` `+-+` `+*+` `+/+` (the symbol table of <<primitives>>). `+/+` is truncating division and *aborts* on division by zero (like overflow). To receive `+Int | DivisionByZero+` as a case, use the functions `+divide+` / `+remainder+` — operator = casual and aborting, function = safe with a case.

`+abs+` / `+min+` / `+max+` / `+clamp+` are ordinary core `+let+`s over `+<+` and `+-+`. `+abs(n)+` negates with the `+-+` operator, so the smallest `+Int+` — the one value with no positive counterpart — aborts on overflow like any other overflow here; it is what turns a signed difference into a distance (`+Int.abs(Date.daysBetween(a, b))+` says "how far apart" without the caller choosing an argument order to dodge the sign). `+min+` / `+max+` are the two-value form the comparison operators imply, distinct from `+List.min+` / `+List.max+`, which take a list and answer an optional because a list may be empty. `+clamp(lo, hi, n)+` holds a value inside a range, the subject last as the pipe convention wants.

`+modBy(divisor, n)+` is the modulo counterpart of that split: it is floored modulo (the result takes the sign of the divisor, unlike the truncating `+remainder+`, so `+Int.modBy(12, -1)+` is `+11+`), and a zero divisor *aborts* like `+/+` rather than returning a case. Its result is therefore a plain `+Int+`, which reads cleanly in an invariant — `+data Box = Int invariant Int.modBy(12, value) == 0+`. The divisor is the first argument (subject last, the pipe convention). Use `+remainder+` when a zero divisor must be a business case instead of an abort.

[#stdlib-decimal]
=== Decimal

[,text]
----
add  subtract  multiply  divide  compare  fromInt  toInt  round
abs  min  max  clamp
----

Division makes the rounding scale and mode explicit as arguments. `+Decimal.divide(a, b, 2, HALF_UP)+` rounds HALF_UP at 2 decimal places. The mode is an ordinary value of the data core declares:

[,text]
----
data RoundingMode = HALF_UP | HALF_EVEN | HALF_DOWN | UP | DOWN | CEILING | FLOOR
----

A mode argument is evaluated like any other, so a policy can be stated once and passed by name, chosen by an `+if+` or a `+match+`, or computed by a helper, and the three operations taking one are ordinary functions that can be handed over by name (<<blocks>>). The cases are unit data and follow the unit-data rules (<<unit-data>>): written bare, shadowable by a binding. The type provides no codec, so it cannot appear where one is required — a field of it, an example fixture over it — and this is intentional: a rounding policy is a computation's input, not a value that crosses a serialization boundary.

The cases correspond to `+java.math.RoundingMode+`. `+Decimal.divide(a, b)+` without scale and mode cannot be written — to surface rounding as a domain decision, the same position as "scale is incidental" in <<primitives>>. Division by zero returns `+Decimal | DivisionByZero+`, opened by `+| Decimal as d+` (<<primitive-arm>>).

`+Int+` and `+Decimal+` meet only where the conversion is written. `+Decimal.fromInt(n)+` widens an `+Int+`; it is exact, so nothing has to be stated. `+Decimal.toInt(d, mode)+` narrows back, and because that drops a fraction it names the rounding at the call, as `+divide+` does. There is no implicit widening: an arithmetic operator takes two operands of one type (<<primitives>>), so a rate applied to an amount in yen reads `+Decimal.fromInt(netAmount) * taxRate+` — the conversion sits where the value stops being an amount. A `+Decimal+` too large for an `+Int+` aborts, as an `+Int+` overflow does (<<primitives>>).

`+Decimal.round(d, scale, mode)+` sets the number of decimal places, naming the rounding at the call as `+divide+` and `+toInt+` do. Unlike `+toInt+` the result stays a `+Decimal+`, so it is how a value is prepared for `+String.fromDecimal+` (<<stdlib-string>>), which keeps whatever scale the value carries: a rate of `+0.10m+` times `+100.0m+` is `+10.000m+`, and `+round(…, 0, HALF_UP)+` is what makes it read as `+"10"+`. The subject comes first here, as it does for `+divide+` and `+toInt+`, so the mode reads last at every rounding call.

`+abs+` / `+min+` / `+max+` / `+clamp+` are the same `+Basics+` arithmetic `+Int+` carries (<<stdlib-int>>), on the same reasoning: `+<+` and `+-+` are defined for `+Decimal+`, so these are ordinary core `+let+`s. `+abs+` compares against `+0.0m+`, so a value whose scale differs still answers by numeric value, as `+compare+` does. `+clamp+` answers one of the three values written, never a re-scaled copy.

The four operations may also be written with the operators `{plus}` `+-+` `+*+` `+/+`. The operator `+/+` divides with a default rounding — significant digits (about 29) and HALF_UP — so `+10m / 3m+` is `+3.3333…+` and does not abort. Division by zero *aborts*. To make rounding an explicit domain decision, or to receive division by zero as a case, use the function `+Decimal.divide(a, b, scale, mode)+`.

[#stdlib-list]
=== List

==== Construction

A list is made by a literal or a guard comprehension.

[,text]
----
[e1, e2, ...]         // literal. One or more elements
[<element> | <condition>, ...]     // guard comprehension. One element if all conditions hold, empty otherwise
----

An empty literal `+[]+` may also be written. It has no element type of its own; its type is decided by context — the counterpart of `{plus}{plus}`, the other branch of an `+if+` / `+match+`, the seed a `+fold+` grows, or a `+List<T>+` a field or return value requires. An empty list does not depend on elements at runtime, so this is always sound. To transcribe a DSL bullet list, a guard comprehension (empty if the condition is false) is natural.

`{plus}{plus}` is concatenation. Both sides MUST be two lists or two strings: two lists give a list, two strings give a string (`+"a" {plus}{plus} "b"+` is `+"ab"+`, the operator form of `+String.append+`; <<stdlib-string>>). A mixed pair (a list and a string, or either with a non-list non-string) is a type error.

The element type is folded if the same, and widened to a sum of cases if different data (the same direction as <<sum-data>>).

[,text]
----
[HighValueTravel { threshold = threshold }] ++ [ClientCost]      // List<HighValueTravel | ClientCost>
----

Guard comprehension and `{plus}{plus}` exist to transcribe conditions the spec DSL listed as bullets.

[,text]
----
// the spec DSL (chapter 10) lists reasons as bullets:
//   reason 1: estimatedCost is at least 100,000 yen / reason 2: applicant is Staff / reason 3: cost borne by the other party
   [HighValueTravel { threshold = threshold } | estimatedCost.value >= threshold.value]
++ [InsufficientAuthority { value = applicant.rank } | isStaff(applicant)]
++ [ClientCost                 | isClientBorne(costBearer)]
----

Each reason makes a 0- or 1-element list and concatenates. *One DSL bullet line becomes one Souther line.* The result is `+List<HighValueTravel | InsufficientAuthority | ClientCost>+`, matching the three cases of `+PreApprovalReason+`. A unit data is constructed by name alone (<<unit-data>>), so `+ClientCost+` is written directly.

Note that `+applicant.rank == Staff+` cannot be written as a condition. `+==+` works only between the same type (<<primitives>>), and `+Rank+` and its case `+Staff+` are different types. Case judgment is done with `+match+`, and to make it a predicate wrap it in a helper `+let+` (the `+isStaff+` above). Ordering (`+>=+`) exists only for `+Int+` / `+String+` / `+Decimal+` / `+Date+` / `+DateTime+`, so compare `+.value+`, not `+Amount+` (a newtype) directly.

==== Operations

[,text]
----
map  filter  fold  foldr  all  any  length  get  indexedMap
reverse  member  sum  product  concat  concatMap  isEmpty  sort  range
distinct  partition  groupBy  indexBy  filterMap  max  min  find  sortBy  allUniqueBy
take  drop  zip  unzip
----

All are called through the qualifier `+List+` (<<stdlib>>). `+List.get+` returns `+Option<T>+`. `+List.map+` / `+List.filter+` / `+List.fold+` / `+List.all+` / `+List.any+` / `+List.indexedMap+` take a block (<<blocks>>). Import them as `+import List (map, all )+` to write unqualified thereafter.

`+range(from, to)+` is the consecutive integers from `+from+` to `+to+`, both ends included; `+from+` above `+to+` gives the empty list, and a span longer than a list can hold *aborts* before the walk starts rather than filling memory until it dies. It is the one list that is neither written out nor read from outside, so a walk over positions — the levels of a bay, the digits of a code — has something to walk. Like `+reverse+` and `+sort+` it is a primitive: building it from `+fold+` would need a list to fold over in the first place.

`+concatMap(f, xs)+` maps each element to a list and joins the results in one pass; writing it as `+map+` then `+concat+` builds an intermediate `+List<List<'b>>+`, which is why the shape is otherwise hand-rolled as a fold with `{plus}{plus}` in the step. `+foldr(step, seed, xs)+` walks from the end, and is the left fold over the reversed list.

`+zip(xs, ys)+` pairs two lists element by element and `+unzip(ps)+` takes the pairs apart again. A length mismatch truncates to the shorter list rather than aborting. Souther has tuples, so a two-list map is written `+zip(xs, ys) |> map(f)+`. The tuples stay inside the behavior — a tuple has no external form (<<tuple>>).

[,text]
----
import List ( map, all )

map(x -> fixLine(x), xs)
all(r -> isMinor(r), reasons)
----

If an injected thing is called from within a block, its requirement appears in the enclosing behavior's `+depends on+` (<<depends-on>>).

None of these is a compiler primitive. `+List.fold+` is a recursive `+let+` in `+souther.list+`: it walks the list with `+List.get+`, threads an accumulator, and takes its step as a function value (<<blocks>>). Its tail-recursive self-call is compiled to a loop, so it reads as a loop would (<<stdlib>>). `+map+` / `+filter+` / `+all+` / `+any+` are `+let+`s derived from it, expanded at the call site: `+map+` / `+filter+` seed with an empty list `+[]+` and grow it, `+all+` / `+any+` fold a `+Bool+`. `+indexedMap(f, xs)+` is `+map+` that also hands `+f+` the element's 0-based index: `+fold+` carries no index, so it threads one in a pair accumulator `+(i, ys)+` and drops the counter at the end — the caller writes a weighted sum or positional transform (`+indexedMap((i, c) -> w(i) * d(c)) |> sum+`) without hand-rolling that `+(i, acc)+` fold. `+List.length+` / `+String.length+` and `+List.get+` / `+Map.get+` are separate module functions, reached by their qualifier.

In the lower row, `+concat+` folds with `{plus}{plus}` and flattens nesting, `+member+` folds with `+==+` so it works for comparable elements, and `+isEmpty+` looks at length. `+sort+`, `+reverse+`, `+sum+` and `+product+` are primitives. Self-language sorting needs, besides comparison, a place to hold intermediate results, which `+fold+` does not give; `+sort+` sorts by the element's natural order.

`+sum(xs)+` / `+product(xs)+` answer the total and the running product of a list of numbers. The element MUST be `+Int+` or `+Decimal+` — the two types arithmetic is defined for (<<stdlib-int>>, <<stdlib-decimal>>) — and the answer has the element's type. A newtype over one of them is not a numeric element: it declares no addition and no zero of its own, so a list of them is summed by mapping to the wrapped value first (`+sum(map(h -> h.value, hours))+`). They are primitives rather than folds because a fold written in the language would have to write its seed, and a written seed is `+0+` or `+0.0m+` — one of the two types, never both. Over the empty list the answer is that seed (`+sum([]) == 0+`, `+product([]) == 1+`, as in Elm), and which of the two comes from the position the call is written in — the field it fills, the annotated binding it feeds, the declared output it returns. A `+?+` field asks for the value it wraps rather than for an optional (<<optional>>), so it says which as a plain field does. Written where nothing states a type, it is a compile error rather than a default: choosing `+Int+` there would make a numeric-default rule out of one library function, and the annotation says what the domain meant. Written where the position states some other type, it is a type mismatch — nothing about the element is unknown, and what is wrong is that a sum does not go there. Elements MUST be an ordered value — one of the ordered types (`+Int+` / `+String+` / `+Decimal+` / `+Date+` / `+DateTime+`; <<primitives>>), a single-value newtype over one, which is ordered by the value it wraps (<<primitives>>) and carries that ordering on the JVM (<<jvm-product>>), or an enumeration, ordered by its declaration (<<primitives>>). Passing a list of product data to `+sort+` is a compile error (a product has no ordering, so it is rejected up front rather than at runtime; to sort them, map to an ordered field first with `+List.map+`, or order by that field with `+sortBy+`).

The third row adds more list operations. `+distinct+` keeps the first occurrence of each element and drops later duplicates, folding a `+Set+` of what it has seen; `+partition+` splits into `+(kept, rest)+` by a predicate; `+groupBy+` buckets elements into a `+Map<'k, List<'a>>+` by a key; `+indexBy(key, xs)+` keys them one entry each into a `+Map<'k, 'a>+`, which is how a list of rows read from outside becomes something a caller looks up by key instead of scanning per lookup — two elements with the same key collapse and the later wins, as `+Map.fromList+` does, so state the key's uniqueness with `+allUniqueBy+` when it matters. `+filterMap(f, xs)+` maps and drops in one pass: `+f+` answers with an optional and only what is there joins the result, which is how an optional field becomes a plain list (`+filterMap(i -> i.assignee, issues)+`) without a stand-in value to filter on afterwards. Its step is the one stdlib signature that writes an optional as a type, `+('a) -> 'b?+` (<<algebraic-types>>). These five are self-language `+let+`s that grow their result from within `+List.fold+`. `+max+` / `+min+` return the largest / smallest as an `+Option+` — `+None+` on an empty list — and compare by natural order, so like `+sort+` the element MUST be ordered; `+find+` returns the first element satisfying a predicate as an `+Option+`. `+sortBy(key, xs)+` orders by a projected ordered key rather than the element itself: unlike `+sort+`, whose comparison is built in, its key is a runtime function value, so the sort carries an actual `+Fn+`. It is stable, so ordering by two keys is a sort by the secondary key followed by one by the primary; a key MUST be a single ordered value, not a tuple. `+max+` / `+min+` / `+find+` / `+sortBy+` are primitives (they step outside `+fold+`); there is no `+head+` — a domain reads the first element with `+List.get(0, xs)+`. `+allUniqueBy(key, xs)+` holds when the elements have distinct keys under `+key+`: the "this projection is a unique id" invariant, written as `+distinct+` of the projected keys compared against the length rather than by hand. Deriving from `+fold+` (through `+map+` / `+distinct+`), it may stand in an invariant, like `+distinct+` itself.

`+take(n, xs)+` keeps the first `+n+` elements and `+drop(n, xs)+` skips them — the top-N of a ranking and the rest of it. Both clamp instead of failing: a count of 0 or less takes nothing / drops nothing, and a count past the end takes the whole list / leaves it empty. Like `+indexedMap+` they thread a pair accumulator `+(i, ys)+` through `+List.fold+` and keep the elements whose index falls on the wanted side of `+n+`.

[#stdlib-map]
=== Map

A `+Map+` is immutable and string-keyed (<<collections>>). The accessors read; the building operations return a fresh map.

[,text]
----
get  containsKey  keys  values                   // read
empty  singleton  insert  remove  isEmpty  size  // build
toList  fromList                                 // convert to / from entry tuples
fold  map  filter  update  upsert                // higher-order
union  intersect  difference                     // key algebra
----

`+get+` returns `+Option<V>+`. `+empty+` is the empty map: like the empty list `+[]+`, its key and value types are fixed by context (a field or return position, a written binding type, the other branch of an `+if+` / `+match+`, or the first `+insert+`), so it is a *value* and not a function — written `+Map.empty+`, never `+Map.empty()+` (<<fn-declaration>>). `+singleton(k, v)+` is a one-entry map; `+insert(k, v, m)+` adds an entry or overwrites the existing one; `+remove(k, m)+` drops one, leaving `+m+` unchanged when the key is absent. Because a `+Map+` is immutable, `+insert+` / `+remove+` return a new map rather than mutating. `+size+` is the entry count and `+isEmpty+` whether there are none. The map operated on is last (<<pipe>>), so `+m |> Map.insert(k, v)+` reads left to right.

`+toList(m)+` is the entries as a `+List<(String, V)>+` — a list of key/value tuples in the map's iteration order — and `+fromList(entries)+` builds a map back (a later entry wins on a duplicate key). Iteration order is a deterministic, implementation-defined hash order (not insertion order): the same set of keys always yields the same order, so encoding is reproducible, but a program must not depend on which order that is. The tuple type in these signatures is allowed because a signature is not a codec boundary (<<tuple>>).

`+fold+` / `+map+` / `+update+` are the operations that take a step function. `+Map.fold(step, seed, m)+` is layered on `+List.fold+` over the entries (`+toList+`) rather than walking the map itself, and the entries combine in the map's deterministic hash order. Its step is `+(acc, key, value)+`. `+map(f, m)+` keeps the keys and rewrites the values (`+(key, value) -> value+`), growing a fresh map through `+fold+`. `+update(key, f, m)+` rewrites the value under one key with `+f+` and is a no-op when the key is absent. Its step is `+('a) -> 'a+`: `+Option+` is not surface-writable, so a step cannot return one — insert a new key with `+insert+`, drop one with `+remove+`, and let `+update+` cover changing what is already there. `+upsert(key, default, f, m)+` collapses insert-if-absent / modify-if-present into one call: it applies `+f+` to a present key's value and inserts `+default+` for an absent one. Like `+update+` it keeps `+Option+` internal — the absent branch takes a plain value (`+default+`). Typical use is accumulation, e.g. counting `+upsert(k, 1, n -> n {plus} 1, m)+`. `+filter(keep, m)+` keeps the entries its `+(key, value) -> Bool+` predicate holds for, growing a fresh map through `+fold+` as `+map+` does — without it a caller goes out through `+toList+`, filters as a list, and comes back through `+fromList+`, leaving the map type behind for two steps.

`+union+` / `+intersect+` / `+difference+` are the key algebra, named as `+Set+`'s are (<<stdlib-set>>). All three answer with entries taken from `+a+`: `+union(a, b)+` adds `+b+`'s entries under keys `+a+` does not have, so `+a+` wins a collision; `+intersect(a, b)+` keeps `+a+`'s entries whose key is also in `+b+`; `+difference(a, b)+` keeps `+a+`'s entries whose key is not. Values from `+b+` are never merged into `+a+`'s — combining two values under one key is a domain decision, so it is written with `+fold+` and `+upsert+` where that rule lives.

[#stdlib-option]
=== Option

`+List.get+` / `+Map.get+` / `+List.find+` and a `+T?+` field all yield an `+Option+` (<<algebraic-types>>). Before this module the only way to read one was a two-arm `+match+`, which ends the value pipe (<<pipe>>); these functions let the optional flow through `+|>+` instead.

[,text]
----
map  withDefault
----

`+withDefault(default, opt)+` reads the option: the wrapped value when present, `+default+` when absent. `+map(f, opt)+` transforms a present value with `+f+` and leaves an absent one absent, so its result is again an `+Option+`; `+f+` is a plain `+('a) -> 'b+` and never sees the absent case. Both take the option last (<<pipe>>), so it threads through the pipe: `+Map.get(k, m) |> Option.map(v -> v.value) |> Option.withDefault("None")+`.

`+Option+` stays non-surface: the caller never writes `+Option<T>+` nor builds a `+Some+` — the optional is inferred and unnamed as it flows here, and `+map+`'s result stays inferred as it reaches `+withDefault+`. There is no `+andThen+`: its step would have to return an `+Option+`, which no user function can build under that rule (insert-if-present style folding stays with `+Map.upsert+` / `+update+`, which keep `+Option+` internal). For the same reason `+map+` cannot be self-hosted — a body cannot construct a `+Some+` — so it is a compiler built-in, while `+withDefault+`, which only reads, is an ordinary helper.

[#stdlib-set]
=== Set

A `+Set<'a>+` is unordered with no duplicates, compared by value equality (<<collections>>). It is immutable, so the building operations return a fresh set.

[,text]
----
empty  singleton  insert  remove  contains       // build / query
union  intersect  difference                      // algebra
isEmpty  size  toList  fromList                   // convert
fold  map  filter  partition                      // higher-order
----

`+empty+` is the empty set — like `+[]+` and `+Map.empty+`, its element type is fixed by context (a field or return position, a written binding type, the other branch of an `+if+` / `+match+`, or the first `+insert+`), so it is a *value* and not a function — written `+Set.empty+`, never `+Set.empty()+`. `+singleton(v)+` is a one-element set; `+insert(v, s)+` adds `+v+`; `+remove(v, s)+` drops it (leaving `+s+` unchanged when absent); `+contains(v, s)+` tests membership. `+union+` / `+intersect+` / `+difference(a, b)+` are the set algebra (`+difference+` is `+a+` minus `+b+`). `+toList(s)+` lists the members in a deterministic, implementation-defined hash order (not first-seen order; the same members always list in the same order, so it is reproducible, but a program must not depend on which order that is) and `+fromList(xs)+` builds a set, dropping duplicates. The set operated on is last (<<pipe>>), so `+s |> Set.insert(x)+` reads left to right.

`+fold+` / `+map+` / `+filter+` / `+partition+` are the operations that take a step function. As with `+Map+`, a `+Set+` adds no loop of its own: each one goes out through `+toList+`, uses the `+List+` combinator, and comes back through `+fromList+`, so `+List.fold+` stays the single primitive. `+map+` may shrink the set — two elements that land on the same image collapse, since a set holds no duplicates — and `+partition(keep, s)+` answers the pair `+(kept, rest)+`, the shape `+List.partition+` gives. `+fold+` runs over `+toList+`'s order, which is deterministic but unspecified, so a step whose result depends on that order is a mistake the compiler cannot catch: combine with something associative and commutative.

A `+Set+` field decodes from a JSON array and deduplicates it; it encodes back to an array in that deterministic hash order (reproducible for the same members, but not the input order).

[#stdlib-bool]
=== Bool

[,text]
----
not
----

`+not+` is the *first self-host function* placed in `+souther.bool+`. It is not a primitive but written in Souther as `+let not (b: Bool) = if b then false else true+`, called qualified as `+Bool.not+` (bare via `+import Bool (not )+`). Being non-recursive, it is inline-expanded at the call site and no dedicated class is generated. Negation is written with this `+not+` — there is no prefix `+!+` operator (redundant, since `+not+` exists).

[#stdlib-date]
=== Date

[,text]
----
addDays  addMonths  addYears  daysBetween  year  month  day
----

[#temporal-literal]
A date is written `+Date("2026-07-25")+` and a date-time `+DateTime("2026-07-25T09:00")+`. The argument MUST be a written string: the compiler parses it where it stands, so a malformed date fails the build rather than a run, and an `+example+` fixture — which holds only written values (<<example-evaluable>>) — can carry a date at all. A computed date comes from the boundary or from the arithmetic below, not from this form.

`+Date+` is a local calendar date (<<primitives>>). Calendar arithmetic is pure and belongs in the domain, not behind an injected behavior (<<injected-behavior>>) — only reading the *current* date needs the outside world. `+addDays(n, d)+` / `+addMonths(n, d)+` / `+addYears(n, d)+` shift `+d+` by `+n+` units (`+n+` may be negative), following `+java.time.LocalDate+`, which clamps the end of a month (`+addMonths(1, 2026-01-31)+` is `+2026-02-28+`). `+daysBetween(from, to)+` is the whole days from `+from+` to `+to+`, negative when `+to+` precedes `+from+`. The date operated on is last (<<pipe>>), so `+d |> Date.addDays(3)+` reads left to right.

`+year(d)+` / `+month(d)+` / `+day(d)+` read a date's parts as `+Int+`s — the month 1 to 12, the day 1 to 31. `+year+` / `+month+` / `+day+` all answer `+Int+`: `+addMonths+` counts in months, and a named month would have to be converted back before adding one. There is no `+dayOfWeek+`: neither language answers that with a bare number, so it needs a named seven-case type.

A month boundary follows from `+day+` and belongs in the domain:

[,text]
----
let monthStart (d: Date): Date = Date.addDays(1 - Date.day(d), d)
let endOfMonth (d: Date): Date = Date.addDays(0 - 1, Date.addMonths(1, monthStart(d)))
----

[#stdlib-datetime]
=== DateTime

[,text]
----
addMinutes  addHours  addDays  minutesBetween  toDate
----

`+DateTime+` is a local date-time with no zone (<<primitives>>); the zone stays a boundary concern. `+addMinutes+` / `+addHours+` / `+addDays+` shift by their unit; `+minutesBetween(from, to)+` is the whole minutes between (negative when `+to+` precedes `+from+`); `+toDate(dt)+` drops the time of day, yielding a `+Date+`. As with `+Date+`, the date-time operated on is last (<<pipe>>).

Decoders and Encoders do not appear in Souther's syntax. Derived from a data's shape, they are generated by the ClassFile backend as Raoh Decoders / Encoders (<<codec-generation>>, <<encoder>>). Primitive parsing, error accumulation, discriminator dispatch, and encoding are handled by Raoh combinators; there is no facade on the souther-runtime side. A custom boundary codec (<<custom-codec>>) uses Raoh directly from the Java side.

[#jvm-output]
== JVM output

[#target-jdk]
=== Target JDK

The artifacts target Java 25 or later, which is also what the compiler is built and run on. Unicode identifiers are generated to conform to Java's identifier rules (escaping / romanization, if needed, is the backend's responsibility).

The class-file version of the generated `+.class+` is fixed at Java 25 (major 69). It MUST NOT be left to the default of the JDK running the backend: pinning is what makes the floor a decision rather than a property of whichever JDK ran the build. souther-runtime is on the artifact side and is compiled to the same target.

[#jvm-nullness]
=== Nullness

No generated value is ever null. Absence is `+Option+` (<<optional>>), a failure is a case of the output union (<<unmarked-sum>>), and a collection holds neither a null key nor a null value — so no accessor, factory, codec or `+apply+` hands one back.

Every generated class carries JSpecify's `+@NullMarked+`, and souther-runtime carries it on its own packages, so a consumer's compiler knows that too. It matters most where a compiler acts on it: Kotlin reads the annotation off the class file and types what it names as non-null, where without it the type is a platform type and a null check is neither required nor possible. The annotation is read by name, so the JSpecify jar need not be on the consumer's classpath.

A record's component accessor is the exception. Kotlin types it from the record component and reaches it without applying the class's marking, so a component read would be a platform type again while every other member of the same class is not. Each accessor therefore says `+@NonNull+` on its return type itself, at every position of it — the `+List+` and the element it holds — and the `+Record+` component repeats it, for a reader that goes through reflection rather than the accessor. A primitive return (an `+Int+` accessor returns `+long+`) states nothing, having no nullness to state.

It rides on each class rather than on a `+package-info+` of the module's package. That package is where a consumer's own `+package-info.java+` sits, and a generated class of the same name would lose to that declaration — the marking would then reach only the modules that own no Java of their own.

A generated method whose descriptor names a generic type carries the `+Signature+` for it, so the type argument survives to a reader. `+__construct+` returns `+Result<T, String>+`; a raw `+Result+` would be a platform type again on the Kotlin side, where the class carrying it says everything else is not.

The few places that do admit a null are annotated one by one — a `+java.util.Map+` implementation's `+get+`, which returns null for an absent key because that interface says so.

[#jvm-product]
=== Product data

Generated as a record: a final class extending `+java.lang.Record+` whose `+Record+` attribute names its fields as components, in declaration order, with a non-public canonical constructor. Fields taken in by a `+...+` spread are laid flatly in the generated class.

[,text]
----
public final class Submitted extends java.lang.Record {
    private final Employee applicant;         // from ...TravelRequestCommon
    private final Amount estimatedCost;       // from ...TravelRequestCommon
    // ...
    private final LocalDateTime submittedAt;

    Submitted(...) { ... }                    // canonical, package-private

    public Employee applicant() { ... }       // one accessor per component
    public String toString() { ... }          // Submitted[applicant=..., ...]
}
----

Being a record is what a reader acts on without being told anything about Souther. javac deconstructs the value in a record pattern, and does so for a case of a sum in an exhaustive `+switch+` — the same way it reads the runtime's `+Ok+` / `+Err+`, which are records too. Kotlin reads each component as a property, so `+issue.id.value+` is written instead of `+issue.id().value()+`; without the `+Record+` attribute Kotlin resolves the backing field instead and reports that it cannot be accessed, naming a field where the accessor was meant.

Every data gets a public read accessor per field (<<field-visibility>>), so an exposed one is readable from another module and from Java; because module = package, package-private cannot read across the boundary. A data the module keeps to itself has accessors too — a component is read through its accessor, and the generated code of the module reads a field the same way — but its class is package-private, so nothing outside can call them. The constructor stays non-public either way, so a value can be read but not constructed.

`+toString+` prints the record form, `+Submitted[applicant=..., estimatedCost=...]+`. It is generated rather than inherited: `+java.lang.Record+` declares it abstract, so a class without one would throw `+AbstractMethodError+` when anything printed the value. `+equals+` / `+hashCode+` are generated over the components as well, and compare a `+Decimal+` by value rather than by scale (<<primitives>>) — a record's shape does not dictate what equality means.

A field MUST NOT be named after a no-argument method of `+Object+` (`+toString+`, `+hashCode+`, `+getClass+`, `+clone+`, `+finalize+`, `+notify+`, `+notifyAll+`, `+wait+`): the accessor would collide with a method the class already has. It is a compile error where the field is written, as a record component of that name is in Java. `+equals+` is not among them — `+equals()+` and `+equals(Object)+` are different methods — and is allowed, as Java allows it as a component name.

A framework that constructs records reflectively — Jackson, given a generated type as a request body — can reach the canonical constructor and build a value without passing the invariant `+__construct+` runs. Construction authority is governed by declaration rather than by visibility, and the same value was already reachable through `+setAccessible+`; what is guaranteed is what a decoder admits (<<decoder>>), not what reflection cannot forge.

A single-value newtype over an ordered type implements `+Comparable+` against itself, comparing the value it wraps. That is what `+sort+` / `+max+` / `+min+` / `+sortBy+` compare by, and it makes the type usable as a `+TreeMap+` key or a `+Collections.sort+` element from Java. A newtype over an unordered type (`+Bool+`) and a product data get no `+Comparable+`.

[#jvm-collection-equality]
=== A collection's equality, seen from Java

A generated data, a newtype and a tuple compare with their own kind and nothing else, so their `+equals+` is the language's value equality (<<equality>>) and a Java reader sees exactly what Souther means.

A `+List+`, a `+Set+` and a `+Map+` implement the JDK interfaces of those names, and a foreign implementation may be on the other side of an `+equals+`. A `+List+` therefore keeps the `+List+` contract — elements compared by their own `+equals+` — because a list that compared them by value equality would be equal to a JDK list that was not equal back. The language's question is answered by a separate pair of methods the runtime calls.

Reading one is not comparing two. `+Map.get+`, `+Map.containsKey+` and `+Set.member+` read the collection they are given by the index it carries: every collection Souther builds is indexed by value equality, and so is the `+Set+` a field decodes into. A `+Map+` a field decodes into is a JDK map, and a boundary map's key is a `+String+`, a String-backed newtype, a temporal or an enumeration (<<collections>>) — for each of those the two agree. A `+java.util.Map+` handed in from Java with some other key is answered by its own index. Comparing two collections normalizes both first, since Java's equality is finer and a foreign collection may hold two elements the language calls one.

A `+Set+` and a `+Map+` cannot do both. Which element a set holds and which key a map finds is decided by the hash the trie is indexed by, and there is one index, not two: `+contains+` and `+get+` answer the language's question, and `+equals+` and `+hashCode+` follow them rather than the elements' own. Against a foreign `+java.util.Set+` holding the same `+Decimal+` at another scale, `+equals+` is therefore not symmetric. Only Java interop can build that pair — a set Souther built is compared with a set Souther built — and the alternative would be a set whose `+contains+` found an element and whose hash said it was not there.

[#jvm-sum]
=== Sum data

Generated as a sealed interface and final implementation classes. If a case is a named data, its final record class implements the sealed interface. A unit data is generated as a record with no components, holding its one value in a shared instance — so a Java `+switch+` deconstructs it as `+case Approved()+` next to the product cases (<<jvm-product>>).

A field every case spreads (<<sum-data>>) is declared on the sealed interface as an abstract accessor, which each case record's accessor of the same name implements. Java reads it off the sum the same way Souther does, without a `+switch+`.

A case may itself be a sum (<<sum-data>>), and then its interface extends the outer one. Only that one step is emitted: interface inheritance carries the rest, so a leaf is a value of every sum above it without being named in any of them. The relation has to exist because the rest of the language already reads it that way — the checker folds a nested sum to its leaves to judge a case, and the derived codec dispatches over those same leaves, so a decoder hands back a leaf where the outer sum is what was asked for.

[#jvm-codec]
=== Decoder / Encoder

An exposed data gets a per-source acquisition API. What is returned is a Raoh Decoder / Encoder (`+Decoder<I, T>+` is `+I -> Result<T>+`).

[,text]
----
public static Decoder<Map<String,Object>, TravelRequest> decoder()      // Map (raoh-core; a newtype is Decoder<Object,T>)
public static Decoder<JsonNode, TravelRequest> jsonDecoder()            // JSON (raoh-json)
public static Decoder<Record, TravelRequest> recordDecoder()            // DB row (raoh-jooq)
public static Encoder<TravelRequest, Map<String,Object>> encoder()      // object/sum -> Map (JSON via valueToTree at the boundary)
// newtype encodes to a bare scalar. e.g. MemberId.encoder() : Encoder<MemberId, String>
----

The concrete implementation is generated directly as bytecode by the ClassFile backend from Raoh combinators (<<codec-generation>>). souther-runtime does not depend on Raoh; the Raoh dependency is on the generated code and the app side. `+jsonDecoder()+` / `+recordDecoder()+` are generated only when the data's shape supports it (<<codec-generation>>; JSON for a shape without temporal, `+Record+` for a flat shape). `+decoder()+` (bare values / Map) is always generated.

[#jvm-behavior]
=== behavior

A fn- or `+>->+`-implemented behavior is generated as a public interface named after the behavior (first letter capitalized), with the implementation in a `+<BehaviorName>$Impl+` class. Java declares the behavior by the interface name and never names the implementation. A single-input behavior's interface extends `+Behavior<In, Out>+` (so it composes with `+>->+` and its `+apply+` is typed by inheritance); an interface for any other input count is standalone and declares the typed `+apply+` directly — `+apply(A, B, …)+` for several inputs, `+apply()+` for none. The interface carries a static factory: `+of()+` for a behavior with an empty requirement set, or `+bind(...)+` taking one implementation per requirement.

[,text]
----
var handle = Handle.bind(new JdbcFindMember(dataSource));   // Handle is the interface; bind builds Handle$Impl
----

An injected behavior (a `+behavior+` with no `+let+`) is instead an abstract class the Java implementation extends (<<java-base-class>>), not an interface.

The generated names are derived from the behavior name (first letter capitalized). Because a data name already starts with a capital, a behavior `+quote+` becomes a type `+Quote+`, colliding with a `+data Quote+` in the same module. This is a compile error; rename one to distinguish them.

[#jvm-construction-privacy]
=== Preventing exposure of construction authority

A data's constructor is non-public (package-private): nothing reaches the fields without the invariant. The checked entry `+__construct+` is public for an exposed data and non-public otherwise, so a construction declared in another module (<<closed-construction>>) has the path its declaration names, and a data a module keeps to itself has none. The Java implementation of a behavior with no implementation extends the generated abstract base class (<<java-base-class>>) and constructs failure cases via the base's `+protected+` factories; it may be placed outside the generated package.

What is guaranteed to Java is that no unvalidated value can be created — not that no value can be created. `+decoder()+` is public API (<<jvm-codec>>) and `+__construct+` is public for an exposed data, so Java may build one at any time; the invariant is checked on both paths (<<invariant-on-construct>>), a decode violation becoming a `+Result+` failure. A unit data ignores input and decodes (<<codec-generation>>), so its `+decoder()+` lets anyone construct it — but a unit data has nothing to validate.

Reflection, Unsafe, and bytecode manipulation are out of scope for guarantees.

[#jvm-abort]
=== Abort on invariant violation

An invariant violation inside the domain (<<algebraic-types>>, <<violation-destination>>) appears in generated code as throwing `+souther.runtime.ConstraintViolation+`. It carries the broken data name and the invariant's location.

Souther code cannot catch this. There is no catching syntax, so it cannot control business flow (<<out-of-scope>>). The boundary Java can catch it, but handles it as distinct from a business failure. A business failure arrives as an output case (<<unmarked-sum>>) and maps to 400; an abort is a model bug and maps to 500.

A decode violation is not this; it returns as a Raoh `+Result+` failure (<<decoder-error>>).

[#jvm-anonymous-union]
=== A behavior output's anonymous union

When a behavior's output is an anonymous union (`+-> Member | NoSuchMember+`), a sealed interface representing that union is generated. Its name is the behavior's class name (first letter capitalized; <<jvm-behavior>>) plus `+Result+`, i.e. `+<BehaviorName>Result+`; `+permits+` lists the union's leaf cases, and each case data implements it. An anonymous union has no common supertype (<<asymmetric-interop>>), so this lets Java receive it as a single return type and exhaustively check with `+switch+`.

[,java]
----
// when findMember is -> Member | NoSuchMember
sealed interface FindMemberResult permits Member, NoSuchMember {}
// Member and NoSuchMember implement it; the injected behavior's abstract base FindMember implements Behavior<MemberId, FindMemberResult>
----

There are two cases where it is not generated. If the output is a named sum data, that is itself a sealed interface (<<jvm-sum>>) and is the return type. If the output is a single case, that case type is the return type.

One data type may appear in the output of multiple behaviors, so it may implement several `+<BehaviorName>Result+` at once. The output of a `+>->+` composition behavior (the folded sum of mainline and departed; <<type-routing>>) is also an anonymous union, generated by the same rule from the composition name.

`+<BehaviorName>Result+` takes a class name in this module, so it is subject to the rule every other name this module emits is subject to (<<bridge-case>>): a `+data BillResult+` beside a `+behavior bill+` whose output is a union is a compile error, and so is a `+behavior billResult+` beside it. Two result unions cannot collide with each other, their behaviors having already been refused for capitalizing into one class (<<jvm-behavior>>).

[#union-encoder]
The generated type carries an `+encoder()+` (<<jvm-codec>>) that dispatches its members by the discriminator `+"type"+`, like a sum over the same leaves (<<sum-discrimination>>). It has to: a member's own encoder writes no discriminator — only the union it sits in knows which member it is — so a behavior answering `+-> Member | NoSuchMember+` would otherwise put out a form nothing could tell apart. What each member writes is what <<sum-discrimination>> says a case of that shape writes. A member that is a product lays its fields flatly beside `+"type"+`; a unit writes `+"type"+` alone; a member whose own representation is not an object — a primitive, a newtype — goes under `+"value"+` beside it. A union every one of whose members is a unit data is an enumeration and travels as the member's name, a bare string, exactly as the named sum over those leaves does. A member reaching the union through a bridge case is read out of it first, so the bridge case appears in no external representation and still carries no codec of its own. A member declaring a field named `+"type"+` is refused, as a sum's case is (<<discriminator-field>>).

[,text]
----
// when bill is -> Issued | UnknownSku, and lengthOf is -> Int | NotFound
Issued { amount = 200 }  ->  {"amount":200,"type":"Issued"}
UnknownSku               ->  {"type":"UnknownSku"}
4                        ->  {"type":"Int","value":4}
----

There is no matching decode. An anonymous union is written only in an output (<<union-intersection>>), so nothing reads one back. A boundary that wants a case back reads it with that member's own decoder — from the object itself where the member laid its fields flatly, and from what is under `+"value"+` where it did not, since a newtype and a primitive read their representation bare (<<newtype>>).

[#bridge-case]
A case class receives the unions it belongs to when *its own* module is generated. A member this module declared therefore carries the interface itself. A primitive cannot — `+Int+` is `+java.lang.Long+`, the JDK's class — and neither can an imported type, whose class the module that declared it has already emitted; giving it an interface from here would make a module's bytecode a function of who imports it, the mirror of what ADR-0024 refuses. Such a member joins the union through a *bridge case*: a record of one component, `+value+`, that this module emits and that implements the union in the member's stead.

[,java]
----
// when owed is -> Yen | NothingOwed, with Yen imported from `up`
sealed interface OwedResult permits NothingOwed, YenCase {}
public record YenCase(up.Yen value) implements OwedResult {}
----

The bridge case is named `+<MemberName>Case+`, and there is one per member per module: it implements every `+<BehaviorName>Result+` of this module the member belongs to. That is the rule a local case class already follows — what differs between the two is not what membership means but which module owns a class it can be put on.

|===
| Member | Where its result-union membership sits

| a data this module declares | the case class itself
| a primitive, or an imported data | a bridge case this module emits
|===

A bridge case takes a class name in this module, so it is subject to the rule every other name this module emits is subject to: no two of them may be one class. `+YenCase+` is a name a model may well have declared, and so are `+IntCase+` and `+DateCase+`, so the collision is reported where it happens rather than the names reserved — a name nothing collides with stays available. Three ways to collide: with a data this module declares, with the class a behavior capitalizes into (<<jvm-behavior>>), and with another bridge case, which is two types of one spelling from two modules, members of two different unions of this module. Within one union the member-name rule (<<union-member>>) has already refused them.

A bridge case has no codec. Belonging to a union does not change a member's own external representation, so a consumer that has switched to a bridge case takes the value out and uses the codec the member itself carries (<<jvm-codec>>). A consumer that wants the answer as the union writes it asks the union instead (<<union-encoder>>), which is where the discriminator no member writes on itself comes from.

The bridge case is a JVM form. It is not a Souther type, it is not written in a `+match+` arm or an `+example+` row, and it does not appear in an external representation. What each side sees:

|===
| Where | What a value of the union is

| Souther source, a `+match+` binding, an `+example+` row | the member's own value
| the external representation | the member's own contents, decided by its Souther type, under the union's discriminator (<<union-encoder>>)
| a Java `+switch+` and the `+apply+` that returned it | the case class, or the bridge case for a member this module could not put the interface on
|===

The two forms meet at exactly two places. A behavior's return puts the Souther value it answers with into its declared union's JVM form; a call takes it back out before the result is used. Both walk the union's members, which are known where they are emitted, so neither asks a value whether it happens to be wrapped — and because everything between the two is a Souther value, nothing is ever put into a bridge case twice. Reading a value out and putting it back gives the value that was there.

The model author does not write this type name in Souther source; they only write `+-> Member | NoSuchMember+`. A Java consumer declares the behavior by its interface name (<<jvm-behavior>>) and calls `+apply+`, whose return type is `+<BehaviorName>Result+` by inheritance, then matches the cases with `+switch+` — so the consumer never writes the `+Result+` name either. It surfaces explicitly only in an injected behavior's Java implementation, which writes it as the `+apply+` return type (<<java-example>>).

[#compiler-pipeline]
== Compiler structure

[,text]
----
Source -> Lexer -> Parser -> AST
  -> Derive (fill decoder/encoder into the AST from a data's shape)
  -> Lower (behavior / let bodies: helper inlining, desugaring)
  -> Type Check -> Core IR (typed: the checker produces it as it types a body)
       name resolution / construction-authority check / requirement-set check and composition inference / exhaustiveness check / invariant type check
  -> ClassFile Backend -> .class (direct bytecode generation)
----

Behavior and `+let+` bodies are lowered — helper inlining and surface desugaring happen once here — and then typed. The type checker produces the Core IR as it types a body: every Core node carries the type decided for it, and the backend emits from that rather than inferring types a second time. Data definitions and derived decoders / encoders stay at the AST level, and their expressions are typed the same way where the backend emits them; there is no separate Domain IR / Decoder IR / Encoder IR. Type checking verifies construction authority, requirement sets, exhaustiveness, and invariants together: the surface checks read the AST, and the body check reads the lowered form. The backend generates `+.class+` with the Class-File API (`+java.lang.classfile+`) and does not go through javac.

[#ast-tracking]
== Information tracked by the AST and backend

Apart from the typed Core IR the type checker produces for behavior and `+let+` bodies (<<compiler-pipeline>>), the compiler keeps no separate intermediate representation; the following is held as the AST and the type-check results.

[#ast-nodes]
=== AST definition nodes

[,text]
----
Module  Data(ProductData)  SumData  UnitData  Include  Field  Invariant
DecoderDef  EncoderDef  SpecBehavior  PipeBehavior  FnDef  Import
Construct  FieldInit  Expression  Case  RawExpr  DecRef  Block
----

Behavior definition nodes are two, corresponding to the two right-hand sides of <<behavior>>. `+SpecBehavior+` holds only input type, output type, and `+constructs+`, with no body. If a same-named `+FnDef+` exists it is the implementation; otherwise it is subject to Java injection (<<injected-behavior>>). `+PipeBehavior+` holds the sequence of stage names. It is itself the implementation, so it takes no `+FnDef+` and is not injected; its type is computed from the stages (<<type-routing>>). Composition vs. simple is distinguished by these two nodes, so later stages need not re-read the right-hand side to tell them apart.

`+FnDef+` holds argument names and a body. If a same-named `+SpecBehavior+` exists the type comes from it; otherwise it is a helper `+let+` and holds its own argument types, except for a parameter its body determines (<<fn-declaration>>).

A `+SumData+` case holds only a reference to a named data (<<sum-data>>). A `+...+` spread inherits taken-in fields and invariants flatly. `+DecoderDef+` / `+EncoderDef+` are filled by derivation from a data's shape (<<decoder>>, <<encoder>>). `+guard+` and `+let+` are desugared, so they do not appear in the AST; they appear as an `+if+` and as block bindings (<<guard>>, <<block-expression>>).

[#ast-behavior-info]
=== Information tracked about a behavior

[,text]
----
input type  output type (sum of possible business results)  requirement set  construction authority (constructs)
----

The output type is a single type or a sum. `+SpecBehavior+` takes these four from the declaration — the requirement set is also taken from `+depends on+` and reconciled with the set inferred from the `+let+` (<<depends-on>>). `+PipeBehavior+` computes input and output types from the stage sequence (<<type-routing>>) and infers the requirement set as the union over stages (<<composition-with-requirements>>).

The body is not here. A behavior has no body; the `+FnDef+` holds it (<<behavior>>, <<ast-nodes>>). The backend combines this behavior-side information with the `+FnDef+`'s body, lowered to Core (<<compiler-pipeline>>), to generate bytecode.

[#compile-errors]
== Compile errors

A code (e.g. `+E1301+`) is the stable, locale-independent identity of an error; the title, message, and hints are prose shown in the selected locale. The catalogue below lists each code with the message and hint it states; the header, the quoted line and the caret described next are left out of the quotations.

An error is rendered from structured data, not a frozen string. The default (human) form is a titled report: a header naming the error and the source location, the offending line quoted with a caret under the token, found-vs-expected type blocks for a type mismatch, and any hints. An error that concerns more than one place — the two branches of a disagreeing `+if+`, the two sides of a failed composition — points at each with its own caret and label. A compile stops at the first error, except where a pass finds several independent ones at once: every failing `+example+` row is reported with its own position and reason, one report after another. `+--format json+` emits each diagnostic as a JSON object (code, source region, message, hints) for tools and agents, one per line; `+--lang+` selects the locale (Japanese by default, English available). The quoted line and caret are shown for a single-file compile.

[,text]

Hint: Where a `?` field is being given a value, write the value on its own.
Elsewhere an optional is only read — a `?` field, `Map.get`, `List.find` — never made.

[,text]

[#e1606]
=== A declared sum's case is imported

[,text]
----
`OutOfStock` is declared in `inventory`, so it cannot be a case of `ShipmentResult`.
Hint: A sum's cases are declared with it: the generated sum is a sealed interface, and
only its own module can implement it. Consume `OutOfStock` at the boundary, or re-express
it as a case of this module.
----

A `+data S = A | B+` declares a type this module owns and publishes. Its cases are its vocabulary, and they are written with it. A case from an imported module cannot be one of them: the generated sum is a sealed interface, the class the other module emitted cannot implement it, and the case would be permitted without being a member — no value satisfies the type and an exhaustive `+switch+` over it has no arms.

An anonymous output union takes an imported member (<<union-member>>), and the difference is not the JVM. A named sum introduces a type name: it is written in a parameter, in a field, in another sum. An anonymous union introduces none — it is the shape of one behavior's answer and nobody names it. Taking another context's type into a shape is answering with the value that context owns; taking it into a declared sum is making it a word of this module's own vocabulary, and that is what a bounded context does not do.

The move for a sum is to translate: match the imported result and return a case of this module. A module boundary is where another context's vocabulary is restated in this one's.

[,text]
----
// allocate is imported and OutOfStock is its departure; CannotAllocate is this module's answer to it
behavior allocateAndShip : (number: PartNumber) -> ShipmentOrder | CannotShip | CannotAllocate
    depends on instructShipment
    constructs CannotAllocate

let allocateAndShip (number, instructShipment) =
    match allocate(number) with
        | Allocated as allocation -> instructShipment(allocation)
        | OutOfStock as shortfall -> CannotAllocate { number = shortfall.number }
----

`+instructShipment+` is a behavior of this module and has a requirement of its own, so it is named in `+depends on+` and arrives bound (<<fn-rules>>): a composition builds its stages and their requirements accumulate into it, while a caller receives what it calls. An imported behavior is reached either way: it is called by name when its requirement set is empty, and named in `+depends on+` when the caller must supply what it requires.

[#e1607]
=== depends on does not name a dependency

[,text]
----
`behavior ship` declares `depends on allocate`, but `allocate` depends on nothing, so
there is nothing to inject.
Hint: Remove `allocate` from `depends on` and call it directly; a behavior that depends
on nothing is reached by name.
----

`+depends on+` names a behavior whose requirement set is not empty, declared here or imported (<<depends-on>>). A behavior that depends on nothing is E1607 — call it instead (<<calling-a-behavior>>) — and so is a `+>->+` composition, whose requirements are inferred from its stages rather than written, and so is a name that is no behavior in scope. All three are reported at the clause, where the name was written.

[#e1608]
=== A behavior reaches itself

[,text]
----

Hint: A behavior does not recurse, through calls, `depends on` or `>->` stages. Write the
recursion as a helper `let`, where it is proven total.

The cycle is reported wherever it closes, and the edges may be calls, `+depends on+`, `+>->+` stages, or a mixture of them (<<calling-a-behavior>>). A `+depends on+` cycle leaves nothing to build first, and a call cycle does not terminate. Recursion belongs to a named module helper, where it is proven total (<<fn-rules>>).

[#e1905]
=== Example does not hold

[,text]
----

found:    Submitted { submittedAt = "2026-07-20T09:00" }

----

Emitted when a row's evaluated result does not match the expected arm or value. Every failing row of a build is reported. Both sides are shown as values, encoded through the data's derived Encoder (<<encoder>>) — the arm name alone does not say what went wrong when a row fails inside one arm. A row that asserts only the arm (a bare case name, <<example-expected>>) shows just that name.

An `examples for` file holds examples, the fakes they run against and the values they

Emitted when a file that begins with `+examples for+` holds something other than an example, a `+fake+` table, or a value its rows name — and when a value it declares carries a name the target module already declares (<<example-placement>>). [#e1910]
=== An example does not terminate

[,text]
----
This example did not terminate (submitTravelRequest) — a `partial` recursion it reaches
may not stop. Make it structural, or reduce it.
----

Emitted when a row's evaluation exceeds the step budget the example runner holds it to. A helper proven total cannot reach this, so what a row reaches is a `+partial+` one (<<fn-rules>>).

[#e1911]
=== An example reached a point declared unreachable

[,text]
----
This row reached a point the model declares cannot arise: twenty insured years cannot
precede the age of thirty (42:17)
Hint: Either the row states a combination the model rules out, or the reason written at
that `unreachable` does not hold.
----

Emitted when a row's evaluation reaches an `+unreachable+` (<<unreachable>>). The reason the model wrote is shown with the line and column it was written at, because the row and the declaration are usually in different rules; the diagnostic's own place is the row's. It is not a failed comparison: the row produced no answer to compare, and what it found is a premise that does not hold.

[#e2001]
=== A recursive helper is not proven total

[,text]
----
Recursive helper `let depth` is not structurally recursive: it passes no argument that is
a strictly smaller part of a parameter. Recurse on a part obtained by `match` (a field or
a case), count with `fold`, or mark the helper `partial`.
----

Emitted when a helper's recursion is not shown to terminate by size-change analysis. A group of mutually recursive helpers is reported together, and a recursion too large for the analysis says so instead of guessing; `+partial+` is the opt-out in every case (<<fn-rules>>).

[#e2010]
=== A construction violates its invariant on a reachable path

[,text]
----

value the invariant rejects. Fix the value, or guard the path so the violating case cannot
reach here.
----

Emitted when the guards on the path to a construction prove the invariant false (<<invariant-discharge>>). The companion E2011 is a warning, not an error: it says the guards do not establish the invariant, so the check remains at run time.

[#e2012]
=== `as` names what a construction builds

[,text]
----
`as` names the value a construction builds, and this is not a construction.
Hint: Write the construction whose invariant decides the branch, or drop the `as` and give
a condition.
----

Emitted for the forms of an attempted construction that cannot be read (<<attempted-construction>>). Attempting a type that declares no invariant is E2013, since the `+else+` value could never be reached.

[#e2014]
=== A clause answered by name does not exist

[,text]
----

Emitted when a per-clause departure names a clause the type does not declare (<<attempt-departures>>, <<invariant-clause-name>>). The rest of that form is checked with its own codes: a clause that can fail and has no arm is E2015, unnamed clauses left unanswered E2016, a `+| _+` with nothing to answer E2017, arms with no attempted construction to answer for E2018, and a clause answered twice E2019.

[#example]
== Example: the business-trip application model

An example transcribing the spec DSL (`+chapter10/types-and-states.dsl+` and others) to Souther. Each definition is annotated with its corresponding spec DSL in a comment.

[,text]
----
module example.businesstrip exposing (
    TravelRequest,
    submitTravelRequest,
    preApprove
)

// --- value types (a simple value + a constraint comment in the spec DSL → invariant) ---
// data Amount = Integer // at least 0, in yen
data Amount = Int
    invariant value >= 0

// data EmployeeId = String // not empty
// newtype (the data X = Y form). The derived Decoder reads from bare text and checks the invariant.
// Normalization (trim, etc.), if needed, is done in a boundary-side custom Decoder.
data EmployeeId = String
    invariant String.length(value) > 0

// --- a nested sum with unit cases and a newtype ---
// data Rank = Manager OR Staff / data Manager = Level / data Level = Integer // 1..5
data Rank = Manager | Staff
data Level = Int
    invariant value >= 1 && value <= 5
data Manager = Level       // a newtype over Level
data Staff

// data CostBearer = OwnCost OR ClientCost / data OwnCost = Reimbursement OR Advance OR CorporateCard
data CostBearer = OwnCost | ClientCost
data OwnCost     = Reimbursement | Advance | CorporateCard
data Reimbursement
data Advance
data CorporateCard
data ClientCost

// --- product (role name ≠ type name) ---
// data Employee = EmployeeId AND Rank AND ManagerId
data Employee =
    { id: EmployeeId
    , rank: Rank
    , managerId: EmployeeId
    }

data TravelRequestCommon =
    { applicant: Employee
    , estimatedCost: Amount
    , destination: String
    , purpose: String
    , startsOn: Date
    , endsOn: Date
    }

// --- sum of states (case = named data, common items taken in flatly by a ... spread) ---
// data TravelRequest = Drafting OR Submitted OR AwaitingPreApproval OR PreApproved
// The derived Decoder reads the discriminator "type", dispatching by tag = case name ("Drafting", etc.).
// To read by a DB "status" or an English tag ("draft", etc.), use a boundary-side custom Decoder.
data TravelRequest =
    Drafting | Submitted | AwaitingPreApproval | PreApproved

data Drafting = { ...TravelRequestCommon }
data Submitted = { ...TravelRequestCommon, submittedAt: DateTime }

data PreApprovalReason = HighValueTravel | InsufficientAuthority | ClientCost
data HighValueTravel = { threshold: Amount }
// data InsufficientAuthority = Rank (a newtype)
data InsufficientAuthority = Rank
data ClientCost

data AwaitingPreApproval =
    { ...TravelRequestCommon
    , submittedAt: DateTime
    , preApprovalReasons: List<PreApprovalReason>
    }

data PreApproved =
    { ...TravelRequestCommon
    , submittedAt: DateTime
    , preApprovedAt: DateTime
    , preApprover: EmployeeId
    }

// NotAuthorized is just data (a failure is ordinary data; no error declaration)
data NotAuthorized

// --- behavior specifications (the spec DSL's behaviors line up as is) ---

// depends: clock → no implementation. Injected from Java
behavior now : () -> DateTime

// behavior decidePreApproval = EstimatedCost AND Applicant AND CostBearer -> PreApprovalReasons
behavior decidePreApproval : (
    estimatedCost: Amount,
    applicant:     Employee,
    costBearer:    CostBearer
) -> List<PreApprovalReason>
    constructs HighValueTravel, InsufficientAuthority, ClientCost

// behavior submitTravelRequest = Drafting -> Submitted OR AwaitingPreApproval (both success → bare sum)
behavior submitTravelRequest : (request: Drafting) -> Submitted | AwaitingPreApproval
    constructs Submitted, AwaitingPreApproval

// behavior preApprove = AwaitingPreApproval AND ApproverId -> PreApproved OR NotAuthorized (a failure is a case too)
// depends: clock → write it in depends on
behavior preApprove : (
    request:    AwaitingPreApproval,
    approverId: EmployeeId
) -> PreApproved | NotAuthorized
    depends on now
    constructs PreApproved, NotAuthorized

// --- implementations ---

let decidePreApproval (estimatedCost, applicant, costBearer) = { ... }

let submitTravelRequest (request) = { ... }

// precondition: approverId equals the applicant's managerId
// depends on now appears as the last argument
let preApprove (request, approverId, now) = {
    guard approverId == request.applicant.managerId
        else NotAuthorized

    PreApproved { ...request, preApprovedAt = now(), preApprover = approverId }
}
----

The type of `+preApprove+`:

[,text]
----
preApprove :
    Behavior<{now}, (AwaitingPreApproval, EmployeeId), PreApproved | NotAuthorized>
----

All three of `+Behavior+` come from the declaration: `+{now}+` is `+depends on+`, the input is the argument list, the output is the right of `+->+`. The `+let+` has 3 arguments because it is pre-injection; when `+PreApprove.bind(clock)+` fixes the last argument, it becomes the declared 2-argument type (<<depends-on>>).

`+...request+` copies the common items and `+submittedAt+` of `+AwaitingPreApproval+` by name, ignores `+preApprovalReasons+` (not in `+PreApproved+`), and adds `+preApprovedAt+` and `+preApprover+` to construct.

[#java-example]
== Java-side implementation example

[,java]
----
// extends the abstract base FindMember generated for a behavior with no implementation (not implements).
public final class JdbcFindMember extends FindMember {
    private final DataSource dataSource;

    public JdbcFindMember(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    @Override
    public FindMemberResult apply(MemberId id) {   // the generated sealed union: Member | NoSuchMember | CorruptStoredData
        try (var connection = dataSource.getConnection();
             var statement = connection.prepareStatement(
                 "select id, email, display_name from member where id = ?")) {

            // value extraction goes through the encoder. MemberId is a newtype, so encode is a bare String.
            statement.setString(1, MemberId.encoder().encode(id));

            try (var resultSet = statement.executeQuery()) {
                if (!resultSet.next()) {
                    return NoSuchMember();                            // inherited protected factory
                }
                var raw = Map.<String, Object>of(
                    "id",   resultSet.getString("id"),
                    "Mail", resultSet.getString("email"),
                    "displayName", resultSet.getString("display_name"));

                // decode is a Raoh Result<Member>. An invariant violation maps to the CorruptStoredData case
                return switch (Member.decoder().decode(raw, Path.ROOT)) {
                    case Ok<Member> ok   -> ok.value();              // Member (mainline)
                    case Err<Member> err -> CorruptStoredData();          // inherited protected factory
                };
            }
        } catch (SQLException e) {
            // A platform failure is not folded into a case but thrown. Souther passes it through; the boundary handles it (503, etc.).
            // SQLException is checked, so wrap it in a non-checked exception of the DataAccessException family the boundary catches
            // (not IllegalStateException or a bare RuntimeException — those pass through the handler and make infrastructure failure look like a bug).
            throw new DataAccessResourceFailureException("member lookup failed", e);
        }
    }
}
----

Binding to a composition behavior:

[,java]
----
var handle = Handle.bind(new JdbcFindMember(dataSource));
var result = handle.apply(rawInput);
----

[#non-functional]
== Non-functional requirements

* compile errors are rendered from structured data — a code, a source region, a message, and hints; the human form quotes the source with a caret, a JSON form (`+--format json+`) is available for tools, and messages are localized (Japanese by default, English available)
* the generated `+.class+` passes standard verification and is usable straightforwardly from Java 25+
* each compiler stage is independently testable
* souther-runtime does not depend on Raoh; the generated bytecode uses Raoh directly for decoder/encoder, and the Raoh dependency is on the generated code and the app side
* the language core does not depend on the Java class model
* the requirement set is tracked statically; a simple behavior reconciles declaration and implementation, and a composition infers from its stages
* generated code exposes no API bypassing invariants
* one spec DSL definition maps to one Souther definition with no intervening translation

[#core-semantics]
== Core semantics

Souther tracks two things about a data.

[,text]
----
which values are that data
which expressions have the authority to construct that data
----

It tracks three things about a behavior.

[,text]
----
input type   output type (sum of possible business results)   the set of required dependencies
----

A behavior conceptually has the type:

[,text]
----
Behavior<Requirements, Input, Output>
----

There is no fourth slot separating failure. A failure is one of the cases of Output, and whether it departs the mainline is decided by composition. `+>->+` simultaneously performs output-case routing (flowing cases the downstream consumes, propagating the rest) and requirement-set composition.

[,text]
----
f : Behavior<R1, A, O_f>
g : Behavior<R2, B, O_g>
f >-> g : Behavior<R1 ∪ R2, A, (O_g) | (sum of O_f minus the consumed part)>
----

This rule is Souther's central composition semantics. Output corresponds to the spec DSL's `+-> Out OR ...+`, and the requirement set to `+// depends+` / `+// side effect+`. What the author states explicitly is input, output (a bare sum), dependencies (`+depends on+`), and construction authority (`+constructs+`). On the same line as the spec DSL writing `+// depends:+` at a leaf but not on a composition, only a composition is left to inference (<<depends-on>>, <<composition-with-requirements>>).

`+Requirements+` is an argument fixed by injection, not a dynamically handled effect. So on the `+let+` side it appears as an ordinary argument, and `+bind+` partially applies it (<<depends-on>>). `+Behavior<R, I, O>+` can be read as `+(I, R) -> O+` closed over `+R+`. That is why no variable enters the requirement set, and that keeps the whole system simple.

Souther maps a specification model to an implementation model with minimal translation by promoting the value constraints, construction paths, and outside-world dependencies the spec DSL left in comments to invariants, confinement of construction paths, and `+depends on+` with injection.
