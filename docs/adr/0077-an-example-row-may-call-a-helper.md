# ADR-0077: An example row may call a helper

Status: Accepted. Extends ADR-0072, builds on ADR-0032 and ADR-0075. What bounds a row is amended by ADR-0052's counted budget and by #1159.

## Context

An `example` row states an input, an expected result, and the value it fakes a dependency with. ADR-0072 let a row *name a value*, so the representative input a module's rules are written against is stated once. A row could not *call a helper*, and since ADR-0075 a helper is the shared statement of a rule — the thing a behavior's example is usually about. So a row restated the rule's result as a literal: it said `Amount(121)` where it meant "the taxed price of 100", and nothing connected the two. That is the duplication issues #163 and #197 removed everywhere else.

The three positions behaved three different ways, measured on the module in issue #200. In an input, refused: `E1903: `taxed` is not a newtype; a fixture cannot call it`. In an expected result, not refused and answered wrongly — the expected side was never built, so the row failed against a value nothing had built and reported `expected Receipt but was Receipt { total = 110 }` when the row was correct. In a `with` value, reported as `E1908: `bill` depends on `quote`, but no fake is given for it`, with the true reason on the hint: a fake *was* given and could not be built.

Issue #200 proposed expanding a row's helper calls before the fixture is built, on the grounds that the fixture builder's rule — literals, records, collections, newtype applications — would then be unchanged. It is not. Expanding the simplest realistic helper leaves the fixture builder exactly what it has no case for:

```
let taxed (a: Amount) = Amount(a.value * 11 / 10)

taxed(Amount(100))
  ->  LetIn($0_a = Amount(100), Amount(FieldAccess($0_a, value) * 11 / 10))
```

`LetIn`, `FieldAccess` and `/` are none of them fixture forms, and the folder's arithmetic is `+`, `-`, `*` over two literals. Expansion is not a way to avoid an evaluator; it is a way to need one. ADR-0032 already answered this question for a constant construction's invariant: run the generated bytecode rather than fold it a second time, so there is no second evaluator to disagree with the first.

## Decision

**A fixture may call a helper**, wherever a fixture value is written: an input, an expected result, a `with` value, a `fake` table's input or output, a record field, a list element, a map key or value, and an argument of another helper call. This is the fourth thing a fixture may apply, beside a newtype, `Date`/`DateTime`, and `Set.fromList`/`Map.fromList`.

**An operand is run, and its result is re-materialised.** These are two steps and are kept apart:

1. The value a row writes at a position is compiled as a definition of the module — taking nothing, answering with that value — and emitted into the same program the behavior is applied in, where it is run as a static method on `$Fns` (ADR-0038). Everything the operand writes is inside it, the helpers it calls among them.
2. The value it answers with is re-materialised into the neutral form a fixture is written in, and the row's reading continues around it.

No runtime value travels into a fixture build around the call. That is what keeps a helper from putting its internal representation into a fixture, and it is now the same fact as the operand being one definition: there is no build around the call to travel into.

These two steps read differently until #681, and what they replaced stood until #743. The unit was the helper call rather than the operand: each helper a row named was applied on its own — its arguments built as fixtures against its settled parameter types (ADR-0066), the call made through a method emitted for it, the answer re-materialised — and the fixture build continued around the result. That was one path for a call at the top of a position and one nested inside a record, which is what it existed to be. Compiling the operand made the whole of it one call, so the paths cannot part. The reading that applied helpers one at a time was then unreachable and was left in place, which is what #743 measured — across the compiler, CLI, LSP and build-driver suites and every `souther-examples` module, 4030 operands run and not once a helper applied through it — and removed. Every paragraph below marked the same way was true when it was written, stopped being true at #681, and says so from #743.

**Re-materialisation is the inverse of writing the fixture**, and is directed by the declared types rather than by the boundary encoding. A scalar or a temporal is its own neutral form. A collection is re-materialised element by element. A data is read field by field through the accessor every data has (ADR-0065), each field against its declared type, and a case of a sum takes the discriminator its sum's decoder reads — which is what a written record fixture is built as, so one decoder reads both. An empty optional is left out, as writing `None` leaves it out.

Going through the derived `encoder()` instead was measured and does not hold: a `Date`'s neutral form is a `LocalDate` while its encoder writes ISO text, so a newtype over a date came back as text its own decoder refuses. The encoder answers what the boundary reads, which is a different question from what a fixture is written as, and only the second one has a decoder waiting for it here.

A value that cannot be read back is one diagnostic with the reason under it — a field the accessor cannot reach, or a type this module cannot name.

The invariant of the result type is evaluated at the helper's own construction and again when the re-materialised value is decoded. An invariant is pure and total, so there is no difference in meaning; it is counted in the row's time budget, and re-checking a value that has crossed the JVM boundary back into a fixture is consistent with every other fixture being decoded.

**What is emitted is a method per operand, and nothing for what the operand names.** A helper a row calls is expanded into the operand's definition by the pass that expands a call in any body, and a kernel is lowered at its call site inside it. A recursive helper is the exception, and not because a row named it: expanding one would not terminate, so it is a method wherever it is reached — in a body, in an invariant, in a row alike. What a module takes on is exactly what it reaches that recurses.

This paragraph said, until #743, that a method was emitted for every non-recursive helper a row named. Nothing had called one since #681, and emitting one was not merely spare work. Taking a helper on puts the declaration another module wrote into this module's check and codegen, where a rule can refuse it: a helper whose body answers no value can stand where a position states a type and cannot be emitted as a method, so a module that compiled alone was refused, at its own line, for a claim a row in another module had made about a definition it exported. The same reading refused a declaration in the module that wrote it, depending on whether a row somewhere named it.

**A helper a row cannot apply is refused by the rule it breaks.** A helper whose body produces a function is one: applied by a row, the block escapes as the operand's answer, and no position that takes a value holds one (E1809). The rule that a fixture may apply a helper keeps no exception of its own to explain, which is what this has always been for.

This paragraph read differently twice. Until #680 it named an intrinsic as having no method, and had the refusal tell a standard-library function apart and refuse it as one — a fixture may not apply a library function however it is implemented. That rule was never held: a library function written in Souther was emitted for the row that applied it and ran, so `Int.abs` was applied while `String.length` was refused, and nothing about what either means accounted for the difference. What decided was whether `exampleHelpers` had a body to emit a method from. It then read, until #743, as a refusal of its own — nothing emitted a method for this, so there is nothing to run — which was a sentence about the emission rather than about what the row wrote. With the operand compiled, what refuses is the language's own rule about where a block may go, said at the block.

**What a row may apply is a property of the call, not of the declaration.** A declaration carrying type variables was refused for carrying them, which read the declaration alone and so refused `List.length([ 1, 2 ])` although the row had written what `'a` is. What the written arguments settle is what decides, and a call is applicable where it is written or nowhere: the reason a row is given is about what the row wrote.

What settles them is the elaboration the operand goes through, which is the one every body goes through, so a row settles a variable exactly where a body settles it — an empty collection reaches the bottom it reaches anywhere, and `List.isEmpty([ ])` runs rather than being refused for a variable nothing wrote. A separate reading used to settle the call and hand a witness to an emitter that wrote a wrapper method per instance, a kernel's lowering being able to read the type it is applied at — `List.sum` chooses between summing `Int` and summing `Decimal`. Inside the operand that lowering happens at the call site, at the instance the elaboration settled, so there is nothing left for a second reading to settle or a wrapper to carry, and no variable it could refuse a row over that a body would have admitted. What made that safe is unchanged and is still measured: a body carrying an open variable into such a kernel is refused where it is written.

**A published helper a row names is expanded into the reader's operand**, which is what ADR-0075 already says a published body is for: it arrives closed, with its own module's values and non-recursive helpers substituted into it, and what stays standing is a call to a recursive helper of the declaring module, which the reader emits as its own. Nothing else of the declaring module's crosses. The reader used to emit a method for the published helper too, on the ground that `$Fns` is package-private everywhere and the declaring module emits none for a non-recursive helper of its own — so calling the owner's would change one module's output because another module's example calls it. That ground still holds; what is gone is the method, there being no call to it.

**The budget is the row's.** Running the operands, re-materialising, decoding, applying the behavior and comparing the result are one evaluation under the existing per-row wall-clock budget, so a row cannot buy more time by calling more helpers. A row that does not finish is E1910. It named the helper it was in until #681 and stopped answering there, the register having nothing left to write to it; #743 removed the wording. An operand is compiled code, so where execution has got to inside it is the JVM's and not something this compiler holds. Answering it again would mean instrumenting the operand to publish its own provenance, which is a different thing from anything decided here.

**A row that cannot build its expected value says so.** E1905 is a mismatch between two values, and is reported only when both exist; an expected value that cannot be built is E1903 under its own message, naming the expected position. A `with` value that cannot be built is E1908 under its own message, told apart from the dependency that has no fake at all. Both are wrong answers today independently of anything above, and are corrected first.

### Amended: what bounds a row, and what a row that does not finish is told

The paragraph above says the evaluation is one under a per-row wall-clock budget and that a row which does not finish is `E1910`. Both were true when it was written and neither is now, and what it was deciding — that the whole of a row is one evaluation, so calling more helpers buys no more of anything — is untouched by either change.

What decides a row is counted rather than timed (ADR-0052). A row that passes more counted points than the policy allows, or recurses deeper than it allows, is `E1910`, and that reading is the same on every host. The clock is beside it and is a different question: it bounds the compiler's own time, and a row that spends it is `E1923` — the compiler failing to answer, not the model failing to terminate.

And the clock is over what the compiler owns, not over everything the row's thread passes through. A row driven from a Java binding reaches an implementation supplied from outside, which answers out of the caller's world; what it takes there is bounded by whoever owns that world and is not counted against the row (#1159). So "the budget is the row's" holds for both readings, with the clock's half of it saying: of the row's own time, the part this compiler is spending.

## Consequences

Issue #200 closes. An example of a behavior that applies a rule states the rule, and a change to the rule reaches the rows that are about it instead of leaving them passing for the wrong reason.

A value whose body calls a helper becomes fixture-evaluable, so ADR-0072's exclusion of it — a value "whose body computes" — is withdrawn. It follows from the row's own rule rather than being a second decision: a value's body is read the way a row's text is, so the helpers a row reaches are the ones its own text names *and* the ones the values it names apply, as far as those values name each other.

A row that states, on its expected side, the very rule the behavior under test applies asserts nothing: both sides compute the same thing, so the row holds whatever that rule does. Nothing refuses it. The useful applications are the input a rule produces, and an expected result stated in terms of a *different* rule than the one being tested — and telling those apart is reading the row, not checking it. This is accepted rather than overlooked: a check would have to decide that a behavior reaching a helper makes a row about it invalid, which is false whenever the behavior does something else with the result.

A row may now fail because of a helper rather than because of the behavior. That is the point — the alternative was a row that could not fail at all when the rule changed — but it puts the helper in the row's failure, so the diagnostic names it.

The generated `$Fns` carries a method per row operand, which nothing in the shipped module calls. A compile-time-only class already ships (`$Ctfe`, ADR-0032), and the alternative is a second emission path for methods that are the same methods. It also carried one per helper and per kernel instance a row named, which nothing has called since #681 — those went with #743.

`Backend.BOUNDARY_VERSION` does not move, and did not move when the emitted methods went away either. What an importing module reads out of a jar — declarations, published bodies, descriptors — is unchanged; the methods are package-private and no reader resolves them.
