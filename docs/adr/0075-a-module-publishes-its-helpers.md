# ADR-0075: A module publishes its helpers

Status: Accepted. Refines ADR-0005, revises ADR-0074.

## Context

ADR-0074 published a module's values and left publishing a *helper* — a `let` with parameters — open, naming three things it would bring with it: construction authority, an executable body under a compatibility contract, and a reader assembling calculation without going through a behavior. This decides those.

Without it, a module that wants another's pure calculation either restates it or declares it a behavior. Declaring it a behavior puts something in the behavior list that the specification does not name, and ADR-0005 keeps that list one-to-one with the spec DSL's. Restating it is the duplication issue #163 removed for values and left in place for rules.

## Decision

**`exposing` may name a helper.** A helper is one of a module's definitions, and what `exposing` lists is what the module offers. The `>->` restriction stays: a helper does not appear in the spec DSL, so it is not a stage.

**A published helper crosses closed**: its body with its own module's values and non-recursive helpers already substituted into it, expanded at the reader's call sites. A published value crosses as a reference to the execution its module owns (ADR-0074), and a helper crosses as executable source, so what a helper is built out of is emitted into the reader. A value and a helper are told apart by the predicate that decides it everywhere — a written parameter list — and a behavior's own `let` is neither, whatever its shape.

**A recursive helper travels with the body that calls it.** Closing cannot remove one: it is lowered to a method (ADR-0038), so the call stays a call. It comes along under the name of the module that declares it, and so does every recursive helper it reaches in turn — a mutually-recursive group arrives whole, and one the reader never imported arrives because the body it did import calls it. The importing module emits them as methods on its own `$Fns`, which is what it already does for a recursive standard-library helper it reaches.

The declaring module is the helper's *identity*, not where its method goes. `$Fns` stays package-private in every module, so publishing a helper opens no Java-reachable entry to a construction — what ADR-0002 gives up is not given up. Two modules may declare a recursive helper of one name and one importer may emit both; they are two methods, named apart, because a bare name could not tell them apart.

The alternatives are the ones issue #197 lists, and each fails on the same point: making `$Fns` public opens the Java entry, nestmates need a shared nest host that a different-package importer cannot join, publishing only helpers that construct nothing decides publishability from the body rather than the signature, and a Java-boundary wrapper is one more path to keep agreeing with the others.

**What a published body builds is not the reader's to declare.** Expansion makes a carried construction look like the reader's own, and the permission check would ask the reader for `constructs` on a type the declaring module may keep to itself — a name the reader has none of. Publishing the definition is what states that origination. A construction therefore records the module whose published body carried it, and the check reads that rather than the shape.

It is preservation, not a grant. What the mark covers is a type of the module that published the body; a type of some *third* module the body happened to build is neither the reader's nor the publisher's to hand over, so it stays the reader's to declare — which it can, because the module declaring it exposed it (ADR-0059). Declaring a carried construction anyway is not called building nothing.

The mark travels wherever a construction does. A recursive helper is not expanded, so what it builds reaches its caller through its construction set instead of through its body, and the two kinds stay apart the whole way — merged there, a reader declaring a carried construction was told it builds nothing. A unit data is built by being named rather than by a construction of its own, so the name carries the mark; that is also where which unit is meant is read from, since a reader may declare one spelled the same and it is not the same type.

**A published definition's type is what the exposed surface is asked about.** A helper's argument types join it, because a reader writes the arguments. Both are settled from the body (ADR-0066) and read as settled, rather than being stood in for by the constructions the body makes: those answer a different question and miss a definition that names a type it never builds — `let published (n: Int) : List<Hidden> = []` was published under the old reading, and a hidden unit data, which is built by being named, went out the same way. What the body reaches for on the way is not part of that surface, as for a value; it is asked a different question, next.

**A published helper's closed body must be runnable in every module that expands it.** Only the types a module exposes are public in its generated code, so a body that builds a type its module keeps to itself is a class the reader cannot link against, and the JVM refuses it when the reader runs. The module that publishes is the one that refuses, when it is compiled. What is held to the question is what the reader is given: the closed body of each helper the module exposes, and of every recursive helper that travels with it. A type that closing substitutes away is not in it, and one a private value contributes is, because a value a helper names is expanded into it. A published value is not asked, since it runs in its declaring module. What counts is a class the emitted code names: a type the body constructs, a unit data the body writes as a value, which is read from the shared instance of its class, a case a `match` tests against, the type whose fields are read, and the sum a comparison or a sort takes its order from. An exposed sum may keep its cases to itself, so a helper that matches them is refused too, and a sum may be kept while its cases are exposed, so a helper that compares two of them is refused as well: the class the order comes from is the sum, which the written comparison does not name.

That last is a fact about types, so the body is read as its reader types it, and what it names is what the emitter's own questions answer for it (`Ordering`, `Comparison`); the sort family's answer is one function that the emitter and this both read. A recursive helper is emitted as a method of its own, so what it takes and what it answers name classes as well, wherever it is called: a value comes out of a method's parameter or a call's result cast to its class. It is read as the check settled it (`EmittedDefinition`), which is the definition its reader emits. A node's type is counted where the emitter casts to it — a call's result, a function's parameter, an element of a tuple, the value an arm binds where binding it casts (`Core.Case.castOnBinding`), and the shape a position asks an `unreachable` to leave, which is read through the same `shapeOf` the emitter uses — or holds it in a field: what a function handed over as a value captures is a field and a constructor argument of its class (`BlockReaches`). A step the emitter runs as the loop body makes no class, so what it closes over names nothing and only the element it is handed is cast (`Core.Call.stepRunWhereItStands`). Which of the two a function is, and which arms cast, are answers the emitter reads from `Core` too, so that they are not decided twice. And a type is not counted for every node that has one: a local that widens a case to its sum is held as an object and never names the sum's class. The walk lists every kind of node, so one added to `Core` has to say which it is. A parameter that takes its type from the body is settled as the check settles it, so a helper with one is typed like any other, and a helper that checked on its own and cannot be typed as its reader types it is this compiler disagreeing with itself.

The emitter is what decides which references there are, and it names the class of a declared type at one place. That place refuses a class its module cannot reach, and the publishing rule is the early and precise form of the same refusal: a form of the tree it does not list is caught at emission, as a fault of the compiler rather than a diagnostic. A module that imports one that failed, for this or for any other reason, is not emitted, so the emitter's refusal never stands in for the failure already reported. This is a separate rule from the exposed surface: that one is about what a reader can write down, and this one is about what a reader can execute.

The reader does not check this again: it trusts that the module that published the helper was held to it, as it trusts the word `partial` (ADR-0098). That is why `Backend.BOUNDARY_VERSION` moves 21 → 22, and why a jar written before it is refused rather than believed.

Running a helper where it is declared, as a value does, would remove the rule and is not taken here. A helper is expanded so that what is known of its arguments at the call, including the element type it is used at and the function it is handed, can be used, and calling across a module boundary would need an entry that takes both.

**ADR-0074's refusal of a published value that reaches a recursive helper is withdrawn.** That rule refused what this ADR now carries, and it was not a corner: `let total = Amount(List.fold(...))` reaches `List.foldFrom` and could not be published. Reading the type rather than the constructions is what keeps the surface rule reaching through such a helper, which is not expanded and so has no construction inside it to read.

**The body a jar carries is under the boundary version.** A published body travels as source and is compiled by whoever imports it, so what the front end makes of it is part of what a compiled module promises. `Backend.BOUNDARY_VERSION` covers it, and moves for a change to how a carried body is read as surely as for a change to a descriptor — the difference being that such a change is the front end's rather than codegen's. `PublishedModule` already refuses a jar that disagrees, so the disagreement is reported as one.

## Consequences

Issue #197 closes. A rule is written once. `exposing` is no longer a list of behaviors plus a few values: it is what the module offers, and this is the last of ADR-0005's sentence about it to be refined.

The operation boundary thins, and nothing here prevents that. A reader may now assemble calculation out of published helpers without going through a behavior, so a module has two kinds of published API: behaviors, which are the business operations the specification names, and helpers, which are shared calculation. That a helper cannot be a `>->` stage is a fact about the spec DSL and not a mechanism — a published helper API can become the de facto business API, and no check will say so. This is accepted as the price of publishing, not overlooked: the alternative is the restatement issue #197 was raised about.

Duplication moves rather than disappearing. A non-recursive helper was already copied into each caller by expansion; a recursive one is now copied into each importing module. What is not duplicated is the decision about what the rule says, which is the point.
